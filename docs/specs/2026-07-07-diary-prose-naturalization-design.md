- 작성: 2026-07-07 (브레인스토밍 산출물)
- 선행: 코칭 v2.1(스펙 `docs/specs/2026-07-07-coaching-v2.1-design.md`, PR #14 머지). §8.1a로 `build_system_prompt`가 이미 "마스코트 1인칭 자기 일기" 관점.
- 백로그: 메모리 `diary-mascot-flavor-ideas` #2 (참조 github.com/epoko77-ai/im-not-ai).
- 다음 단계: writing-plans → `docs/plans/` → SDD → PR → 사용자 E2E → 다이어리 재생성.

## 1. 배경과 목표

다이어리는 LLM이 쓰는 한국어 프로즈라 전형적인 "AI티"(번역투·이중피동·과잉영어·기계적 나열·상투구·이모지 남발·리듬
획일·빈 헤지)가 새어나오기 쉽다. 목표는 다이어리 서사를 **진짜 사람이 캐주얼하게 적는 일기처럼** 자연스럽게 만드는 것.

**핵심 재프레이밍.** 참조한 im-not-ai는 *이미 쓰인 텍스트를 탐지→수술적 수정*하는 사후 파이프라인이다(그래서
"30% 초과 경고·50% 중단" 안전장치로 원문 과수정을 막는다). 우리는 사후 수정이 아니라 **생성 시점의 예방**을
택한다 — im-not-ai의 범주를 "탐지 규칙"이 아니라 "이렇게 써라 / 이건 피하라"는 *문체 가이드*로 번역해 시스템
프롬프트에 흡수한다. 따라서 im-not-ai의 % 안전장치는 우리 모드에 대응물이 없고, 팩트 안전은 기존 **정밀도의 선**
(브리프 사실·수치만 인용, 지어내기 금지)이 그대로 담당한다.

## 4. 코드 구조 (표면 최소 변경)

- `crates/core/src/diary/mod.rs`에 문체 규칙만 담는 재사용 조각 추가:
  ```
  pub fn voice_guidance() -> &'static str
  ```
  (`&'static str` 반환 — 나중에 #1/#3의 다른 태스크 프롬프트가 그대로 이어붙여 재활용.)
- `build_system_prompt`는 기존 페르소나·정밀도의 선·회고/다짐·occasions 지시를 **그대로 두고**, `format!`에
  `{voice}` 자리를 추가해 `voice_guidance()`를 조합만 한다. §8.1a 1인칭 관점 전환은 불변.
- 그 외 `render_diary`·`assemble_brief`·`finding_advice`는 **무변경**. `finding_advice`의 `detail`/`suggested_action`
  문구는 사실·방향 서술이라 그대로 두고(§8.1a 원칙), 문체 전환은 시스템 프롬프트에서만.

## 5. 문체 가이드 내용 (`voice_guidance()` 산출물)

생성 프롬프트에 흡수될 실제 지시. 긍정 보이스를 먼저 제시하고, 이 장르(1인칭 캐주얼 다마고치 일기)에 실제로
무는 회피 범주만 큐레이션한다.

### 5.1 긍정 보이스 (먼저)

> 진짜 사람이 그날 하루를 캐주얼하게 적는 일기처럼 자연스럽게 쓰세요. 문장 길이와 종결어미를 다양하게 섞고
> (짧은 감탄·구어 종결을 간간이), 담백한 구어체로.

### 5.2 회피목록 (im-not-ai 10범주 중 장르 큐레이션)

| # | 피할 것 | 예 |
|---|---|---|
| 1 | 번역투 | "~을 통해", "~에 대해", "작업을 진행/수행하였다"(do/have류 직역) |
| 2 | 이중·과잉 피동 | "읽혀지다", "보여지다", "되어지다" → 능동/단일 피동 |
| 3 | 과잉 영어 | 굳이 안 써도 될 영어 (단 기술 고유명 Read·Opus·MCP·플러그인/스킬 이름은 **보존**) |
| 4 | 기계적 병렬·번호목록 | findings를 1)2)3)·불릿 나열 → 하나의 이야기 흐름으로 녹임 |
| 5 | AI 상투구 | "결론적으로", "종합하면", "시사하는 바가 크다", "~라고 할 수 있다" |
| 6 | 이모지 **남용** | 문장마다 이모지 (아주 가끔이면 캐릭터상 OK — 완전 금지 아님) |
| 7 | 리듬 획일 | "~했다. ~했다. ~했다."처럼 같은 길이·같은 종결 반복 |
| 8 | **빈** 헤지 남발 | 습관적 "~인 것 같기도", "어느 정도", "다소" |

### 5.3 헤지 carve-out (정밀도의 선과 충돌 방지 — 핵심)

빈 헤지(습관적 얼버무림)는 제거하되, **브리프 수치·가설의 불확실성을 표시하는 헤지(추정·잠재·"~로 보여요")는
정밀도의 선이므로 반드시 유지**한다. R5 추정 토큰("~추정/잠재"), R10 "자동화 스크립트가 만든 패턴으로 보여요"가
그 예. 프롬프트에 이 둘을 혼동하지 말라고 명시한다.

### 5.4 예시 (form-only, 내용 아님)

- ❌ 어색함: "오늘은 총 세 개의 세션을 통해 작업이 진행되었고, 같은 파일이 여러 번 읽혀지는 상황이 발생하였다."
- ✅ 자연스러움: "오늘 세션 세 번. 같은 파일을 자꾸 다시 열었다 — 좀 헤맸네."

(이 예시는 번역투·이중피동·리듬 획일 제거와 구어 종결을 형태로만 보여준다. 브리프에 없는 사실은 넣지 않는다.)

## 6. 검증 / 테스트 기준

기존 룰/프롬프트 테스트 스타일(인메모리 + 문자열 계약 assert) 유지.

- **`voice_guidance()` 계약**: 반환 문자열이 핵심 지시 포함 — 긍정 보이스(구어체/다양), 번역투·이중피동 회피,
  기술 고유명 보존, 이모지 남용 금지, 예시 마커, 헤지 carve-out(추정/잠재 유지 문구).
- **조합 계약**: `build_system_prompt`가 `voice_guidance()` 내용을 포함(조각이 실제로 배선됨).
- **기존 계약 유지 (§8.1a·다이어리 확장 회귀 방지)**: `system_prompt_uses_self_diary_perspective`·
  `system_prompt_has_humor_evidence_and_occasions_instructions` 등 — 1인칭·주인 3인칭·회고/다짐·유머·detail·
  suggested_action·occasions 검증 계속 green. 정밀도의 선("지어내지 마세요") 문구 잔존 확인.
- **수동 E2E**: §7 재생성 후 실제 다이어리 육안 — AI티 감소·사실 보존.

## 7. 재생성 / E2E (작업 완료 후)
