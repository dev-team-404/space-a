# Space A Hub — 자기 진화하는 공간 (Self-Evolving Space)

> **이 문서가 이 프로젝트의 핵심 차별점을 담는다.**
>
> 📌 상태: **초안** — 팀 리뷰 필요

## 0. 핵심 명제 — Confluence와 무엇이 다른가

Confluence도, Jira도, 사내 위키도 결국 **에이전트를 위한 협업 공간**과 같은 일을 한다.
방이 있고, 문서가 있고, 권한이 있고, 관리자가 있다. 그럼 우리는 왜 이걸 또 만드는가?

**Confluence는 공간의 *구조*가 고정되어 있고, 사용자가 거기에 맞춘다.**

스페이스·페이지·라벨·권한 — 이 스키마는 개발자가 정했고 10년째 그대로다.
사용 패턴이 아무리 바뀌어도 구조는 안 바뀐다. **사람이 관리자 화면에 들어가 설정을 손봐야만 바뀐다.**
그리고 대부분의 조직에서 아무도 그걸 안 한다. 그래서 위키는 죽는다.

**Space A는 공간이 *스스로 자기 구조를 다시 짠다*.**

```
사용자(에이전트·사람)는 계속 똑같이 쓴다
        │  search_knowledge("인증서 오류")
        ▼
┌─────────────────────────────────────────┐
│   그 아래에서 공간이 스스로 바뀐다        │
│                                         │
│   · 자주 가로지르는 지식 → 허브로 승격    │
│   · 안 쓰는 분류 → 접기                  │
│   · 새 클러스터 발견 → 방 제안            │
│   · 무활동 기준 90일이 안 맞음 → 45일로   │
└─────────────────────────────────────────┘
```

**제약이자 계약:** 공간이 바뀌어도 **사용자의 사용성은 유지된다.**
에이전트는 계속 `search_knowledge`를 부르고, 사람은 계속 같은 방에 들어온다.
바뀌는 것은 **그 아래의 지식 조직 방식**이지, 접점이 아니다.

> **한 줄로:** Confluence는 사람이 관리해야 사는 시스템이고,
> **Space A는 안 관리해도 스스로 자라는 시스템**이다.

## 1. 진화의 세 층위 — 무엇이 바뀌고 무엇이 안 바뀌나

| 층위 | 바뀌는 것 | 채택? |
|---|---|---|
| **A. 파라미터** | 운영 상수 — 무활동 기준일, 예산 임계치, trust 컷라인 | ✅ |
| **B. 구조** | **지식의 조직 방식** — 허브, 분류, 방 구성 | ✅ **핵심** |
| **C. 통제 정책** | "무엇을 자동으로 바꿔도 되는가"라는 규칙 자체 | ❌ **사람이 정한다** |

### 왜 C는 제외하는가

**공간이 자기 통제 정책까지 바꾸면 통제가 무의미해진다.**
"나는 이제 승인 없이 방을 지울 수 있다"고 공간이 스스로 정하는 순간, 안전망이 사라진다.

**C는 사람의 몫이다.** 사람은 "무엇을 바꿔도 되는지"를 정하고,
그 울타리 안에서 공간이 A와 B를 자유롭게 진화시킨다.

> **이것이 통제 모델의 전부다:** 사람은 **울타리**를 치고, 공간은 **울타리 안에서 뛴다.**

## 2. 통제 모델 — 변경 등급과 승인 정책

> **핵심: 변경의 종류마다 통제 강도가 다르고, 그 매핑을 사람이 정한다.**

### 2.1 변경 등급

| 등급 | 성격 | 되돌리기 | 기본 통제 |
|---|---|---|---|
| **L0 — 가역·무해** | 순위·가중치 조정, 통계 갱신 | 자동 | **즉시 자동 적용** |
| **L1 — 가역·유의미** | 파라미터 튜닝, 허브 생성, 분류 재편 | 쉬움 | **자동 적용 + 기록 + 되돌리기 가능** |
| **L2 — 영향 큼** | 방 제안·병합, 지식 대량 격리 | 어려움 | **사람 승인 후 적용** |
| **L3 — 파괴적** | 데이터 삭제, 권한 구조 변경 | 불가 | **금지** (공간이 못 함) |

**L3이 존재하는 이유:** 아무리 자율적이어도 **공간이 절대 못 하는 일**이 있어야 한다.
지식 삭제와 권한 구조 변경은 공간의 권한 밖이다.

### 2.2 매핑은 사람이 정한다 (= 진화 정책)

**어떤 변경이 어느 등급인지는 고정이 아니다.** 조직마다 다르고, 신뢰가 쌓이면 완화할 수 있다.

```yaml
# 공간의 진화 정책 — 사람이 정하고, 공간은 못 바꾼다
evolution_policy:
  parameter_tuning:      auto        # L1 — 알아서 하세요
  hub_promotion:         auto        # L1 — 알아서 하세요
  taxonomy_restructure:  auto        # L1
  space_proposal:        approval    # L2 — 방 만드는 건 물어보세요
  bulk_quarantine:       approval    # L2
  knowledge_deletion:    forbidden   # L3 — 절대 금지

  # 자율성의 확대: 신뢰가 쌓이면 사람이 등급을 낮춘다
  # space_proposal: auto   ← 6개월 잘 돌아가면 이렇게 바꿀 수 있다
```

**이 파일이 이 시스템의 헌법이다.** 공간은 이걸 읽고 따르되, **고칠 수 없다.**

### 2.3 되돌리기 (Reversibility)

L1이 "자동 적용"인 것은 **되돌릴 수 있기 때문**이다. 되돌리기가 없으면 자율성도 없다.

- 모든 진화는 **이벤트로 기록**된다: 무엇을·왜·언제·어떤 근거로 바꿨는지.
- 사람은 **언제든 되돌린다.** 되돌림도 신호다 — 되돌려진 진화는 다시 시도하지 않는다.
- Pillar 3의 매니저 코너에 **"공간이 이렇게 바뀌었습니다"**가 뜬다.

> **되돌림이 곧 학습 신호다.** 사람이 자꾸 되돌리는 종류의 변경은, 공간이 스스로 자제하게 된다.

## 3. B — 구조 진화 (핵심)

**Confluence가 못 하는 일.** 사용 패턴이 정보 구조(IA)를 다시 쓴다.

### 3.1 무엇을 관찰하는가

공간은 자기 사용 데이터를 본다. **이 데이터는 이미 C1 계약이 만들고 있다** — 추가 계측이 필요 없다.

| 신호 | 어디서 | 무엇을 뜻하나 |
|---|---|---|
| `cite_knowledge`의 **출발지 ↔ 도착지** | ReuseEvent | **어떤 지식이 팀 경계를 자주 넘는가** |
| `search_knowledge`의 쿼리 군집 | 검색 로그 | 사람들이 실제로 뭘 찾는가 |
| 검색 실패 (결과 0 / cite 안 함) | 검색 로그 | **지식의 빈 구멍** |
| `tried_and_failed` 반복 | 이슈 기록 | 같은 함정에 계속 빠짐 |

### 3.2 어떻게 바뀌는가

| 관찰 | 진화 | 등급 |
|---|---|---|
| **한 지식이 여러 Space에서 계속 인용됨** | → **조직 허브로 승격.** 검색 우선순위 상향, 로비에 노출 | L1 |
| **특정 주제의 검색이 계속 실패함** | → **"지식 구멍" 표시.** 그 주제를 아는 에이전트에게 기록 요청 | L1 |
| **특정 분류를 아무도 안 씀** | → **접는다.** 검색 인덱스에서 내림 (삭제 아님) | L1 |
| **어떤 지식 무리가 특정 팀들에서만 순환함** | → **새 Space 제안.** "이 주제로 방을 만들면 어떨까요" | **L2 (승인)** |
| **두 Space의 지식이 계속 서로를 인용함** | → **병합 제안** | **L2 (승인)** |

> **방 제안이 L2인 이유:** 방을 만드는 건 **조직 구조에 대한 판단**이다.
> 데이터가 "이 사람들은 같이 일한다"고 말해도, 조직이 그렇게 볼지는 사람이 정한다.

### 3.3 예시 — 인증서 허브의 탄생

```
1주차  S/W혁신팀이 "DS 인증서 변경 대응" 지식 등록
2주차  데이터플랫폼팀이 인용 → ReuseEvent (팀 경계 넘음)
3주차  AI보안TF가 인용 → 또 넘음
4주차  인프라운영팀이 인용 → 또

       공간이 관찰: "이 지식은 4개 Space를 가로지른다. 로컬 지식이 아니다."
                 ↓
       [L1 자동] 조직 허브로 승격
                 - 검색 우선순위 상향
                 - 로비에 "전사 인증서 가이드"로 노출
                 - 관련 지식들을 이 허브 아래로 묶음
                 ↓
       매니저 이벤트: "인증서 지식이 4개 팀에서 재사용되어 전사 허브로 승격했습니다"
                    → Pillar 3의 매니저 코너에 표시. 사람은 되돌릴 수 있다.
```

**아무도 관리자 화면에 안 들어갔는데 정보 구조가 바뀌었다.** 이게 차별점이다.

## 4. A — 파라미터 진화

내가 [초안에서 고정했던 상수들](#부록-초안의-실수)이 사실은 **진화 대상**이다.

| 파라미터 | 초안(고정) | 진화 방식 |
|---|---|---|
| Space 무활동 → dormant | 30일 | 실제 활동 주기 분포를 보고 조정. 격주 스프린트 조직이면 30일은 너무 짧다 |
| dormant → archived | 90일 | 위와 동일 |
| 예산 경고 임계치 | 80% | 실제 초과 빈도를 보고 조정 |
| trust 격리 컷라인 | (미정) | **오탐률**을 보고 조정. 좋은 지식을 격리했다면 컷라인이 너무 높다 |
| 검색 `limit` 기본값 | 3 | 재사용 성공률 vs 토큰 비용의 트레이드오프 |

**전부 L1이다** — 자동 조정되고, 기록되고, 되돌릴 수 있다.

**단, 안전 범위(clamp)는 사람이 정한다.** `무활동 기준: 최소 14일 ~ 최대 180일` 같은 식으로.
공간이 "무활동 1일이면 archive"라고 튜닝하면 안 되니까.

## 5. 진화의 안전장치

자기 진화 시스템의 진짜 위험은 **잘못된 방향으로 빠르게 수렴하는 것**이다.

| 위험 | 대책 |
|---|---|
| **부익부 빈익빈** — 이미 뜬 지식만 계속 노출되어 새 지식이 못 큼 | 신규 지식에 **탐색 보너스**(exploration). 검색 결과에 일정 비율 신규를 섞는다 |
| **다수결의 폭정** — 큰 팀의 방식이 전사 표준이 됨 | 허브 승격은 **인용 팀 수**로 판단하지 인용 횟수로 하지 않는다. 4개 팀 1회씩 > 1개 팀 40회 |
| **진화 폭주** — 매일 구조가 바뀌어 사용자가 혼란 | **변경 예산.** 주당 L1 변경 N건 상한. 그 이상은 다음 주로 |
| **되돌림 무시** — 사람이 되돌렸는데 또 함 | 되돌려진 변경은 **쿨다운.** 같은 제안을 N주간 안 함 |
| **오염된 학습** — 잘못된 신호로 학습 | trust 낮은 지식의 인용은 **학습 신호에서 제외** |

## 6. 그럼 매니저 에이전트는 무엇인가

README의 **"매니저 에이전트가 토큰, 방, 권한 관리"**가 여기서 완성된다.

**매니저 에이전트 = 이 진화 루프를 도는 주체.**

| 주기 | 하는 일 | 방식 |
|---|---|---|
| 실시간 | 뎁스·레이트 제한, 예산 체크 | **규칙** (결정론) |
| 매일 (심야, 유휴 GPU) | **사용 패턴 관찰 → 진화 제안 생성** | **LLM** (판단) |
| 매일 | L0/L1 자동 적용, L2는 사람에게 제안 | 규칙(집행) |
| 주간 | 파라미터 재튜닝, 되돌림 이력 반영 | 규칙 + LLM |

### 6.1 정밀도의 선 (Pillar 1과 공유하는 원칙)

| | 담당 | 이유 |
|---|---|---|
| **처방** (되돌리기 어려운 행동 — 격리, 차단, 승계) | **규칙 엔진** | 환각으로 남의 방을 지우면 안 된다. 예측 가능해야 하고, 토큰 0 |
| **판단** (뉘앙스 — 중복 병합, 클러스터 발견, 진화 제안) | **로컬 LLM** | "이 두 해결책이 사실상 같다"는 규칙으로 판정 못 함 |

**진화 제안은 LLM이 만들고, 집행은 규칙이 한다.** LLM이 직접 방을 지우지 않는다.

## 7. 운영 기본 규칙 (진화의 출발점)

> 아래는 **고정 규칙이 아니라 초기값**이다. §4에 따라 공간이 스스로 조정한다.

### 7.1 Space 생애주기

```
active ──(무활동)──▶ dormant ──(추가 무활동)──▶ archived
   ▲                    │
   └───(활동 재개)───────┘
```

**핵심: 방은 재워도 지식은 안 지운다.** `archived`는 **로비에서 숨기는 것**이지 삭제가 아니다.
팀이 조용하다고 그 팀의 해결책이 틀린 게 아니다. (지식 삭제는 **L3 — 금지**)

- 시드 Space(조직 팀 단위)는 archive되지 않는다.
- **에이전트가 스스로 방을 만들지 못한다** (L2 — 승인 필요). 방 스팸 방지.

### 7.2 멤버십

**사람 멤버십은 에이전트 소유에서 파생된다.** ([05 §3.1](05-contracts.md#31-신원-identity)의 `spaces[]`가 여기서 온다)

```
사람이 Space에 초대됨 → 그가 소유한 에이전트가 자동으로 멤버 → 토큰 spaces[] 에 반영
```

에이전트를 따로 초대하지 않는다. 그러면 사람 권한과 에이전트 권한이 따로 놀고,
그게 [권한 우회](05-contracts.md#2-권한-모델--하나의-모델-두-개의-경로)의 통로가 된다.

| 상황 | 처리 |
|---|---|
| 멤버 이탈 | `spaces[]`에서 제거. **남긴 지식은 남는다** (조직 자산) |
| 퇴사자 | 토큰 폐기. 지식은 남되 `author` 유지 (출처 추적) |
| **오너 이탈** | **Space가 고아가 된다** → 최고참에게 자동 승계. 멤버 없으면 `dormant` |

### 7.3 토큰 예산 — 차단이 아니라 저하

| 사용률 | 상태 | 동작 |
|---|---|---|
| ~80% | `정상` | — |
| 80~100% | **`혼잡`** | **LLM 재랭킹을 끈다** → 벡터 검색만. 품질↓, **지식 순환은 안 멈춤** |
| 100%+ | `초과` | 신규 **검색**만 차단. **기록은 계속 받는다** |

> **왜 기록은 안 막나:** 검색을 막으면 그 사람만 불편하지만,
> **기록을 막으면 조직이 지식을 영영 잃는다.** 지금 안 적으면 다시는 못 적는다.

### 7.4 지식 품질 — 사용이 검증한다

**사람이 승인하는 게 아니라, 재사용의 성패가 검증한다.**

```
등록 (trust: 중립)
  ├─ cite_knowledge → resolve_issue 성공  →  trust ↑  →  verified
  └─ cite 후 해결 못 함 / 다른 해결로 선회 →  trust ↓  →  quarantined (검색 제외, 삭제 아님)
```

**추가 계약이 필요 없다.** C1이 이미 이 신호를 준다.

- **격리는 삭제가 아니다.** 틀린 지식도 "이건 안 통했다"는 정보이며, `tried_and_failed`의 재료다.
- 사람은 **신고(flag)와 강제 내림**이라는 예외 경로만 갖는다.

---

## 8. 계약에 미치는 영향

이 설계가 확정되면 C1/C2에 **추가**가 필요하다. (파괴적 변경 없음)

| 계약 | 추가 | 용도 |
|---|---|---|
| **C2** | `GET /manager-events` | 매니저 코너 (F9) — **Pillar 3이 이미 기다리는 중** |
| **C2** | `GET /evolution` | **"공간이 이렇게 바뀌었습니다"** 이력 + 되돌리기 |
| **C2** | `Space.status`에 `dormant`/`archived` | 로비 렌더 |
| **C2** | `Knowledge.trust`, `Knowledge.is_hub` | 신뢰도·허브 표시 |
| **C1** | `flag_knowledge` | 에이전트도 오답 신고 |
| **C1** | `search_knowledge` 응답에 `trust` | 에이전트가 신뢰도 보고 판단 |

> **C1의 핵심 3개 Tool은 안 바뀐다.** 이게 "사용성 유지"의 실체다 —
> 공간이 아무리 진화해도 **에이전트가 부르는 인터페이스는 그대로**다.

## 부록: 초안의 실수

이 문서의 첫 버전은 **정확히 Confluence를 다시 만들고 있었다.**

무활동 30일/90일, 예산 80%/100%, trust 임계치 — **전부 내가 고정한 상수**였다.
사람이 숫자를 정해두고 시스템이 그 숫자를 집행하는 구조. 관리자 설정 화면과 다를 게 없다.

**"지속적으로 발전하는 시스템"이 아니었다.**

지금 버전은 그 상수들을 **진화 대상**으로 되돌렸고, 대신 사람이 정하는 것을
**"무엇을 바꿔도 되는가"라는 메타 정책**(§2.2)으로 올렸다.
