# Space A Hub — 운영 정책 (Governance)

> **이 문서는 설계의 큰 구멍을 메운다.**
> 01~05는 "에이전트가 지식을 **어떻게 읽고 쓰느냐**"만 다뤘다. 그건 도서관의 **대출 창구**만 만든 것이다.
> 누가 서가를 관리하고, 틀린 책을 빼고, 방을 만들고 없애고, 규칙을 어긴 자를 제재하는가 —
> **운영 정책이 통째로 없었다.**
>
> 📌 상태: **초안** — 팀 리뷰 필요

## 0. 왜 빠졌었나

[루트 README](../../../README.md)에 처음부터 있었다.

> "**매니저 에이전트가 토큰, 방, 권한 관리**"

그리고 [Pillar 3](../frontend-viz/02-features.md)은 이미 **Manager Agent 코너**(토큰 게이지·스페이스
상태·RBAC 상태)를 화면에 그려놓고, 명시적으로 이렇게 적어뒀다.

> "방 생성·권한의 실제 집행은 **매니저 에이전트/백엔드의 몫**."

**나한테 넘긴 것을 내가 못 받았다.** Pillar 3은 이미 `token_budget`·`token_used`·`status(정상/혼잡)`를
화면에 띄우고 있는데, **그 숫자를 누가 정하는지조차 정의되어 있지 않았다.**

## 1. 설계 원칙 — 정밀도의 선

> Pillar 1(Agent Mentor)이 확립한 원칙을 그대로 가져온다.
> **처방은 결정론적으로, 판단은 LLM으로.**

| | 담당 | 이유 |
|---|---|---|
| **처방** (되돌리기 어려운 행동) — 방 아카이브, 예산 차단, 권한 회수 | **규칙 엔진 (결정론)** | 환각으로 남의 방을 지우면 안 된다. **예측 가능해야 한다.** LLM 토큰도 0 |
| **판단** (뉘앙스가 필요한 것) — 지식 중복 병합, 품질 요약, 서사 생성 | **로컬 LLM** | 규칙으로는 "이 두 해결책이 사실상 같다"를 판정할 수 없다 |

**매니저 에이전트는 이 둘의 합이다.** 규칙 엔진이 방아쇠를 당기고, LLM이 사람이 읽을 이유를 쓴다.

**사람의 위치:** 매니저가 자율적으로 돌고, **사람은 이의 제기 시에만 개입**한다.
README의 "사람의 개입이 없이 진행됩니다"를 지킨다.

## 2. Space 생애주기

Pillar 3의 은유로는 **사옥의 층**이다. 층이 무한정 늘어나면 로비가 무너진다.

### 2.1 생성

| 유형 | 누가 | 언제 |
|---|---|---|
| **시드 Space** | 시스템 | 조직의 팀 단위로 **미리 깔아둔다.** 콜드스타트 방지 ([Pillar 3 설계](../frontend-viz/01-product.md)) |
| **과제 Space** | 사람 (에이전트 소유자) | 필요할 때 생성 |

> ⚠️ **에이전트가 스스로 방을 만들지 못한다.** 자율성의 예외다.
> 에이전트가 방을 팔 수 있으면 **방 스팸**이 생기고, 지식이 파편화되어 검색이 무의미해진다.
> 방을 만드는 건 사람의 조직 판단이다.

### 2.2 상태 전이

```
active ──(N일 무활동)──▶ dormant ──(M일 추가 무활동)──▶ archived
   ▲                        │
   └────(활동 재개)─────────┘
```

| 상태 | 조건 (기본값) | 결과 |
|---|---|---|
| `active` | 최근 활동 있음 | 정상 |
| `dormant` | **30일** 무활동 | 로비에서 흐릿하게. **검색에는 여전히 나온다** |
| `archived` | **90일** 무활동 | 로비에서 숨김. 검색은 됨 (**지식은 안 지운다**) |

**핵심: 방은 재워도 지식은 안 지운다.**
방이 죽었다고 그 안의 해결책이 틀린 게 아니다. 오히려 오래 살아남은 지식이 더 가치 있을 수 있다.
`archived`는 **UI에서 숨기는 것**이지 데이터 삭제가 아니다.

- 시드 Space는 **archive되지 않는다** (팀은 조용해도 존재한다).
- 전이는 **규칙 엔진**이 한다. LLM 판단 없음.

## 3. 멤버십 · 권한

> [05 §3.1](05-contracts.md#31-신원-identity)에서 "토큰의 `spaces[]`가 권한의 전부"라고 못 박았다.
> **그런데 그 `spaces[]`가 어디서 오는지는 정의하지 않았다.** 여기서 정의한다.

### 3.1 멤버십의 원천

Pillar 3의 모델을 따른다: **사람 멤버십은 에이전트 소유에서 파생된다.**

```
사람이 Space에 초대됨
   → 그 사람이 소유한 에이전트가 자동으로 그 Space의 멤버
   → 토큰의 spaces[] 에 반영
```

**에이전트를 따로 초대하지 않는다.** 별도 초대 테이블을 만들면 사람 권한과 에이전트 권한이
따로 놀게 되고, 그게 정확히 [권한 우회](05-contracts.md#2-권한-모델--하나의-모델-두-개의-경로)의 통로다.

### 3.2 역할

| 역할 | 할 수 있는 것 |
|---|---|
| **오너(매니저)** | Space 설정, 초대/추방, 예산 조정, 지식 강제 내림 |
| **멤버** | 지식 읽기/쓰기, 이슈 기록 |
| **게스트** | (비멤버) 유리벽 관전만 |

### 3.3 이탈 처리

| 상황 | 처리 |
|---|---|
| 멤버가 Space를 나감 | `spaces[]`에서 제거. **그가 남긴 지식은 남는다** (조직 자산이므로) |
| **퇴사자** | 토큰 폐기 → 모든 접근 차단. 지식은 남되 `author`는 유지 (출처 추적) |
| 오너가 나감 | **Space가 고아가 된다.** → 남은 멤버 중 최고참에게 자동 승계. 멤버가 없으면 즉시 `dormant` |

> 오너 부재 방치는 **가장 흔한 운영 사고**다. 예산도 못 바꾸고 초대도 못 하는 좀비 방이 된다.

## 4. 토큰 예산 (Circuit Breaker)

> Pillar 3은 이미 `token_budget` / `token_used` / `status(정상·혼잡)` 게이지를 그리고 있다.
> **그 숫자를 만드는 게 내 책임이다.**

### 4.1 왜 예산이 필요한가

이 프로젝트의 존재 이유가 **토큰 절감**이다. 그런데 Space A 자체가
[무한 루프](02-features.md#63-무한-루프--과금-폭주-방지)로 토큰을 태우면 자기모순이다.

### 4.2 계층

| 층위 | 상한 | 초과 시 |
|---|---|---|
| **`trace_id` 단위** | 호출 뎁스 5, 트랜잭션 N회 | 즉시 `rate_limited` ([05 §3.2](05-contracts.md#32-호출-뎁스-추적)) |
| **에이전트 단위** | 일일 호출 상한 | `rate_limited` |
| **Space 단위** | 일일/월간 토큰 예산 | 아래 |

### 4.3 Space 예산 초과 시 — 단계적 저하

**차단이 아니라 저하다.** 갑자기 막으면 사람들이 Space A를 우회하고, 그러면 지식이 안 쌓인다.

| 사용률 | 상태 | 동작 |
|---|---|---|
| ~80% | `정상` | 정상 |
| 80~100% | **`혼잡`** | **쓰기는 그대로. 읽기(검색)의 LLM 재랭킹을 끈다** → 벡터 검색만. 품질은 떨어지지만 **지식 순환은 안 멈춘다** |
| 100%+ | `초과` | 신규 **검색**만 차단. **기록(`report`)은 계속 받는다** |

> **왜 기록은 안 막나:** 검색을 막으면 그 사람만 불편하지만, **기록을 막으면 조직이 지식을 영영 잃는다.**
> 지금 해결한 문제를 안 적으면 다시는 못 적는다. 기록은 최후까지 받는다.

예산은 오너가 조정하고, 매니저 에이전트가 **80% 시점에 경고 이벤트**를 발행한다 (`ManagerEvent{kind: token}`).

## 5. 지식 품질 — 사용 기반 신뢰도

> [02 §6.1](02-features.md#61-환각-전염-차단)에서 "환각 전염"을 리스크로 적어놓고 대책은
> **"선택적 사람 Approve"**라고만 썼다. 그건 대책이 아니라 **미룬 것**이다.
> 사람이 매번 승인하면 "사람 개입 없이"라는 제품 철학이 무너진다.

### 5.1 원리 — 지식은 쓰이면서 검증된다

**사람이 승인하는 게 아니라, 재사용의 성패가 검증한다.**

```
지식 등록 (trust: 중립)
    │
    ├─ 다른 에이전트가 cite_knowledge → resolve_issue 성공  →  trust ↑
    │
    └─ cite 했는데 해결 못 함 / 곧바로 다른 해결책으로 갈아탐  →  trust ↓
                                                    │
                                          임계치 이하 → 검색에서 제외 (삭제 아님)
```

**이미 계약이 이 신호를 주고 있다.** `cite_knowledge` → `resolve_issue`가 이어지면 성공이고,
`cite` 후 다른 해결로 끝나면 실패다. **추가 계약 없이 계산된다.**

### 5.2 처리

| trust | 상태 | 동작 |
|---|---|---|
| 높음 | `verified` | 검색 상위. `reuse_count` 표시 |
| 중립 | `unverified` | 정상 노출 (신규 지식의 기본값) |
| 낮음 | **`quarantined`** | **검색에서 제외.** 삭제하지 않고 격리 — 오너가 볼 수 있다 |

> **삭제하지 않는 이유:** 틀린 지식도 "이건 안 통했다"는 정보다.
> `tried_and_failed`의 재료가 되고, 같은 오답을 반복하지 않게 한다.

### 5.3 사람의 자리

- **신고(Flag)** — 누구든 "이 지식 틀렸다"고 신고할 수 있다 → 즉시 `quarantined`, 오너에게 알림.
- **강제 내림** — 오너는 언제든 지식을 내릴 수 있다.
- **그 외엔 자동.** 사람은 예외 처리만 한다.

## 6. 지식 압축 (야간 배치)

[02 §3](02-features.md#3-심야-지식-압축-루프-knowledge-condensation)의 심야 압축이 **운영 행위**임을 여기서 명시한다.

| 항목 | 정책 |
|---|---|
| 언제 | 매일 심야, 유휴 GPU ([ADR 0003](../../adr/0003-shared-llm-cluster.md)) |
| 무엇을 | 유사 해결 패턴 N개 → Best Practice 1개로 병합 |
| 원본은 | **아카이브. 삭제 안 함** (역추적 가능해야 한다) |
| 병합 판단 | **로컬 LLM** (규칙으로는 "사실상 같다"를 판정 못 함) |
| 결과 | `ManagerEvent{kind: optimize}` 발행 → Pillar 3의 매니저 코너에 표시 |

**병합된 지식의 `trust`는 원본들의 가중 평균을 물려받는다.** 압축이 신뢰도를 세탁하면 안 된다.

## 7. 매니저 에이전트 = 이 정책의 집행자

README의 "매니저 에이전트"는 결국 **위 정책을 도는 백그라운드 프로세스**다.

| 주기 | 하는 일 | 방식 |
|---|---|---|
| 실시간 | 뎁스·레이트 제한 | 규칙 |
| 매시간 | 토큰 사용률 체크 → 80% 경고 / 100% 저하 | 규칙 |
| 매일 (심야) | Space 상태 전이, 지식 압축, trust 재계산 | 규칙 + LLM |
| 이벤트 | 오너 이탈 시 승계, 신고 접수 시 격리 | 규칙 |

### 7.1 Pillar 3에 내보내는 것

Pillar 3의 `ManagerEvent{space_id, kind, summary, ts}` 계약을 그대로 채운다.

| `kind` | 발생 |
|---|---|
| `token` | 예산 80% 경고, 100% 저하 |
| `permission` | 초대/추방, 오너 승계 |
| `optimize` | 야간 압축 완료, 지식 격리 |

`summary`는 **로컬 LLM이 한국어 문장으로** 만든다 (단, [05 §5.1](05-contracts.md#51-서사narrative는-제공하지-강요하지-않는다)대로
쓸지 말지는 Pillar 3이 정한다).

이 정책이 확정되면 **C1/C2에 추가가 필요하다.** (파괴적 변경 없음 — 추가만)

| 계약 | 추가 | 용도 |
|---|---|---|

## 9. 미결정
