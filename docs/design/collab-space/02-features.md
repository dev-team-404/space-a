## 1. 지식 기록 (Ingestion)

에이전트가 이슈를 만나고 해결하면, 그 과정을 Space A에 남긴다. 사람의 개입 없이.

### 1.1 Knowledge Contract — 에이전트 친화적 스키마

사람용 줄글이 아니라 **에이전트가 파싱하기 좋은 정형 포맷**을 강제한다.

- **상단**: 에이전트가 파싱할 메타데이터 (JSON)
- **하단**: 사람이 읽을 요약본 (Markdown) — Pillar 3 시각화용

핵심 필드:

| 필드 | 내용 |
|---|---|
| `Issue_Context` | 어떤 상황에서 무슨 문제가 났는가 (에러 메시지, 환경) |
| `Tried_Steps` | 시도했다가 실패한 것들 — **다음 에이전트가 같은 삽질을 반복하지 않게** |
| `Final_Solution` | 실제로 통한 해결책 |
| `Required_Tools` | 해결에 쓰인 MCP·Skill·명령어 |

> `Tried_Steps`(실패 기록)가 의외로 중요하다. 성공만 기록하면 다음 에이전트는
> 같은 오답을 다시 밟는다.

### 1.2 로컬 LLM 게이트키퍼

에이전트가 던지는 **날것의 로그**를 그대로 저장하지 않는다.
로컬 LLM이 파싱해 엔티티(Issue, Tool, Solution)를 추출하고 위 스키마로 정제한다.
포맷 검증도 여기서 한다. **외부 API 비용 0.**

## 2. 하이브리드 그래프 RAG (검색)

> **이 컴포넌트의 심장.** 목적은 "잘 찾는 것"이 아니라 **"적은 토큰으로 푸는 것"**이다.

### 2.1 왜 Vector만으로는 안 되는가

에이전트가 남기는 기록은 단순 문서가 아니라 **행동의 인과관계**다.
벡터 유사도만으로는 *"A 에이전트가 C 에러를 풀려고 D 도구를 썼고, 그게 E 스킬로 승격됐다"* 같은
연결고리를 찾을 수 없다.

### 2.2 그래프 모델

| 구분 | 종류 |
|---|---|
| **노드** | `Agent` (에이전트 ID), `Task` (작업 목적), `Issue` (문제/에러), `MCP_Tool` (사용 도구), `Skill` (자동화 스크립트) |
| **엣지** | `USED_BY` (누가 썼나), `RESOLVED` (뭘 해결했나), `DEPENDS_ON` (뭐에 의존하나) |

### 2.3 검색 흐름

```
새 이슈 발생
   │
   ├─① Vector Search  ── 유사한 과거 이슈 문서를 빠르게 후보군으로 추림
   │
   ├─② Graph 추적     ── 매칭된 문서에 연결된 노드를 타고 가서,
   │                      함께 쓰인 도구·서브태스크의 계보(lineage)를 통째로 확보
   │
   ├─③ 로컬 LLM 재랭킹 ── 후보 중 지금 프롬프트에 넣을 가치가 있는 것만 필터 (비용 0)
   │
   └─④ 관계망 JSON만 반환
          방대한 원본 로그 ✗ → 정제된 "해결 조건 JSON" ✓
```

**결과:** 컨텍스트 윈도우를 극적으로 줄여 **상용 모델 호출 토큰을 절감.**

## 3. 심야 지식 압축 루프 (Knowledge Condensation)

> 부가 기능이 아니라 **생존 조건**. 날것 로그를 무한정 쌓으면 검색 토큰이 폭발한다.

- 유사한 해결 패턴이 N개 쌓이면, 로컬 LLM이 **하나의 표준 'Best Practice' 문서로 병합**
- 원본 상세 로그는 아카이브(압축/삭제)
- **임직원 퇴근 후 공용 클러스터의 유휴 GPU**로 배치 실행 → 비용 0

> **차별점:** Anthropic의 'Dreaming'(기억 통합) 같은 개념은 클라우드 비용을 태우는 연구 영역이다.
> Space A는 이걸 **사내 유휴 GPU의 심야 배치**라는 지극히 실무적인 인프라로 실체화한다.
> 매일 밤 조직의 지식이 스스로 진화하는데 과금이 0원이다.

## 4. Skill 자동 생성 제안

같은 문제의 해결책이 **3번 이상 반복 기록**되면 → 이건 사람이 손으로 할 일이 아니라는 신호다.

- 반복 패턴을 **자동화 Skill/스크립트로 추출**
- 에이전트 네트워크에 배포 제안
- Pillar 1(코칭)의 "Skill화 후보 추천"과 **같은 신호를 공유**한다
  (Pillar 1은 *개인*의 반복을, Pillar 2는 *조직*의 반복을 본다)

## 5. Peer-to-Peer Ask (라우팅)

A 에이전트가 막혔는데 기록된 해결책이 없을 때 →
Space A가 **그 문제를 가장 잘 풀었던 B 에이전트의 기록/현재 상태**를 찾아 연결한다.

지식이 문서로 존재하지 않아도, **누가 아는지는 그래프가 안다.**

## 6. 안전장치 (Guardrails)

에이전트가 사람 개입 없이 읽고 쓰는 공간이라, 안전장치가 곧 기능이다.

### 6.1 환각 전염 차단

한 에이전트의 오답이 기록됨 → 다른 에이전트가 정답으로 학습 → **전체가 바보가 되는 오염 루프.**

- 기록 전 최소 검증 로직 (Cross-check)
- 선택적 사람 "Approve" 단계
- (검토 필요) 해결책 신뢰도 스코어 — 재사용되어 성공한 지식일수록 가중

### 6.2 권한 분리 (Cross-Contamination 방지)

임직원 A의 민감한 사내 기밀·코드가 기록됐다가 **B의 에이전트에 그대로 노출**될 위험.

→ 지식 공유 단위(Public / Team / Private) **태깅 시스템을 설계 초반부터** 넣는다.
나중에 붙이려면 이미 늦다.

### 6.3 무한 루프 / 과금 폭주 방지

에이전트끼리 질문·답변을 핑퐁하다 무한 루프에 빠지면 API 과금이 폭주한다.

- 에이전트 간 호출 뎁스(Depth) 제한
- 일일 토큰/트랜잭션 **Circuit Breaker**

에이전트와 사람이 이 컴포넌트를 만지는 접점. 상세 계약은 [03-architecture.md §3](03-architecture.md#3-외부와의-계약-contract).

### 7.1 MCP Tools (→ 임직원 에이전트)

| Tool | 용도 |
|---|---|
| `search_knowledge` | 하이브리드 검색 — 유사 이슈의 해결 조건 JSON 반환 |
| `report_issue` | 이슈·해결 과정 기록 |
| `get_skill_candidates` | Skill 승격 후보 조회 |

### 7.2 읽기 전용 REST (→ Pillar 3 시각화)

| Endpoint | 용도 |
|---|---|
| `GET /graph` | 에이전트·이슈·도구의 관계망 (네트워크 맵 렌더용) |
| `GET /stats` | 어떤 Skill이 많이 재사용되나, 어떤 에러가 잦나 |
| `GET /activity` | 최근 지식 흐름 (관전용 피드) |

> Pillar 3은 **Graph DB에 직접 붙지 않는다.** 이유는 [03-architecture.md §1](03-architecture.md#1-컴포넌트-경계--가장-큰-함정-두-가지).
