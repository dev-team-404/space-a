# Space A Hub — 검색 설계

> 담당: 허준녕. C1 `search_knowledge`(MCP Tool)의 내부 설계.
> 목적은 "잘 찾는 것"이 아니라 **"적은 토큰으로 푸는 것"** — 호출자는 1회 호출로 끝나고,
> 검색 내부 연산은 전부 사내 로컬 LLM(비용 0)이 진다.

## 1. 문제 정의

| | 내용 |
|---|---|
| 입력 | 에이전트의 이슈 질의 (에러 메시지, 상황 설명) |
| 출력 | 정제된 "해결 조건 JSON" — `Final_Solution` + `Required_Tools` 중심 |
| 제약 | 호출자(상용 모델) 왕복 1회 · 검색 연산은 사내 GPU · 권한 필터(`org`/`space`) 준수 |

## 2. 인덱싱

검색 대상은 Knowledge Contract 정형 레코드다. 기록 시점에 동기로 색인한다.

| 인덱스 | 대상 | 비고 |
|---|---|---|
| BM25 (키워드) | 전 필드, `Issue_Context` 가중 | 에러 코드·도구명·라이브러리명의 정확 매칭이 주력 |
| 벡터 | `Issue_Context` + `Final_Solution` 요약 | 표현이 다른 유사 사례 보완. 임베딩은 사내 GPU (BGE-m3 등) |

## 3. 질의 파이프라인

1. BM25와 벡터 각각 top-k 검색
2. **RRF(Reciprocal Rank Fusion)로 융합**
3. 정렬 가중: **trust 점수**(cite→resolve 성패 집계) + 최신성
4. 권한 필터: 토큰에서 유도된 `spaces[]` + `visibility`

## 4. 에이전틱 루프

융합 검색 위에서 **사내 로컬 LLM이 검색을 다회 시도**한다.

```
search_knowledge(query)
   │
   ▼
[로컬 LLM 검색 에이전트]        ← 사내 클러스터, 비용 0
   │  루프 (최대 3회):
   │   ① 질의 생성/재구성 ── 에러 코드 추출, 동의어 확장, 필터 조정
   │   ② 융합 검색 (§3)
   │   ③ 판정 ── 충분하면 종료, 부족하면 다른 각도로 ①
   ▼
해결 조건 JSON 반환
```

| 항목 | 결정 |
|---|---|
| 재시도 상한 | 3회. 초과·실패 시 1차 융합 검색 결과를 그대로 반환 (폴백) |
| 종료 판정 | 로컬 LLM이 "질의의 문제를 해결 조건이 커버하는가"로 판단 |
| 로컬 모델 | 사내에 이미 도입된 모델 사용 (파싱용 소형 모델 이상의 판단력 전제) |
| 지연시간 | 상한 3회로 고정. 목표치는 구현 후 실측으로 설정 |

## 5. 응답 매핑

C1 `search_knowledge` 응답 스키마에 그대로 맞춘다.

- 본문: 해결 조건 JSON (원본 로그 미포함)
- `searched: {vector_hits, graph_expanded: 0, returned}` — 기존 카운터 유지
- `rounds` 선택 필드 추가 (계약의 "추가만 허용" 정책 내)

## 6. 평가

구현 후 골든셋 질의(실제 이슈 N건)로 측정한다: 적중률, 평균 라운드 수, 응답 토큰량.
목표치는 실측 기반으로 정한다.

## 7. 관계 데이터 처리

그래프 스토어는 두지 않는다. 관계가 필요한 기능은 생애주기 이벤트 레코드의
일반 질의로 처리한다: Skill 승격 감지 = 반복 집계, trust = cite→resolve 성패 집계,
P2P Ask = 레코드 조회.
