# Space A Hub — 검색 설계 제안: 그래프 RAG 대신 에이전틱 하이브리드 검색

> 📌 **상태: 제안 (팀 리뷰 전)** — 제안자: 허준녕
>
> 이 문서는 [02-features.md §2 (하이브리드 그래프 RAG)](02-features.md#2-하이브리드-그래프-rag-검색)의
> **대체 제안**이다. 규칙대로 문서 기반으로 반박한다.
> 합의되면 02 문서의 §2를 이 내용으로 갱신하고, 결정은 ADR로 남긴다.

## 1. 한 줄 요약

**검색 핫패스에서 그래프 순회와 LLM 리랭킹을 뺀다.**
대신 **BM25 + 벡터 융합 검색**을 프리미티브로 깔고, 그 위에서 **사내 로컬 LLM이
다회 시도(질의 재구성 → 재검색 → 검증)하는 에이전틱 루프**로 답을 좁힌다.

원안의 원칙은 그대로다 — **비용 0 (전부 로컬 LLM), 목적은 토큰 절감.**
바뀌는 것은 그 원칙을 달성하는 **수단**뿐이다.

## 2. 무엇을 바꾸자는 것인가

| | 원안 (02 §2) | 제안 |
|---|---|---|
| 검색 흐름 | ① Vector → ② Graph 추적 → ③ 로컬 LLM 리랭킹 → ④ JSON 반환 | ① BM25+Vector 융합(RRF) → ② 로컬 LLM이 결과 판정, 부족하면 **질의를 바꿔 재시도** (상한 N회) → ③ JSON 반환 |
| 그래프의 역할 | **검색의 핵심 경로** | 검색 경로에서 제거. **저장은 유지** — 시각화(C2 `/graph`)·Skill 승격·trust·P2P Ask 용 (§6) |
| 리랭킹 | 로컬 LLM이 후보 재정렬 | 삭제. 대신 **trust 점수 + 필드 가중**으로 정렬 (LLM은 정렬이 아니라 **판정·재질의**에 씀) |
| 지능이 놓이는 곳 | 인제스천 시점 (엔티티 추출 → 그래프 구축) | **질의 시점** (로컬 LLM의 다회 탐색) |

## 3. 왜 그래프 RAG를 빼는가

### 3.1 관계가 이미 문서 안에 있다

원안이 그래프의 근거로 든 것: *"A 에이전트가 C 에러를 풀려고 D 도구를 썼다는
연결고리를 벡터 유사도로는 찾을 수 없다."*

그런데 v2 스키마에서 이 연결고리는 그래프를 타야 나오는 게 아니라
**검색된 문서의 필드다.** `Required_Tools`, `Final_Solution`, `Tried_Steps` —
유사 이슈 하나를 찾으면 해결에 쓰인 도구와 과정이 통째로 딸려 온다.

그래프 순회가 값어치를 하는 건 **문서를 넘나드는 멀티홉 질의**뿐인데
("이 인증서 변경이 또 뭘 깨뜨렸나"), 그게 `search_knowledge`의 주 시나리오라는
근거는 원안에 없다. 데모 시나리오(의존성 에러 → 유사 사례 검색)조차
싱글홉으로 풀린다.

### 3.2 인제스천이 검색의 인질이 된다 — GraphRAG의 고질병

그래프 검색의 품질은 **기록 시점의 엔티티 추출 품질**에 묶인다.
로컬 LLM이 엣지를 잘못 뽑으면 그 지식은 그래프 상에서 **영구히 잘못된 자리**에
있고, 질의를 아무리 잘 해도 회복이 안 된다.

다회 시도 구조는 반대다 — 인덱스가 부실해도 **질의를 바꿔서 회복한다.**
지능을 인제스천(1회, 되돌리기 어려움)이 아니라 질의(매번, 회복 가능)에 두는 쪽이
실패에 강하다.

### 3.3 이 코퍼스는 BM25에 특히 유리하다

에이전트 기록의 검색 키는 **에러 메시지, 도구명, 라이브러리명, 환경변수명** —
희귀 토큰의 정확 매칭이다. 이건 벡터가 약하고 BM25가 강한 지점이다.
정형 스키마 덕에 필드 가중(`Issue_Context` 부스팅 등)도 공짜로 된다.
벡터는 표현이 다른 유사 사례("인증 실패" ↔ "certificate error")를 보완한다.
**둘의 융합(RRF)이 이 도메인의 정석이고, 그래프 없이도 후보군 품질은 충분하다.**

### 3.4 호출자가 이미 에이전트다

그래프 RAG류 "질의 1회 → 최대한 풍부한 컨텍스트" 설계는 호출자가 재시도를
못 하던 수동적 RAG 시대의 것이다. 이 시스템의 소비자는 MCP를 부르는
에이전트이고, 서버 안에도 로컬 LLM이 있다. **다회 탐색이 공짜인 환경에서
비싼 원샷 파이프라인을 유지할 이유가 없다.** 최근 실무 흐름
(에이전틱 검색이 무거운 인덱싱 파이프라인을 대체)도 같은 방향이다.

### 3.5 규모

사내 에이전트 기록은 수백~수천 건 규모다(심야 압축이 상한을 눌러준다).
이 규모에서 7~14B 리랭킹은 지연만 더하고, 후보 분간은
**trust 점수(이미 설계에 있는 cite→resolve 성패 기반) + 필드 가중 정렬**이
더 싸고 예측 가능하다.

## 4. 제안 파이프라인

```
search_knowledge(query)
   │
   ▼
[로컬 LLM 검색 에이전트]  ← 사내 클러스터, 비용 0
   │
   │  루프 (최대 N회, 기본 3):
   │   ① 질의 생성/재구성 ── 에러 코드 추출, 동의어 확장, 필터 조정
   │   ② BM25 + Vector 융합(RRF) ── 밀리초 단위, 필드 가중 + trust 가중
   │   ③ 판정 ── "이 결과로 충분한가?"
   │        충분 → 종료 / 부족 → ①로 (다른 각도의 질의)
   │
   ▼
정제된 "해결 조건 JSON" 반환 (Final_Solution + Required_Tools 중심)
```

- **호출자(상용 모델)는 1회 호출로 끝.** 다회 시도 비용은 전부 사내 GPU가 진다.
- 루프 상한·종료 조건은 새 개념이 아니라 기존 안전장치(depth 상한, Circuit Breaker)와
  같은 결이다 — 같은 설정 체계에 편입한다.
- 응답의 `searched` 카운터는 그대로 채운다:
  `{vector_hits, graph_expanded: 0, returned}` + **`rounds` 필드 추가** (추가만 허용 정책에 부합).

### 전제 — 로컬 모델 성능

원안은 로컬 LLM을 Qwen 7B급 "파싱·리랭킹" 용도로 가정했다.
이 제안은 그보다 나은 판단력을 요구하는데, **사내에 이미 충분한 성능의 로컬 모델이
도입되어 있다**는 인프라 팩트가 전제다. → 리뷰 시 확인 항목 (§8)

## 5. 원안의 원칙과의 정합성

01-product §6의 설계 원칙에 하나씩 대응한다. **위반이 아니라 더 나은 이행이다.**

| 원칙 | 이 제안에서 |
|---|---|
| §6.2 검색의 목적은 **토큰 절감** | 호출자 왕복이 1회로 고정, 응답도 압축 JSON. 그래프 확장으로 부풀린 계보 JSON보다 호출자 토큰이 **적다** |
| §6.3 백오피스는 전부 **로컬 LLM, 비용 0** | 다회 탐색이 전부 사내 GPU. 상용 API 비용 0 유지 |
| §6.4 압축이 기능이다 | 그대로 유지. 압축은 오히려 코퍼스를 작게 유지해 이 제안의 §3.5 근거를 강화 |
| §6.5 오염 차단 | trust 가중 정렬이 검색 순위에 직접 반영 — 원안보다 trust의 쓰임이 **더 깊어짐** |
| §6.6 소유 경계 | 변화 없음. Graph DB 운영 부담이 줄어 오히려 가벼워짐 |

## 6. 그래프는 어디에 남는가

**"관계를 저장하는 것"과 "매 검색마다 그래프를 순회하는 것"을 분리한다.**
빠지는 건 후자뿐이다.

| 용도 | 유지 여부 | 비고 |
|---|---|---|
| C2 `GET /graph` (시각화 관계망) | ✅ 유지 | 엣지는 생애주기 호출(open/cite/resolve)이 **공짜로** 만든다. 엔티티 추출 불필요 |
| Skill 승격 감지 (3회 반복) | ✅ 유지 | 배치 경로. 검색 핫패스 아님 |
| trust 계산·전파 | ✅ 유지 | cite→resolve 성패 집계 |
| P2P Ask ("누가 아는가") | ✅ 유지 | 배치/온디맨드 그래프 질의 |
| **검색 핫패스의 그래프 확장** | ❌ 제거 | 이 문서의 제안 |

따라서 Graph DB 선택지도 가벼워진다 — 검색 지연 요구가 사라지므로
**NetworkX(경량)로 충분**할 가능성이 높다. Neo4j 도입 근거가 약해진다.

| C1 생애주기 3단계 | 변경 없음 |

## 8. 데모 시나리오 갱신

원안 데모의 3번(그래프 추적)이 이 제안으로 대체된다. 대체 비트가 더 선명하다:

| # | 장면 | 포인트 |
|---|---|---|
| 3′ | 로컬 LLM이 1차 검색 실패 → **에러 코드를 추출해 질의를 재구성** → 2차에서 적중하는 과정을 라이브로 노출 | "스스로 찾아내는" 그림. `rounds: 2` 카운터 표시 |
| 4′ | 호출자 화면에는 **상용 모델 토큰이 1회 호출분뿐**임을 나란히 표시 | 토큰 절감이 눈에 보임 — 원안 4번과 동일한 클라이맥스 |

## 9. 트레이드오프와 열린 질문

| # | 항목 | 내용 |
|---|---|---|
| 1 | **지연시간** | 다회 로컬 추론이 원샷보다 느릴 수 있다. 리랭킹 제거로 일부 상쇄, 라운드 상한(기본 3)으로 상한 고정. 목표 지연(예: p95 몇 초?)은 리뷰에서 합의 |
| 2 | **로컬 모델 성능 전제** | §4의 전제 확인 — 현재 도입된 모델·컨텍스트 길이·동시 처리량. 인프라 담당과 확인 필요 |
| 3 | **루프 통제** | 종료 조건("충분하다" 판정 기준)과 실패 시 폴백(융합 검색 1회 결과 그대로 반환) 명세 필요 |
| 4 | **멀티홉 질의 비중** | §3.1의 반론 여지. 실사용에서 멀티홉 요구가 유의미하게 나오면, 그래프 확장을 **폴백 2차 경로**로 되살리는 건 이 구조에서 추가만으로 가능 — 문이 닫히지 않는다 |
