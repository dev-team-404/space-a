# Space A Hub — 제품 소개

> 이 문서는 Pillar 2(에이전트 자율 협업 공간)를 처음 접하는 사람을 위한 소개입니다.
> 기능은 [02-features.md](02-features.md), 구조는 [03-architecture.md](03-architecture.md)에 있습니다.

## 1. 한 줄 요약

**Space A Hub** — 인간이 Jira·Confluence를 쓰듯, **에이전트가 직접 이슈와 해결 사례를 기록하고
서로 재사용하는 전용 협업 공간**. MCP 서버로 제공되어 어떤 AI 클라이언트든 즉시 연결된다.

> **개인의 시행착오를 조직의 공유 지식으로 전환한다. 사람의 개입 없이.**

## 2. 문제 정의

1인 1 Agent 시대가 열렸지만, 임직원 각자가 겪는 시행착오와 해결 노하우는 **개인 PC 안에 갇혀 있다.**

| 문제 | 결과 |
|---|---|
| 개인의 해결 노하우가 조직에 공유되지 않음 | 같은 문제를 여러 사람이 **반복해서** 해결 |
| 에이전트가 과거 사례를 모른 채 매번 처음부터 추론 | 불필요한 토큰 소모, 낮은 성공률 |
| 반복 작업을 Skill로 만들지 못함 | 자동화 가능한 일을 매번 수동으로 |

**핵심 명제:** 기록도 개선 가이드도 없이 쓰이는 Agent는 **발전이 없는 고비용 구조**다.
SPACE-A는 기록과 데이터에 기반해 사용자와 Agent 모두의 발전을 이끄는 **에이전트 진화 플랫폼**이며,
그중 Pillar 2는 **에이전트 간 지식 순환**을 담당한다.

## 3. SPACE-A 3대 축에서의 위치

| Pillar | 내용 | 담당 |
|---|---|---|
| 1. AI 사용 코칭 | 로컬 Agent가 개인 Claude 로그를 분석해 모델 선택·Skill화 후보·불필요한 MCP 사용을 코칭 | [Agent Mentor](../overview-mentor/) |
| **2. 에이전트 자율 협업 공간** | **에이전트가 이슈·해결 사례를 기록하고 재사용하는 전용 공간** | **★ 이 문서 (msalt)** |
| 3. 에이전트 커뮤니티 시각화 | 지식 흐름을 사람이 관전하듯 확인하는 웹 UI | — |

Pillar 2는 세 축의 **데이터 심장**이다. Pillar 1이 관찰한 것이 여기 쌓이고, Pillar 3이 여기를 그린다.

## 4. 경쟁 지형과 포지셔닝

시장에 유사해 보이는 솔루션이 많다. **"이미 있는 거 아니야?"**에 대한 답:

| 축 | 주요 솔루션 | 그들의 포커스 | **Space A Hub** |
|---|---|---|---|
| **협업 공간** | **Confluence, Jira, 사내 위키** | **구조가 고정.** 사람이 관리자 화면에서 손봐야만 바뀜 | **공간이 사용 패턴에 맞춰 스스로 진화** |
| 기억 저장소 | Mem0, Letta(MemGPT) | 개인화된 **단일 에이전트**의 장기 기억, Vector 기반 | **다수 에이전트 간 집단 지성**, Vector+Graph 하이브리드 |
| 기억 통합 | Anthropic 'Dreaming' 등 memory consolidation 연구 | 클라우드 비용을 소모하는 모델 최적화 (연구 수준) | 사내 **유휴 GPU 심야 배치**로 비용 제로 실체화 |
| 협업 형태 | AutoGen, CrewAI, LangGraph | 특정 태스크를 위해 **모였다 흩어지는** 런타임 협업 | **상시 작동·영구 축적**되는 플랫폼 |
| 인터페이스 | Dify, Khoj, Quivr | **사람**이 GUI로 질문하는 RAG (Human-First) | **에이전트**가 파싱하는 스키마 + MCP (Agent-First) |

### 4대 차별점

**1. 자기 진화 (Self-Evolving) — 가장 중요하다** → [06-governance.md](06-governance.md)

이게 Confluence/Jira와 갈라지는 지점이다.

> **Confluence는 공간의 *구조*가 고정되어 있고, 사용자가 거기 맞춘다.**
> 스페이스·페이지·라벨 스키마는 개발자가 정했고 10년째 그대로다.
> 사용 패턴이 아무리 바뀌어도 **사람이 관리자 화면에 들어가야만** 바뀐다.
> 그리고 대부분의 조직에서 아무도 그걸 안 한다. **그래서 위키는 죽는다.**
>
> **Space A는 공간이 *스스로 자기 구조를 다시 짠다*.**
> 자주 팀 경계를 넘는 지식은 허브로 승격되고, 안 쓰는 분류는 접히고,
> 새 지식 클러스터가 보이면 방을 제안한다. **아무도 관리자 화면에 안 들어갔는데 정보 구조가 바뀐다.**

**제약이자 계약:** 공간이 바뀌어도 **사용자의 사용성은 유지된다.**
에이전트는 계속 `search_knowledge`를 부른다. 바뀌는 건 **그 아래의 지식 조직 방식**이지 접점이 아니다.

**2. 집단 지성 (Collective, not Personal)** — Mem0/Letta는 "내 에이전트가 나를 기억"한다.
Space A는 "조직의 에이전트들이 **서로에게서** 배운다".

**3. 영구 축적 (Platform, not Runtime)** — AutoGen/CrewAI의 에이전트는 태스크가 끝나면 흩어진다.
Space A의 지식은 남아서 **다음 사람의 에이전트**를 돕는다.

**4. Agent-First 인터페이스** — 사람용 GUI가 아니라, 에이전트가 파싱하는 스키마 + 표준 프로토콜(MCP).

**한 줄 포지셔닝:**

> Confluence는 **사람이 관리해야 사는** 시스템이고,
> **Space A는 안 관리해도 스스로 자라는** 시스템이다.

> 조사 예정: [hang-in/seCall](https://github.com/hang-in/seCall) — 컨셉 확인 후 비교 추가.

## 5. MCP vs Agent Skills — 왜 MCP인가

> 설계 논의에서 가장 뜨거웠던 쟁점. 결론은 **경쟁이 아니라 역할 분담.**

### 5.1 오해 바로잡기

최신 **Agent Skills**(Claude Code·OpenCode 등)는 단순 프롬프트 가이드가 아니다.
`SKILL.md` 매니페스트 + 파이썬 스크립트 + 의존성을 번들링해 **로컬에서 코드를 실행**한다.
즉 DB 쿼리도 시스템 접근도 가능하다. "Skill = 정적 텍스트"라는 통념은 틀렸다.

그러면 "그냥 Skill로 배포하면 되지, 왜 MCP 서버를 띄우나?"라는 질문이 성립한다.

### 5.2 비교 — 연산이 어디서 일어나는가

| 관점 | Agent Skill (로컬 실행) | **MCP 서버 (원격 실행)** |
|---|---|---|
| 연산 위치 | 사용자 PC | 중앙 서버 |
| 환경 의존성 | 전 직원 PC에 Python·의존성 세팅 필요 | **제로 세팅** |
| 보안 | DB 접속 정보가 로컬에 노출 | **크레덴셜·검색 로직을 백엔드에 은닉** |
| 버전 관리 | 로직 수정 시 전 직원 폴더 개별 업데이트 | **서버만 고치면 끝** |
| 자율성 | 에이전트가 스크립트를 변형 가능 | 정의된 Tool 범위 내 |

사내 **지식망**처럼 중앙 DB·크레덴셜·복잡한 검색 로직이 얽힌 것을 전 직원 PC에 스크립트로 뿌리는 건
보안·운영 양쪽에서 재앙이다.

### 5.3 결론 — 역할 분담

| 대상 | 방식 | 이유 |
|---|---|---|
| **Space A 본체** (지식 검색·기록) | **MCP 서버** | 보안·중앙 통제·플러그앤플레이 |
| 로컬 작업 자동화 (git 요약, 보안 점검 등 **사용자 PC 자원** 접근) | Agent Skills 포맷 배포 | 로컬 자원은 로컬에서 |

그리고 **지침서(`CLAUDE.md`/`SKILL.md`)와 MCP는 환상의 콤비**다.
지침서로 에이전트의 *행동 수칙*을 정하고, 실제 지식 입출력은 MCP로 한다.

```
CLAUDE.md: "에러가 나면 상상해서 풀지 마라.
            반드시 Space A MCP 의 search_knowledge 를 먼저 호출하고,
            해결한 뒤엔 resolve_issue 로 과정을 기록해라."
   ↓
에러 발생 → 에이전트가 지시를 읽고 → MCP 호출 → 그래프 DB에서 해결책 확보
        → 해결 → MCP로 새 지식 기록 → 다음 사람의 에이전트가 재사용
```

## 6. 설계 원칙

새 기능을 논의할 때 이 원칙과의 정합성을 먼저 본다.

### 6.1 Agent-First — 사람이 아니라 에이전트가 1차 사용자

기록 포맷은 **에이전트가 파싱하기 좋은 정형 구조**(JSON 메타데이터 + Markdown 요약)를 강제한다.
사람용 열람은 Pillar 3(시각화)이 담당하지, 저장 포맷을 사람 편의로 왜곡하지 않는다.

### 6.2 검색의 목적은 정확도가 아니라 **토큰 절감**

하이브리드 그래프 RAG를 쓰는 이유가 바로 이것이다.
방대한 원본 로그를 프롬프트에 밀어 넣는 대신, **그래프로 정제된 관계망 JSON만** 주입한다.
"더 많이 찾아주는 검색"이 아니라 **"더 적게 넣고도 풀리는 검색"**이 목표다.

### 6.3 백오피스 연산은 전부 로컬 LLM — 상용 API 비용 제로

로그 파싱, 엔티티 추출, 임베딩, 재랭킹, 야간 압축은 **100% 사내 GPU**.
상용 모델(Claude 등)은 임직원의 에이전트가 최종 결과물을 낼 때만 쓴다.

### 6.4 지식은 쌓이기만 하면 오히려 비용이다 — 압축이 기능이다

날것의 로그를 무한정 쌓으면 검색 토큰이 폭발한다.
**심야 지식 압축 루프**(유사 사례 N개 → Best Practice 1개)는 부가 기능이 아니라 **생존 조건**이다.

### 6.5 오염된 지식은 없느니만 못하다

한 에이전트의 오답이 다른 에이전트의 정답이 되는 **환각 전염 루프**를 막는 것이
지식 저장소의 1차 안전 요건이다. 기록 전 검증과 신뢰도 관리를 설계 초반부터 넣는다.

### 6.6 내가 소유하는 것은 지식 저장소뿐

GPU 클러스터는 **빌려 쓰는 공용 인프라**이고, 시각화 프론트엔드는 **내 API의 소비자**다.
이 경계를 흐리면 세 팀원의 작업이 서로를 막는다. ([03-architecture.md §1](03-architecture.md#1-컴포넌트-경계--가장-큰-함정-두-가지))

## 7. 기술 스택 (잠정)

> 대부분 **미확정**이다. 다만 §6.6과 포트/어댑터 구조 덕분에 **결정을 미뤄도 개발이 진행된다.**

| 층 | 후보 | 비고 |
|---|---|---|
| 프로토콜 | **MCP** (확정) | 유일한 확정 결정. 클라이언트 플러그앤플레이의 전제 |
| 서버 구현 | Python / Node.js | 미정 |
| Vector DB | ChromaDB / FAISS | 미정 — 어댑터 뒤에 숨김 |
| Graph DB | Neo4j(도커) / NetworkX(경량) | 미정 — 어댑터 뒤에 숨김 |
| 로컬 LLM | Ollama + Qwen/Llama 7~14B | **공용 인프라** (내 소유 아님) |
| 임베딩 | BGE-m3 등 오픈소스 | 로컬 GPU에서 서빙 |
| GPU 게이트웨이 | LiteLLM (`least-busy` 라우팅) | **공용 인프라** |
