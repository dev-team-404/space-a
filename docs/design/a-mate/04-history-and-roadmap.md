# Agent Mentor — 개발 연혁과 로드맵

> 프로젝트가 어떤 순서로, 어떤 의사결정을 거치며 자랐는지의 기록.
> 다른 구현과 아이디어를 합칠 때 "왜 이렇게 되어 있나"의 맥락을 제공한다.

## 1. 개발 방식

이 프로젝트는 **브레인스토밍 → 설계 스펙 → 구현 플랜 → 구현(PR) → 사용자 수동 E2E → 교훈을 다음 스펙에 반영**
사이클로 개발됐다. 산출물 위치:

- [`brainstorming/`](brainstorming/) — 킥오프 시드 문서 (열린 질문 목록)
- [`specs/`](specs/) — 브레인스토밍 합의 결과인 설계 스펙 (확정 결정 로그 포함)
- [`plans/`](plans/) — 스펙을 태스크로 분해한 구현 플랜

특징적인 점: **실사용 E2E가 설계를 두 번 뒤집었다** (§3 교훈 참고). 스펙은 "합의 시점의 기록"이고,
이후 결정이 바뀐 경우 후속 스펙이 이전 스펙을 명시적으로 참조하며 수정한다.

## 3. E2E에서 얻은 교훈 (설계를 뒤집은 것들)

다른 구현과 아이디어를 합칠 때 같은 함정을 피할 수 있도록 기록한다.

### 3.1 ccusage 위임 → 직접 파싱 (킥오프 → 데이터 파운데이션)

킥오프 시점엔 "집계는 ccusage에 위임"이 확정이었으나, 코칭 신호(턴별 cache_read, tool_use 시퀀스,
메시지별 model)는 **턴 단위 이벤트**가 필요하고 집계기인 ccusage는 그걸 못 준다.
→ 원본 JSONL을 직접 파싱하되, 스키마 취약성은 관대한 파싱 + 버전 인지형 어댑터로 방어.

### 3.2 세션 단위 코칭 카드는 스팸이 된다 (v1 → v2)

R7("가벼운 작업에 Opus는 과해요")이 실전에서 **같은 지적 81회 노출** — 자동화 도구(cowork probe)가
만든 동형 초단기 세션마다 카드가 1장씩 나왔다. 게다가 처방(`/model haiku`)은 사용자의 실제 레버가
아니었다(세션은 도구가 생성한 것).
→ **v2 원칙**: 조치 지점이 ① 설정 파일 한 곳 또는 ② 다음 세션의 선택인 것만 코칭. 프로젝트 집계 카드가 기본.

### 3.3 "사용자 잘못"으로 읽히는 규칙은 신뢰를 깎는다 (v2 → v2.1)

R5(같은 파일 반복 Read)의 주체는 대부분 에이전트 자신(컨텍스트 압축 후 재읽기 등)인데,
카드가 "사용자 잘못"처럼 읽혔다.
→ 세션 카드 폐기, **관찰 지표로 재프레이밍**: "에이전트가 어떤 환경에서 반복 확인을 하게 되는지,
다음 세션에 어떻게 도우면(예: CLAUDE.md에 핵심 사실 기재) 줄어드는지"를 보여준다.

### 3.4 도트 픽셀 ≠ 싸이월드 미니미 (마스코트 렌더 3회 반복)

로봇 렌더가 16×16 도트 → 32×32 도트 → **128px 프로시저럴 드로잉**으로 진화.
E2E 피드백 "여전히 투박" — 미니미는 뚜뚜한 도트가 아니라 **매끈한 소형 스프라이트**(셀 셰이딩 + 아웃라인)라는 결론.
레트로 픽셀 폰트·도트 프레임 전면 사용도 같은 이유로 **파스텔 모던**(둥근 모서리·부드러운 그림자)으로 선회했다.
단, 미니홈피 **레이아웃 문법**(타이틀바 카운터, 좌측 컬럼, 책갈피 탭)은 유지.

### 3.5 LLM 프로즈의 "AI티"는 사후 수정이 아니라 생성 시점에 예방

im-not-ai(탐지→수술적 수정 파이프라인)를 참조하되, 사후 패스는 토큰·지연 2배에 팩트 드리프트
위험이 있어 기각. 회피목록을 **문체 가이드로 번역해 시스템 프롬프트에 흡수**(`voice_guidance()`),
팩트 안전은 기존 "정밀도의 선"이 담당.
