# 방 방문(Life Visit) 설계

> 담당: 허준녕 · 개념: [level-2-life-visit.md](../highlevel/level-2-life-visit.md)
> 서버(hub)의 방·위치 API와 클라이언트(미니홈피·마스코트)의 뷰 규칙.

## 1. 데이터 소유 경계

> **불변식: 서버가 가진 것 = 방문자가 볼 수 있는 것. 정확히 일치.**

| 데이터 | 위치 | 이유 |
|---|---|---|
| 에이전트 위치 (어느 방, 어느 셀) | 서버 | 위치의 단일 원천. 겹침 방지의 원자 처리 주체 |
| 방 디자인 (벽지·바닥·가구와 셀 배치) | 서버 | 방문자에게 보여주는 공개 표면. 주인이 오프라인이어도 방문 가능 |
| 다이어리·코칭·세션 데이터 | 클라이언트만 | 사적 내용. 서버·방문자 모두 모름 |

## 2. 공간 모델

- 방 = 유저당 1개, 정사각 셀 격자 **30(가로) × 16(세로)**. 셀 좌표는 정수 `(x 0~29, y 0~15)`
- 에이전트 점유 = **논리 1셀**. 렌더는 셀보다 커도 됨 (이웃 셀 위로 겹쳐 그림)
- 가구도 셀을 점유한다 → 점유 셀(에이전트+가구) = 이동 불가 셀
- 에이전트는 **동시에 한 방, 한 셀에만** 존재. 다른 방 입장 = 이전 방에서 자동 퇴장

## 3. 뷰 규칙 (클라이언트)

- 미니홈피 홈 탭이 그리는 방 = **내 에이전트의 현재 방** (서버에 물어봄)
  - 내 방 → 내 방 디자인 + 입장 중인 에이전트들(방문자 포함)
  - 남의 방 → 그 방 디자인 + 그 방의 에이전트들. 사적 탭 내용은 안 따라감
- 위치 갱신은 폴링(2초). 추후 이벤트 채널로 교체 가능
- 커서 피드백: 빈 셀 = pointer, 점유·범위 밖 = not-allowed
- **마스코트 입력 재배치**: 더블클릭 = 미니홈피 열기 · 우클릭 = 방 이동 팝오버
  ("내 방으로 돌아가기" + 방 목록 버튼, `max-height` + 스크롤) · 드래그 = 창 이동(기존 유지)
- 미니홈피 좌측 프로필 영역 하단에는 `미니홈피 이동` 드롭다운을 둔다.
  - 마스코트 우클릭의 방 이동 목록과 같은 공용 목적지 생성 규칙을 사용한다.
  - 남의 방에 있을 때는 `내 방으로 돌아가기`를 첫 항목으로 표시한다.
  - 내 방과 현재 방은 일반 이동 목록에서 제외하고, 나머지는 서버 목록 순서를 유지한다.
  - 현재 선택값과 `내 미니홈피`를 포함한 모든 방 항목에 서버의 현재 인원수를 표시한다.
  - 닫힌 상태는 별도 안내용 항목 없이 현재 위치를 표시한다. 내 방의 기본 표기는 `내 미니홈피`다.
  - 드롭다운은 이동 가능한 목적지가 없거나 이동 중일 때 비활성화한다.

## 4. 서버 API (A-Hub Life / life-server)

**A-Hub Work와 별개의 서버 프로세스** — `a-hub/life/` 폴더의 독립 FastAPI 앱
(기본 호스트 포트 **8001**). 같은 `a-hub/` 아래에 있지만 Work(Space/Page 협업 도메인)와
Python 프로젝트·배포·스토어·생애주기를 공유하지 않는다. 신원은 life 전용 토큰(Bearer).

| Method | Path | 동작 |
|---|---|---|
| POST | `/life/register` | `{name}` → `{agent_id, token, life_id}`. 유저 등록 + 개인 방 생성. 에이전트는 자기 방에 자동 입장 |
| GET | `/life` | 방 목록 `[{life_id, owner_name, occupants}]` — 이동 메뉴의 원천 |
| GET | `/life/{id}` | 방 상태: `{design, occupants: [{agent_id, name, cell, is_owner}]}` — 폴링 대상 |
| POST | `/life/{id}/enter` | `{cell?}` 입장. cell 생략 = 서버가 빈 셀 배정(자율 입장). 이전 방 자동 퇴장 |
| POST | `/life/{id}/move` | `{cell}` 방 안 이동. 그 방에 있어야 함 |
| PUT | `/life/{id}/design` | 방 주인만. `{wallpaper, floor, objects: [{asset_id, category, cell, size, rotation}]}` |
| GET | `/life/me` | 내 에이전트의 현재 위치 `{life_id, cell}` — 뷰 규칙의 입력 |

### 원자성 (겹침 금지)

- enter/move는 서버가 **"해당 셀이 비었을 때만 점유"를 원자 연산**으로 수행. 실패 = `409 cell_taken`
- 인메모리 구현은 전역 락, DB 구현은 `(life_id, x, y)` 유니크 제약으로 동일 의미
- 가구 배치(design PUT)는 회전된 footprint 전체를 검사하며, 에이전트·다른 가구와 충돌하면 409

### 에러

`400 invalid_request`(범위 밖 셀 등) · `401 unauthorized` · `403 forbidden`(남의 방 design 등) ·
`404 not_found` · `409 cell_taken`

## 5. 클라이언트 구현 지점

| 지점 | 내용 |
|---|---|
| 설정 | 설정 창에 "Space A 서버" 섹션: life-server URL(예: `http://localhost:8001`) + 유저 이름. 저장 시 register 호출, 토큰은 로컬 설정에 보관 |
| Rust 커맨드 | `life_me` / `life_list` / `life_state` / `life_enter` / `life_move` — hub HTTP 호출 래퍼 (네트워크는 락 밖 규율 동일) |
| 홈 탭 | 기존 장식용 MiniLife을 격자 방 렌더로 교체. 점유 맵 기반 커서, 좌클릭 이동, 에이전트는 이름 시드 로봇으로 렌더 |
| 마스코트 | 280×280px 투명 창. 우클릭 → 팝오버(내 방으로 + 방 목록), 이동 항목이 3개 이상이면 3행 높이에서 세로 스크롤. 클릭 = 미니홈피(기존 동작 유지, 더블클릭 분리는 후속) |
| 미니홈피 좌측 | 프로필 영역 하단에 `미니홈피 이동` 드롭다운. 마스코트 메뉴와 동일한 공용 목적지 목록을 사용하고 선택 즉시 이동 |
| 테스트용 | `AGENT_MENTOR_DATA_DIR` env로 데이터 디렉터리 오버라이드 — 한 PC에서 두 인스턴스 실행 가능 |

## 6. 검증 시나리오 (한 PC, 실제 배치 흉내)

1. life-server를 기동(`a-hub/life/`에서 `docker compose up` — 호스트 포트 8001), 클라이언트는 `http://<호스트IP>:8001`으로 접속
2. 클라이언트 A(유저 "A")·B(유저 "B")를 데이터 디렉터리 분리로 동시 실행
3. A가 우클릭 메뉴에서 B의 방으로 이동 → B의 홈 탭에 A 에이전트가 나타남
4. A의 홈 탭은 B의 방(디자인+입주자)을 보여줌 → "에이전트 시점" 뷰 규칙 확인
5. 같은 셀 동시 점유 시도 → 한쪽 409 → 겹침 없음 확인

## 8. 인테리어 편집

### 데이터 소유 경계

| 데이터 | 소유자 | 이유 |
|---|---|---|
| 테마·가구 픽셀 리소스 | 클라이언트 | 앱 버전과 함께 캐시·배포하고 서버의 정적 파일 트래픽을 없앤다 |
| 카탈로그 메타데이터(`asset_id`, 카테고리, 기본 footprint) | 클라이언트 | 리소스와 동일 버전으로 관리한다 |
| 선택 테마·배치·회전·실제 점유 셀 | life-server | 모든 방문자가 같은 방을 보고 이동/배치 충돌을 원자 검증한다 |

서버는 리소스 파일을 저장하지 않는다. 대신 안정적인 `asset_id`와 검증에 필요한
`category`, `origin`, `footprint`, `rotation`을 저장한다. 클라이언트가 모르는 미래
`asset_id`는 자리와 점유는 유지하되 대체 스프라이트로 표시한다.

### 공간과 배치 규칙

- 방은 정면 직사각형이 아니라 싸이월드 미니라이프과 같은 **2.5D 아이소메트릭 공간**이다.
- 논리 바닥은 `20×20` 정사각 격자이며 화면에서는 확대된 마름모 타일로 투영한다. 화면에 보이는 모든 바닥 셀은 이동·가구 배치가 가능하다.
  `screenX=(x-y)×tileW/2`, `screenY=(x+y)×tileH/2`를 공통 투영식으로 사용한다.
- 바닥의 뒤쪽 두 변에서 북쪽 벽과 측면 벽이 수직으로 올라온다. 벽지는 두 벽면에
  같은 테마를 적용하되 각 평면의 투영에 맞춰 렌더한다.
- 에이전트와 소파·조명·책상·식탁·가전은 바닥 평면에만 배치한다.
- 창문은 `wall=north|west`와 벽면 셀을 가지며 바닥 점유에는 포함하지 않는다.
  창문 방향은 벽에서 파생하며 `west=90(↘)`, `north=180(↙)`만 허용한다.
- 가구는 1셀로 제한하지 않는다. 객체는 기준점 `cell`, 회전 전 크기 `size=[w,h]`,
  `rotation=0|90|180|270`을 가진다. 90/270도에서는 실제 footprint의 폭·높이가 뒤집힌다.
- 점유 셀 전체가 범위와 영역 규칙을 만족해야 하며, 다른 가구·에이전트와 한 셀이라도
  겹치면 서버가 `409 cell_taken`을 반환한다.

### 스프라이트와 앵커

- 생성형 아틀라스를 런타임에서 분할하지 않는다. 가구 리소스는 `asset_id/방향.png` 형태의 독립 투명 PNG 파일로 관리하고 카탈로그가 개별 파일을 직접 참조한다.
- 두 벽이 만나는 뒤 꼭짓점을 원점으로 삼고 월드 X축은 화면 `↘`, Y축은 화면 `↙`이다.
  `base_size=[x_span,y_span]`은 이 월드 축의 길이이며 화면 픽셀의 가로·세로가 아니다.
- 책상은 회전 0도에서 장축이 X축에 놓이고 다섯 자산 모두 `[3,2]`다. 90·270도 회전에서만
  `[2,3]`이 된다. 이전 `[4,2]` 저장값도 클라이언트 카탈로그 정규화 시 `[3,2]`로 바꾼다
  (ADR 0011).
- 일반 바닥 가구는 원본 PNG의 최하단 접촉 구간 중앙을 이미지 앵커로 사용하고,
  좌우 반전한 뷰는 접지 X도 함께 반전한다(ADR 0009). 다만 책상처럼 여러 다리와 전체 직사각
  footprint가 명시된 자산은 가장 낮은 한 점이나 이미지 박스를 배치 기준으로 사용하지 않는다.
  원본별 다중 지지점 윤곽을 footprint 네 경계 안에 균일 배율로 맞추고, 그 결과에서 렌더 너비와
  앵커를 함께 파생한다(ADR 0011).
- 각 PNG의 픽셀 접지 앵커, footprint 내부의 월드 접지 앵커와 투영 너비는 자산
  매니페스트에 기록한다. 이미지 높이는 원본 비율을 유지하며 정사각형 렌더 박스로 제한하지 않는다.

- 정면 이미지를 CSS/Canvas로 임의 회전하지 않는다. 각 원본 슬롯은 다른 아이템이 섞이지
  않는 독립 PNG이고 원본 종횡비를 유지한다.
- 원본 슬롯 이름과 그림이 실제로 바라보는 방향을 분리한다. 카탈로그는 자산별 실제 방향
  메타데이터를 가지며, 목표 `ne/se/sw/nw`에 맞는 원본과 좌우 반전 여부를 해석한다.
  파일 순번을 네 방향에 공통으로 대입하지 않는다(ADR 0006).
- 카탈로그는 선택된 원본의 픽셀 접지 `anchor=[x,y]`와 정규화된
  `footprintAnchor=[x,y]`를 가진다. 기본 월드 접점은 화면 전면 꼭짓점 `[1,1]`이며,
  중앙 받침대처럼 실제 접점이 다른 자산은 footprint 내부 위치를 명시한다(ADR 0007).
- 2×2 원형 테이블의 최하단 픽셀은 중앙 1×1 받침의 전면 끝이므로
  `footprintAnchor=[0.75,0.75]`를 사용한다(ADR 0009).
- 창문은 논리 벽 방향과 PNG 반전을 분리한다. 각 원본의 상단 모서리 기울기를 기록하고,
  필요한 자산만 좌우 반전한 뒤 Y축 전단을 적용한다. 좌상벽은 기울기 `-0.5`, 우상벽은
  `+0.5`로 맞추며 접지 앵커에도 같은 행렬을 적용한다(ADR 0008).
- 창문의 `size[0]`은 벽 점유 칸 수다. 미리보기와 편집 중 배치 표시는 3칸 또는 5칸의
  실제 연속 점유 구간 전체를 표시한다.
- 책상의 `↗`·`↖`은 같은 `sw` 원본을, `↘`·`↙`은 같은 `ne` 원본을 좌우 반전해 사용한다.
  각 원본에는 보이는 다리·패널 하단의 외곽 지지점을 여러 개 기록한다. 접점 묶음을 회전된
  `2×3` footprint 안에 `0.02`칸 여유로 넣는 최대 균일 배율을 계산한다. 두 원본 중
  더 작은 렌더 너비를 네 방향이 공유하고 접점의 전면 끝을 footprint 전면 경계에 맞춘다.
  같은 원본을 쓰는 반전 방향은 같은 등록을 재사용한다. 책상 PNG에는 상판 일부만을
  기준으로 한 Y축 전단이나 방향별 박스 리프트를 적용하지 않는다(ADR 0011).
- 화면상의 겹침 순서는 바닥 객체와 에이전트 모두 `depth=x+y+footprintDepth` 순으로 정렬한다.
  따라서 앞쪽 가구/캐릭터가 뒤쪽 항목을 자연스럽게 가린다.
- 회전은 방향 스프라이트 선택과 footprint 회전을 동시에 수행하며, anchor 화면 좌표는
  바뀌지 않는다. 이미지 확대는 정수 배율과 `image-rendering: pixelated`만 허용한다.

### 클라이언트 카탈로그

- 테마 10개: 각 테마는 벽지와 바닥 패턴의 조합이다.
- 카테고리 7개: 소파·조명·책상·테이블·의자·가전·창문.
