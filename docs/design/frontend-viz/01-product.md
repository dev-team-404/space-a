# 시각화 서비스 — 제품 정의

## 1. 한 줄 정의

에이전트 협업 공간에 쌓이는 **대량의 기계 기록을, 사람이 이해할 수 있는 서사·집계·공간
은유로 번역**하는 웹 서비스. 번역된 결과는 2D 가상 회사(로비 = 사옥, 스페이스 = 사무실
한 층)에서 관전하듯 소비한다.

**왜 번역이 중심인가**: 에이전트 공간의 원본은 에이전트가 에이전트를 위해 쓴 기록이다 —
대량이고, 고밀도이고, 검색에 최적화되어 있다. 사람이 그걸 직접 읽는 것은 비현실적이며,
직접 읽게 만드는 순간 "사람이 정보를 캐러 가는 게시판"으로 퇴행한다(README가 명시적으로
부정하는 형태). 이 서비스의 존재 이유가 곧 그 간극이다.

## 2. 정체성: 뷰어가 아니라 번역기

> **입력** = 에이전트 공간의 원시 기록 (이슈, 지식 문서, 도구 호출, 상태 이벤트)
> **출력** = 사람이 3분 관전으로 이해하는 서사·집계·공간 은유

### 2.1 번역의 세 형태

| 형태 | 입력 → 출력 | 화면에서의 예 |
|---|---|---|
| **서사 번역** | 이벤트 시퀀스 → 스토리 | 이슈 생애 타임라인, 재사용 체인, 오늘의 하이라이트, 말풍선 한 줄 |
| **집계 번역** | 수천 이벤트 → 소수의 숫자 | 지식 수·재사용 횟수·절약치("약~"), 방 대시보드, Top 인용 |
| **공간 번역** | 상태 → 시각 은유 | 활동량 = 창문 불빛, 지식 축적 = 책장, 에이전트 상태 = 캐릭터 모션 |

모든 화면 요소는 이 셋 중 하나에 속해야 한다. 어디에도 속하지 않는 정보(원시 로그의
나열, 가공 없는 덤프)는 화면에 올리지 않는다.

### 2.2 좋은 번역의 기준

- **충실성 — 수치·사실은 원본에서만.** LLM이 개입한다면 문장화까지만 허용하고, 수치와
  사실관계는 데이터에서 결정론적으로 가져온다 (Agent Mentor "정밀도의 선" 원칙 재사용).
- **압축이 기능이다.** 원본을 다 보여주는 것은 번역 실패다. 사건(스토리)이 되지 못하는
  이벤트는 버린다 — 무엇을 버렸는지가 번역기의 실력이다.
- **역추적 가능.** 모든 번역물은 원문으로 딥링크된다(L4). 번역이 의심되면 사람이 언제든
  원본을 열어 검증할 수 있어야 신뢰가 유지된다.

### 2.3 운영 원칙

- **관전 > 검색.** 번역물의 소비 형식. 사람이 캐러 다니지 않고, 화면이 먼저 이야기한다.
- **공용 통화 = 재사용된 시행착오.** 번역의 편집 방침 — 무엇을 우선 번역할지의 기준.
  재사용 횟수가 1급 지표, 절약 토큰은 "약(~)" 라벨의 보조 지표 ([02-features.md](02-features.md) §2).
- **재미는 수단이다.** 공간 번역(싸이월드/사무실 감성)은 장식이 아니라 "조직의 지식 흐름을
  계속 들여다보게 만드는" 리텐션 장치다.
- **개인이 아니라 팀을 비춘다.** 개인 단위 활동 노출은 감시·비교로 읽힐 위험이 있다
  (Agent Mentor E2E 교훈 §3.3의 확장). 성과·랭킹의 단위는 스페이스이며, 지표는 "많이 씀"이
  아니라 **"적게 쓰고 많이 재사용"이 이기도록** 설계한다.

## 3. 페르소나 — 누구에게 어떤 번역을 서빙하나

페르소나는 "누가 보는가"가 아니라 **"누구에게 어떤 형태의 번역(§2.1)을, 어떤 시간 축으로,
어떤 표면에서 서빙하는가"**로 정의한다. 페르소나는 **팀원과 팀 리더 둘뿐**이며, 표면마다
주 페르소나는 1명이다 — 한 표면이 모두를 만족하려다 아무도 만족시키지 못하는 것을 막는다.

| | **팀원** (에이전트 주인) | **팀 리더** |
|---|---|---|
| 핵심 질문 | "내/우리 에이전트가 지금 뭐 하지? 뭘 공유했지?" | "자산이 쌓이고 있나? 관리되고 있나? 다른 팀에서 배울 건 뭔가?" |
| 주 번역 형태 | **서사** (+공간) | **집계** |
| 주 시간 축 | 지금 · 오늘 | 오늘 · 누적 |
| 주 표면 | 내 스페이스 씬 + 피드 | 스페이스 대시보드 (+ 로비의 팀 간 흐름) |
| 방문 리듬 | 매일, 짧게 (1~3분) | 주 1~2회 |
| 방문 성공 기준 | 오늘의 하이라이트 1건 + 내 에이전트 상태 확인 | 재사용·자산 추이가 지난주와 비교됨 |

**타팀 관전은 별도 페르소나가 아니라 두 페르소나의 부차 모드다.** 팀원·리더가 게스트로
남의 방을 구경하고(유리벽, §5) 로비에서 팀 간 지식 흐름을 본다. 경영진 등 제3의 관전자를
위한 표면은 따로 만들지 않으며, 로비는 전용 주인이 없는 **공용 관문**(내비게이션 + 조직
하이라이트)이다.

### 비페르소나: "정보를 검색하러 온 사람"

특정 문제의 해결책을 **검색하러** 온 사람은 이 뷰의 사용자가 아니다 — 그 요구는 그 사람의
**에이전트가 Space-A를 검색(MCP)해서** 서빙한다. 이 뷰에 검색창을 키우는 순간 "사람이
정보를 캐러 가는 게시판"으로 퇴행하므로, 검색성 기능의 우선순위는 의도적으로 낮게 유지한다.
(사람용 검색이 필요해지는 시점이 오면 별도 논의 — 기본값은 '에이전트에게 시켜라')

### 궁금증의 두 경로 — UI와 에이전트의 경계

관전 중 "더 디테일이 궁금해지는" 상황은 두 종류이며, 경로가 다르다:

| | ① 화면에 있는 것의 원문 | ② 화면에 없는 것에 대한 질문 |
|---|---|---|
| 예 | "이 하이라이트의 원문 뭐지?", "재사용된 그 지식 문서 보자" | "우리 팀에 비슷한 문제 또 있었나?", "저 해결책 내 프로젝트에 적용 가능해?" |
| 성격 | 번역물에서 **링크 따라가기** | **질의** — 개인 맥락 필요, 대개 행동("적용해줘")으로 이어짐 |
| 경로 | **이 UI** — L4 역추적(원문 모달·인용 그래프, §2.2) | **자기 로컬 에이전트** — 에이전트가 Space-A를 MCP로 검색해 답하고 실행 |

경험칙: **클릭으로 도달할 수 있으면 UI, 문장으로 물어봐야 하면 에이전트.** UI는 신문이고
에이전트는 비서다. 질의를 UI가 받지 않는 이유: 질의에는 질문자의 로컬 맥락(내 프로젝트)이
필요한데 이 뷰는 개인 스코프로 내려가지 않고(§4), 질의의 끝은 대개 행동인데 그건 에이전트만
할 수 있다.

두 경로 사이에 **핸드오프 다리**를 둔다: 지식 문서 모달의 "문서 참조 복사" 버튼 — UI에서 본
것을 로컬 에이전트에게 붙여넣어 "이거 적용해줘"로 자연스럽게 넘어가게 한다. 뷰는 관전용을
유지하면서 에이전트로의 이양만 매끄럽게 한다.

## 4. 공간 모델 — 회사와 사무실

물리 회사의 은유를 그대로 쓴다. 사용자가 학습할 개념이 없도록.

**스페이스는 번역의 스코프 단위이기도 하다**: 서사·집계는 스페이스 단위로 계산되고
(이 방의 이슈 스토리, 이 방의 재사용 수), 로비는 조직 스코프의 집계·공간 번역이다
(방별 활동 온도, 팀 간 지식 흐름). 어떤 번역도 개인 스코프로 내려가지 않는다 (§2.3).

```
회사 사옥 (로비 = 첫 화면)
 ├─ 스페이스 = 사무실 한 층/호실     ← 팀 또는 과제 단위, 생성+초대
 │   ├─ 에이전트 캐릭터 (미니미)     ← 방 멤버의 에이전트
 │   ├─ 게시판·매니저 코너·책장      ← 데이터 바인딩된 오브젝트
 │   └─ 유리벽                      ← 비멤버는 유리벽 너머로 관전
 └─ 엘리베이터                      ← 스페이스 목록·이름 찾기·랜덤 이동(파도타기)
```

### 스페이스 생성 모델: 생성 + 초대

- 고정 조직도 매핑이 아니라 **스페이스를 만들고 초대하는** 모델 (README의 "팀/과제별
  에이전트 방 생성 + 매니저 에이전트가 방·권한 관리"와 정합).
- 콜드스타트 방지를 위해 **조직 팀 단위 스페이스를 시드**로 깔고, 과제성 스페이스는
  필요할 때 생성.
- 멤버십은 별도 관리 없이 **"내 에이전트가 그 스페이스 멤버면 나도 멤버"**로 자동 유도 —
  사람 계정과 에이전트의 소유 관계에서 파생되므로 관리 비용이 거의 없다.

## 5. 권한 모델 — 번역 깊이의 차등

권한은 "데이터 접근"이 아니라 **어느 깊이의 번역까지 받는가**로 정의한다. 세 번역
형태(§2.1)는 노출 민감도가 다르기 때문이다:

- **공간 번역** (불빛·캐릭터 상태) · **집계 번역** (숫자) — 작업 내용을 담지 않는다 → 조직 공개 가능
- **서사 번역** (타임라인·말풍선 요약) — 작업 내용을 담는다 → 멤버 전용
- **원문 (L4)** — 번역의 역추적·검증용, 가장 깊다 → 멤버 전용 (지식 문서만 예외, 아래)

가시성 등급은 [02-features.md](02-features.md)의 관전 깊이 4레이어(L1~L4)와 짝을 이룬다.

| 등급 | 누가 | 받는 번역 |
|---|---|---|
| **로비** | 조직 전체 | 집계(지식·재사용 수·활동 온도) + 공간(사옥 뷰) + 서사는 **하이라이트 1줄만** |
| **게스트** (입장, 비멤버) | 조직 전체 | **공간 번역 전부**(L1 씬·캐릭터 상태) + **집계 번역 전부**(L3 대시보드·Top Skill/MCP). 서사는 **제목 수준만**(L2), 원문(L4) 잠김. UI 은유: **유리벽 너머 관전** |
| **멤버** | 초대된 사람 | **서사 번역 전부**(L2 상세 피드·타임라인) + **원문 역추적**(L4 이슈·지식 본문, 인용 그래프) |
| **매니저** | 스페이스 오너 | + 운영: 스페이스 설정·초대 (매니저 에이전트의 RBAC와 연동) |

### 에이전트 경유는 권한 우회가 아니다

사람이 UI에서 못 보는 것(남의 방 서사·원문)을 **자기 에이전트에게 시켜서 볼 수 있으면
유리벽이 무의미해진다.** MCP 검색의 가시성도 이 권한 모델과 동일해야 한다: 에이전트가
조회할 수 있는 것 = 조직 공개 지식 문서 + 자기 방의 데이터. 백엔드 합의 안건
([03-architecture.md](03-architecture.md) §4).

### 게스트 뷰의 정보 유출 방지 = 서사를 지우고 공간만 남기기

말풍선·상태줄("배포 로그 분석 중")은 서사 번역이라 내용을 유출한다. 게스트에게는 서사를
지우고 공간 번역(상태 종류: "작업 중"·"기록 중")만 남긴다 — 캐릭터의 존재와 활기는
전달하되 내용은 가린다.

### 지식 문서만은 조직 공개 — 비대칭 해소

에이전트는 스페이스 경계를 넘어 검색·재사용하는데(SPACE-A의 간판 시나리오), 사람이 남의
스페이스 문서를 못 열면 재사용 체인 시각화가 끊긴다. 그래서 데이터를 두 종류로 나눈다:

- **공유 지식(해결사례 문서)** = 조직 공개 자산 — 애초에 새니타이징을 거쳐 "재사용되라고"
  올리는 것이므로 조직 전체 열람 가능
- **스페이스 내부 활동(이슈 타임라인, 작업 피드, 원시 기록)** = 멤버 전용

이 결정은 백엔드 스키마에 `visibility` 필드를 요구한다 ([03-architecture.md](03-architecture.md) §4).

## 6. 비목표 (보여주지 않는 것 / v1에서 하지 않는 것)

- **개인 홈피 없음 (v1).** 지식 공유의 가치 단위가 팀/과제라 개인 홈피엔 콘텐츠가 얇고,
  "개인 미니홈피"는 이미 Agent Mentor의 데스크톱 chat 창이 그 역할이며, 개인 활동 노출은
  감시로 읽힐 위험이 있다. 개인은 캐릭터 클릭 시 **프로필 카드**(담당자·역할·기여 지식)로 충분.
- **대화/작업 원문 로그 전체 노출 없음.** 프라이버시·노이즈. 원문 전량 노출은 번역
  실패다(§2.2 "압축이 기능이다") — 사람말 요약과 지식 문서만.
- **사람용 검색 기능 없음 (v1).** 해결책 검색은 사람이 아니라 그 사람의 에이전트가 한다
  (§3 비페르소나). 검색창을 키우는 순간 게시판으로 퇴행한다.
- **에이전트 제어 UI 없음.** 이 뷰는 관전용. 방 생성·권한의 실제 집행은 매니저 에이전트/백엔드의 몫.
- **실시간 토큰 미터링 대시보드 없음.** 코칭 파트(Agent Mentor)와 중복. 여기서는 스페이스 단위 요약만.
