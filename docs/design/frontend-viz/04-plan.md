# 시각화 서비스 — 구현 플랜과 열린 질문

## 1. 구현 플랜

스택 미확정(CLAUDE.md) 전제로, **백엔드 없이도 진행 가능한 순서**로 배치한다.
기능 번호(F1~F19)는 [02-features.md](02-features.md) §6.

| Phase | 목표 | 산출물 | 의존 |
|---|---|---|---|
| **0. 계약 확정** | [03-architecture.md](03-architecture.md) §4 데이터 계약을 백엔드 담당과 합의. 특히 ReuseEvent 1급 이벤트화(MCP 서버 방식)와 `Knowledge.visibility` | 스키마 합의안, ADR (스택 포함) | 백엔드 설계 |
| **1. 목업 구동 MVP** | mock JSON 고정 데이터로 F1~F7 동작: 로비(사옥) → 스페이스(사무실 층) 진입 → 씬+캐릭터+말풍선 → 피드 2종 → 원문 모달 → 멤버/게스트 토글 | 데모 가능한 정적 프로토타입 | 없음 (즉시 착수 가능) |
| **2. 라이브 연동** | 실제 API/폴링 연결(F11), 인증·멤버십(F12 — 유리벽의 서버 측 집행), 게시판·매니저 코너(F8·F9), 에이전트 핸드오프(F19) | 백엔드 연동 서비스 | Phase 0 계약, 백엔드 API |
| **3. 인사이트** | F10·F13 — 스페이스 대시보드, Top Skill/MCP, 로비 층간 지식 흐름 | 리더용 완성 | 집계 API |
| **4. 감성·리텐션** | F14~F18 — 파도타기, 인용 그래프, 방명록, 사무실 꾸미기, 일일 다이제스트 | 완성형 서비스 | Phase 2~3 |

**Phase 1을 최우선으로 미는 이유**: 스택·백엔드가 미확정인 지금, mock 프로토타입이
(a) 데모로 프로젝트 가치를 즉시 보여주고 (b) 데이터 계약의 타당성을 화면으로 검증해
백엔드 설계에 피드백을 주며 (c) 멤버/게스트 토글로 권한 모델의 UX를 미리 확인할 수 있다.

### Phase 1 세부 (착수 순서)

1. mock 데이터셋 작성 — 계약 스키마(03 §4) 그대로의 JSON. 스페이스 2개(권한 있음/없음),
   이슈 흐름 1건, 재사용 체인 1건(크로스 스페이스) 포함
2. 로비 씬 (F1) — 사옥 단면 + 층 카드 + hover
3. 스페이스 씬 (F2·F3) — 배경 + 캐릭터 오버레이 + 말풍선 (MVP는 정적 배경 이미지 방식, 03 §5)
4. 사이드바 피드 (F4·F5) + 원문 모달 (F6)
5. 게스트 유리벽 토글 (F7) — 씬 유지 + 피드 제목화 + 말풍선 상태만
6. 팀 데모 → 계약·UX 피드백 수집 → Phase 0 확정에 반영

**상태 (2026-07-12): Phase 1 구현 완료** — [`prototype/frontend-viz/`](../../../prototype/frontend-viz/).
의존성 없는 정적 HTML/JS/CSS로 F1~F7 동작 (생성 배경 이미지 + 픽셀 좌표 오버레이 방식 검증).
문서가 앞서 있는 갭: F5 절약치("약~") 표기, 하이라이트 관문, F19 핸드오프 버튼은 프로토타입 미반영.

## 2. 열린 질문

| # | 질문 | 후보 / 현재 기울기 |
|---|---|---|
| Q1 | 프론트 스택 | Svelte 5 (Mentor와 통일) vs React — ADR로 확정 |
| Q2 | 씬 렌더링 | MVP: 정적 배경 + DOM 오버레이 → 이후 Canvas/PixiJS 전환 여부 |
| Q3 | 실시간 프로토콜 | MVP 폴링 → SSE vs WebSocket (분 단위 갱신이라 급하지 않음) |
| Q4 | **서사 번역 파이프라인** — 사람말 요약·스토리의 생성 주체와 시점 | 에이전트 기록 시 vs 백엔드 LLM 배치 vs 뷰 서버 · "번역기" 정체성(01 §2)에서 가장 중요한 아키텍처 질문으로 승격 |
| Q5 | 씬 갱신 리듬 | 분 단위 스냅숏 기본 (03 §2.1) — 구체 주기는 실데이터 보고 튜닝 |
| Q6 | 캐릭터 아트 | 파츠 조합 절차 생성 (Mentor `robot/` 재사용) vs 고정 스프라이트 셋 |
| Q7 | 사옥 뷰의 스케일 한계 | 스페이스가 수십 개를 넘으면 층 단면이 안 그려짐 — 동/단지 확장? 검색 우선 전환? |
| Q8 | 지식 새니타이징 책임 | 공유 시점(로컬 에이전트) vs 서버 수신 시점 — ②고리 설계와 공동 결정 |
| Q9 | 방명록의 노출 범위 | 멤버만 쓰기? 게스트도 응원 가능? |
| Q10 | 절약 추정 산식 | 원본 이슈 해결 비용 기반(03 §4-6) vs 고정 계수 — 백엔드와 공동 결정 |
| Q11 | 씬의 멤버 수 확장 (배경에 책상 수가 고정되는 한계) | 단계 대응: ① 서 있는 자리 앵커 추가(~12명) → ② 방 크기 티어 S/M/L (팀 성장 = "사무실 이사" 연출) → ③ 모듈러 스프라이트 합성(가구=데이터, 방 꾸미기 기반) |

## 3. 결정된 것 (이 문서 묶음에서 확정한 설계)

| 결정 | 내용 | 근거 |
|---|---|---|
| 제품 중심 | "뷰어가 아니라 번역기" — 서사·집계·공간 3형태 번역, 충실성·압축·역추적 기준 | [01-product.md](01-product.md) §2 |
| 공간 모델 | 개인 홈피 없음(v1) · 스페이스 생성+초대 · 팀 시드 | [01-product.md](01-product.md) §4, §6 |
| 권한 모델 | "번역 깊이의 차등" — 로비 공개 → 게스트 유리벽(공간·집계) → 멤버(서사·원문), 지식 문서만 org 공개 | 01 §5 |
| 레이어 = 번역 형태 | L1=공간 · L2=서사 · L3=집계 · L4=원문 역추적 — 레이어 경계가 곧 권한 경계 | 02 §1 |
| 페르소나-표면 1:1 | 페르소나는 팀원·리더 둘뿐. 씬=팀원(서사) · 대시보드=리더(집계) · 로비=공용 관문 · 타팀 관전은 부차 모드 · "검색하러 온 사람"은 비페르소나 | 01 §3 |
| 궁금증의 두 경로 | 클릭(역추적)=UI · 질문(검색·적용)=자기 에이전트 · 사이에 "참조 복사" 핸드오프(F19) · 에이전트 경유는 권한 우회 불가 | 01 §3, §5 |
| 번역 계산 분리 | 집계·공간 = 결정론, 서사만 LLM — 이벤트 시 1회 생성해 캐시 | 03 §2.2 |
| UI 은유 | 로비 = 회사 사옥(층=스페이스), 스페이스 = 사무실 한 층 | 02 §3 |
| 북극성 지표 | 재사용 횟수 = 1급, 절약 토큰 = 보조("약~" 추정 표기) | 02 §2 |
| 하이라이트 관문 | 로비 카드·방 입장·알림이 전부 "오늘의 사건 1건"을 민다 | 02 §2 |
| 멤버십 | 사람 멤버십은 에이전트 소유 관계에서 파생 | 01 §4 |
| 갱신 리듬 | 초 단위 라이브가 아니라 분 단위 스냅숏 + 서사적 재생 | 03 §2.1 |
| 간판 기능 | 지식 재사용 체인 (F5) — ReuseEvent 1급 이벤트가 성립 조건 | 03 §3 |
