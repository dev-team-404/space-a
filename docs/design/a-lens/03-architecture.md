## 목표 아키텍처에서의 위치 (2026-07-17 합의)

전체 그림: [docs/highlevel/architecture.html](../../highlevel/architecture.html)

```
로컬 PC                        공용 서버                         소비
Claude Code ──C1(MCP)────▶ a-hub-work  ──C2(계약 확정)──▶ a-lens (서버) ◀─브라우저─ 사람
a-mate      ┄텔레메트리(계획)▶            (지식·이슈·재사용)      ▲
a-mate      ──입장·이동────▶ a-hub-life ┄프레즌스 조회(계획)┄┘
            ┄하트비트(계획)─▶  (= room server)
```

- a-lens는 두 서비스의 **읽기 전용 소비자**이면서, 그 자체는 관전 웹 UI를 서빙하는
  **서버**다 (브라우저는 컴포넌트가 아니라 사람의 접근 수단).
- 유일한 확정 파이프는 C1과 방 방문(room-server) API. **a-mate → 서버 방향의 텔레메트리·하트비트는
  아직 계획**이다 — 프레즌스·토큰 게이지 등 이 데이터에 기대는 표면은 그 전까지
  fake/mock으로만 굴러간다.
- 쓰기는 방명록(P2) 하나뿐이라 **mock 데이터로 백엔드 없이 선행 개발 가능**하다.
  (방명록의 쓰기 대상은 미정 — "a-lens는 hub에 읽기만" 원칙과의 정합은
  [02-features](02-features.md)의 기능 우선순위(P2) 참고.)

## 핵심 기술 결정

- **데이터 리듬은 두 축.** ① work 축(지식·이슈·집계)의 "실시간"의 실체는 분 단위
  스냅숏 — 너무 빨라서 못 읽는 화면은 관전이 아니다. MVP는 주기 폴링으로 충분, 이후
  SSE/WebSocket. ② life 축(프레즌스)은 휘발성·고빈도라 별도의 가벼운 폴링으로 분리한다
  (원천은 a-mate 하트비트 — 계획, [04 G8](04-data-mapping.md) 참조).
- **번역 계산의 분리** — 집계·공간 번역은 결정론(서버 쿼리·매핑 테이블)이라 LLM이 필요
  없다. LLM 비용·환각 리스크는 **서사 번역에만** 존재하므로, 조회 시가 아니라 **이벤트
  발생 시 1회 생성해 캐시**한다. 생성 주체·시점은 최중요 열린 질문(README Q1).
- **간판 기능의 성립 조건 = ReuseEvent 1급 이벤트.** 인용이 본문 속 링크로 묻히면 재사용
  체인을 그릴 수 없다. 에이전트 공간이 MCP 서버(search/cite)라서 서버가 cite 호출을 직접
  기록 — C1/C2 v2에 반영 완료.
- **유리벽은 서버 집행.** 게스트 응답에서 서버가 상세 필드를 제거한다. 클라이언트 blur는
  연출이지 보안이 아니다. (단, 허브가 세밀한 접근 제어를 해커톤 범위 밖으로 선언(#36)해
  데모에서는 클라이언트 연출로 남을 수 있다 — 원칙은 유지, 시점은 [04](04-data-mapping.md)
  유리벽 절의 단서 참조.)

## 프론트 기술 후보 (미확정 — 확정 시 ADR)

| 항목 | 후보 | 비고 |
|---|---|---|
| 프레임워크 | Svelte 5 vs React | 조직 숙련도 기준 |
| 씬 렌더 | 정적 배경 + DOM 오버레이 (MVP 검증됨) → Canvas/PixiJS | PixiJS로 확정 (ADR 0003, frontend 구현) |
| 캐릭터 | 파츠 조합 절차 생성 vs 고정 스프라이트 셋 | 코칭 파트의 로봇 렌더가 참조 구현 |
| 실시간 | 폴링 (MVP) → SSE vs WebSocket | 분 단위 갱신이라 급하지 않음 |
