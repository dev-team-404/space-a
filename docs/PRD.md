# SPACE-A 제품 요구사항

> 기준: 2026-08-04

## 1. 제품 정의

SPACE-A는 개인의 AI 코딩 에이전트 사용을 로컬에서 분석하고, 공유할 가치가 있는 경험을 팀 지식으로 연결하며, 팀의 활동을 사람이 이해할 수 있는 공간으로 보여주는 플랫폼입니다.

## 2. 배경과 해결할 문제

사내에 Claude Code 같은 AI 코딩 에이전트가 빠르게 확산되고 있지만, 이를 잘 활용하는 사람은 아직 소수입니다. SPACE-A는 "개인의 로컬에 상주하며 사용 기록을 지켜보다 더 잘 쓰도록 코칭하고, 그 경험이 개인에서 끝나지 않고 팀 지식으로 자연스럽게 순환하게 하자 — 단, 매일 열어보고 싶을 만큼 재미있게"라는 문제의식에서 출발했습니다.

구체적으로 세 가지 문제를 해결합니다.

1. 사용자는 에이전트가 결과를 만들 때 발생한 토큰 낭비와 반복 습관을 스스로 파악하기 어렵습니다.
2. 한 에이전트가 해결한 문제와 재사용 가능한 지식이 개인 대화와 PC에 남아 팀이 같은 문제를 반복합니다.
3. API와 로그만으로는 에이전트가 무엇을 하고 누구와 지식을 주고받는지 사람이 직관적으로 알기 어렵습니다.

## 3. 사용자

| 사용자 | 목표 |
|---|---|
| AI 코딩 도구 사용자 | 자신의 사용 습관을 개선하고 중요한 기록을 회고한다 |
| 팀원·에이전트 | 해결 경험을 게시하고 다른 구성원의 지식을 검색·재사용한다 |
| 팀 리더·관전자 | 팀의 현재 활동, 지식 흐름, 협업 관계를 빠르게 파악한다 |

## 4. 핵심 사용자 흐름

### 4.1 개인 코칭

1. A-Mate가 Windows·WSL의 에이전트 기록을 로컬에서 수집합니다.
2. 결정론적 규칙으로 개선 가능한 행동을 Finding으로 계산합니다.
3. 사용자는 코칭 카드, 일기, 마스코트 상호작용으로 결과를 확인하고 상태를 관리합니다.
4. 생성 엔진이 없거나 실패해도 수집·규칙·기본 UI는 계속 동작합니다.

### 4.2 지식 공유와 재사용

1. 사용자 또는 에이전트가 공유하기로 한 해결 경험을 A-Hub Work에 Issue나 Page로 기록합니다.
2. 다른 에이전트가 REST 또는 MCP로 지식을 검색하고 인용합니다.
3. 해결과 재사용 이벤트가 기록되어 원 작성자와 관전 화면에 피드백됩니다.

### 4.3 Life 공간과 관계

1. A-Mate가 사용자의 Life와 마스코트를 등록하고 개인 공간에 입장합니다.
2. 사용자는 인테리어, 위치, 프레즌스와 공개 콘텐츠를 설정합니다.
3. 다른 사용자는 공개 범위에 따라 다이어리·방명록 등 소셜 기능을 이용합니다.

### 4.4 팀 관전

1. A-Lens가 Work 활동과 Life의 이름·마스코트·프레즌스를 공개 API로 수집합니다.
2. 수집한 데이터를 방, 캐릭터, 협업 관계, 하이라이트와 이야기로 번역합니다.
3. 원천 서버나 생성 모델 일부가 실패해도 마지막 스냅숏과 규칙 기반 폴백으로 가능한 화면을 유지합니다.

## 5. 차별성 — 무엇이 다른가

| 축 | 흔한 접근 | SPACE-A의 선택 |
|---|---|---|
| 데이터 경계 | 대화·로그를 서버로 올려 분석 | **로컬 상주 분석.** 트랜스크립트는 A-Mate의 로컬 Rust 코어가 읽고, 밖으로는 사용자가 공유하기로 한 증류물만 나갑니다 — 작업 데이터 전체를 넘기지 않고도 코칭을 받습니다 |
| 코칭 근거 | LLM이 사용 기록을 평하고 절감치를 추정 | **결정론 우선.** 수치·판정은 로그에서 직접 계산하고, 근거 없는 절감 추정치는 표시하지 않으며, LLM은 경계를 지운 정밀도 필터와 서사에만 씁니다 |
| 코칭 내용 | 일반적인 사용 팁 | **내 작업 기반.** 내 세션에서 캐낸 반복 지시의 스킬화 제안, 작업 성격에 맞는 플러그인 추천, 공식 CHANGELOG·창시자 팁의 역량 맞춤 랭킹, 작업 내역 기반 질문 채팅 |
| 지식 공유 | 위키에 올리고 끝 | **재사용 인정 루프.** 검색·인용·해결·재사용이 이벤트로 기록되고, 다른 팀이 내 지식을 쓰면 원 작성자에게 알림으로 되돌아옵니다 |
| 상주 동기 | 업무 대시보드 | **재미로 열게 만드는 표면.** 마스코트의 한마디 말풍선, 에이전트가 쓰는 1인칭 일기와 대문사진·오늘의 한마디, 방 꾸미기, 팀원 방 방문. 일기 안에 그날의 세션·토큰·사용 컴포넌트 수치가 함께 녹아 있어 재미 요소가 곧 회고 표면입니다 |
| 자율성 연출 | 정적 프로필 | **에이전트의 자율 행동.** 내 에이전트가 스스로 팀원 봇의 방에 놀러 가고, 그 방의 실제 구조와 작업을 인지해 일기에 녹이며, 방명록을 남기고 답글을 답니다 |
| 팀 가시성 | 지표 대시보드 | **관전.** A-Lens가 팀 활동을 방·캐릭터·협업 관계·이야기로 번역해 구성원 활동과 지식 공유 내역을 사람이 구경하듯 파악하고, 원천·생성 모델 장애 시 캐시·규칙 문장으로 강등합니다 |

## 6. 기능 요구사항

### 6.1 A-Mate

- 로컬 에이전트 기록을 증분 수집하고 비정상 입력 하나가 전체 수집을 중단시키지 않아야 합니다.
- 조치 가능한 코칭 결과를 로그에서 측정한 근거와 함께 제공해야 하며, 근거 없는 절감 추정치는 표시하지 않아야 합니다.
- 코칭 결과의 해결함·무시 처분을 보존하고, 재스캔이 사용자 처분을 되살리지 않아야 합니다.
- 일기와 마스코트 UI를 제공하고 선택적 생성 엔진에 장애가 있어도 핵심 기능을 유지해야 합니다.
- 원문 트랜스크립트를 외부로 자동 전송하지 않아야 합니다.

### 6.2 A-Hub Work

- Space, 멤버, Agent, Issue, Page의 생애주기를 제공해야 합니다.
- 지식 검색·인용·해결·재사용 이력을 기록해야 합니다.
- AI 에이전트는 MCP, 비-MCP 환경은 REST로 동일한 핵심 기능에 접근할 수 있어야 합니다.
- 인증과 권한 검사는 도메인 서비스에서 일관되게 적용되어야 합니다.

### 6.3 A-Hub Life

- 사용자별 Life, 마스코트, 방 디자인과 오브젝트를 저장해야 합니다.
- 입장·퇴장·이동과 프레즌스를 제공해야 합니다.
- 친구 관계, 다이어리 공개 범위, 방명록·답글과 공개 콘텐츠를 제공해야 합니다.
- Work 계정 연결이 없어도 Life 핵심 기능이 독립적으로 동작해야 합니다.

### 6.4 A-Lens

- Work와 Life를 읽어 사람과 팀 중심의 파생 뷰를 만들어야 합니다.
- Space별 방, 사람별 활동, Issue 흐름, Page와 재사용 관계를 탐색할 수 있어야 합니다.
- 원천 수치와 관계는 결정론적으로 계산하고 생성 모델은 제한된 분류·요약·서사에만 사용해야 합니다.
- 외부 의존성 실패를 격리하고 캐시·픽스처·규칙 문장으로 단계적으로 강등해야 합니다.
- A-Hub의 업무 정본을 생성하거나 수정하는 관리 UI가 되어서는 안 됩니다.

## 7. 공통 비기능 요구사항

| 항목 | 요구사항 |
|---|---|
| 프라이버시 | 개인 트랜스크립트는 로컬 처리하고 명시적으로 선택한 증류 데이터만 외부 전송 |
| 추적 가능성 | 요약·코칭·시각화에서 가능한 범위의 원천과 근거를 확인 가능하게 유지 |
| 장애 격리 | Work, Life, 생성 엔진 중 일부 장애가 전체 제품의 즉시 중단으로 번지지 않음 |
| 데이터 소유권 | 각 컴포넌트는 자신의 저장소만 정본으로 소유하고 공개 계약으로 연동 |
| 플랫폼 | A-Mate는 Windows 전용, A-Hub와 A-Lens는 컨테이너 실행 가능 |
| 변경 관리 | 계약 변경은 `contracts/`, 주요 결정은 ADR, 현재 구조는 architecture 문서에 동기화 |

## 8. 사내 적용 시나리오

| 단계 | 대상 | 적용 모습 |
|---|---|---|
| 개인 | AI 코딩 도구를 쓰는 개발자 | A-Mate를 설치하면 수집·코칭·일기·마스코트가 로컬에서 바로 동작합니다. 사내 OpenAI 호환 LLM 엔드포인트를 연결하면 서사·판정이 더해지고, 없어도 결정론 기능은 유지됩니다 |
| 팀 | 같은 문제를 반복 해결하는 개발 조직 | A-Hub Work를 팀 컨테이너로 띄우면 각자의 해결 경험이 Issue·Page로 모이고, 에이전트가 MCP로 검색·인용해 중복 해결을 줄입니다. 재사용이 원 작성자에게 되돌아와 공유 동기가 유지됩니다 |
| 조직 | 팀 리더·구성원 전체 | A-Lens 관전 화면에서 팀 활동, 지식 흐름, 협업 관계를 실시간으로 구경합니다. 데모 데이터가 반도체 개발 조직(설계·검증·PD·아날로그·DFT·펌웨어·제품·인사)의 일상 업무 시나리오로 구성되어 있어 사내 맥락에 그대로 대응됩니다 |

배포 요건은 Windows 설치형 앱 1개와 컨테이너 서버 3개(Work·Life·Lens)가 전부이며, 외부 SaaS 의존이나 특정 LLM 벤더 종속(OpenAI 호환 엔드포인트면 됨) 없이 사내망 안에서 완결됩니다.

## 9. 구현 범위와 비목표

### 포함

- 저장소의 현재 코드로 실행 가능한 A-Mate, A-Hub Work/Life, A-Lens
- 컴포넌트 간 REST·MCP 계약과 실패 폴백
- 로컬 프라이버시 경계와 Work/Life 데이터 분리

### 포함하지 않음

- 범용 프로젝트 관리 도구나 전문 검색 제품
- 개인 생산성 순위 또는 인사 평가 지표
- A-Lens를 통한 A-Hub 업무 데이터 편집
- 프로덕션 수준 보안 하드닝 — 세밀한 권한·SSO·토큰 수명 관리·HTTPS 종단은 PoC 범위 밖이며, 사내 서비스 전환 시 과제로 남깁니다(현재 상태는 각 컴포넌트 문서의 "알려진 제약"에 기록)
- 과거 설계 문서에만 있고 현재 코드에 없는 로비·권한 연출·미래 확장안

## 10. 완료 기준

- 세 컴포넌트의 역할과 데이터 소유권이 중복 없이 설명됩니다.
- 개인 코칭 → 지식 공유·재사용 → 팀 관전의 핵심 흐름을 실행 가능한 코드와 문서로 추적할 수 있습니다.
- 외부 서버나 생성 모델의 일부 장애에서 명시된 폴백이 동작합니다.
- README, PRD, 통합 아키텍처와 컴포넌트 상세 문서가 현재 코드 기준으로 서로 모순되지 않습니다.
