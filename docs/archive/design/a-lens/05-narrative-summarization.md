# a-lens — 데이터 번역 파이프라인 (분류·요약·서사)

> 담당: 김주영. 이 문서는 **열린 질문 Q1**([README](README.md#열린-질문))을 확정한다:
> *"서사(요약·스토리)를 누가·언제 생성하나 — 에이전트 기록 시 vs 백엔드 배치 vs 뷰 서버?"*
>
> **결정: 뷰 서버(a-lens backend)에서 a-hub raw를 받아 `분류 → 요약 → 서사` 3단계로
> 번역하고, 콘텐츠 해시로 캐시한다.** 지금 a-lens가 raw를 거의 그대로(`body[:120]`·규칙
> 문장) 싣는 걸, **뷰 서버 안에서 사람이 읽을 분류된 서사로** 바꾼다.

---

## 1. 하고 싶은 것 — 3단계 번역

a-hub에서 받은 데이터를 세 단계로 사람용으로 옮긴다.

```
a-hub raw (Page.title/body, Issue, 활동)
   │
   ├─① 분류 (Categorize)   문서가 어떤 종류인가 — 사람이 알아들을 카테고리 부여
   │                        예: 문제해결 / 설계·스펙 / 분석·결과 / 릴리즈·변경 / 노트·회의 / 가이드
   │
   ├─② 요약 (Humanize)     방대한 본문 → 사람이 읽을 2~3문장
   │
   └─③ 서사 (Narrate)      "누가 무엇을 왜" 한 줄 스토리 (말풍선·하이라이트·피드)
   ▼
a-lens 뷰모델 → 화면 (분류 배지 + 요약 미리보기 + 서사 문장)
```

세 단계 모두 **뷰 서버(a-lens backend)**에서 한다. a-lens는 이미 REST로 받은 데이터를
뷰모델로 **번역**하는 서버(`pipeline.py`)라, 이 번역은 그 연장이다 — **DB 직접조회가 아니라
받은 데이터를 가공**하는 것이라 [a-hub 03 §1](../a-hub/03-architecture.md#1-컴포넌트-경계--가장-큰-함정-두-가지)
경계 원칙과 충돌하지 않는다.

---

## 2. 왜 뷰 서버(a-lens)인가

전제는 **범위가 "화면 표시용"**이라는 것. 에이전트 검색 품질(의미검색·RAG)은 지금 목표가
아니며, 그건 a-hub 소유의 별개 과제다 → [a-hub/10-ingestion-indexing-rag.md](../a-hub/10-ingestion-indexing-rag.md)(미래/선택).

| 후보 (Q1) | 평가 |
|---|---|
| 에이전트 기록 시(로컬) | 에이전트가 분류·요약까지 쓰게 하면 C1 부담↑. 화면 문투·분류 체계를 에이전트가 알 필요 없음 |
| a-hub 백엔드 배치 | a-hub에 LLM·저장을 얹는 큰 공사. 에이전트 검색까지 개선할 때의 길(문서 10). **표시용만이라면 과함** |
| **뷰 서버(a-lens)** ✅ | 번역이 이미 a-lens의 일. 분류·요약·서사는 번역의 세 형태. LLM 비용·환각 리스크는 **서사/분류에만** 존재([03](03-architecture.md#핵심-기술-결정)), 집계·공간 번역은 지금처럼 결정론 |

**유일하게 새로 생기는 것:** a-lens가 **LLM 엔드포인트(C3)의 소비자**가 된다. 지금 a-lens는
LLM 의존이 전혀 없다 — 이 문서가 그 첫 의존을 추가한다(§6).

## 3. ① 분류 (Categorize)

a-hub는 문서를 `authored`/`issue-derived`/`guide`(source)로만 구분한다 — 사람이 화면에서
"무슨 종류 지식인지" 알기엔 부족하다. **사람이 알아들을 카테고리**를 뷰 서버가 부여한다.

### 3.1 카테고리 체계 (초안 — 설정 가능)

공간(팀)과 **직교**하는 축이어야 유용하다("어느 팀이든 문제해결 지식이 이만큼").
더미 데이터(fabless 반도체 8팀의 일상 업무)를 기준으로:

| 카테고리 | 내용 | 예(더미) |
|---|---|---|
| `troubleshoot` 문제해결 | 에러·이슈를 푼 기록 | "합성 QoR 타이밍 위반 해결" |
| `spec` 설계·스펙 | 설계 문서·마이크로아키텍처 | "PMU 마이크로아키텍처 스펙 v1.1" |
| `analysis` 분석·결과 | 측정·QoR·리포트 | "JTAG 브리지 합성 QoR 1차 분석" |
| `release` 릴리즈·변경 | 릴리즈 노트·diff | "MIPI CSI-2 릴리즈 노트 v2.8 diff" |
| `note` 노트·회의 | 메모·회의록·초안 | "ACE 인터페이스 타이밍 노트" |
| `guide` 가이드 | 방 규칙·온보딩 | space 생성 시 seed 가이드 |

### 3.2 분류 방법

- **LLM 제로샷 분류**: 본문/제목을 위 라벨 중 하나로 매핑(요약과 **한 번의 호출**에 합침, §5).
- **규칙 폴백**: LLM 없거나 실패 시 — `issue-derived → troubleshoot`, `guide → guide`,
  그 외 제목 키워드 규칙(diff/릴리즈→`release`, 스펙→`spec`…), 애매하면 `note`.
- **분류는 라벨만**(자유 텍스트 아님) → 화면 그룹핑·필터·집계에 바로 쓴다.

### 3.3 분류로 생기는 화면

| 쓰임 | 화면 |
|---|---|
| 배지 | 지식 카드·모달에 카테고리 칩 |
| 그룹핑 | 방 지식 목록을 카테고리별로 묶기 |
| 집계 | "이 방은 분석·결과가 많다" — 카테고리 분포(공간 번역: 책장 색/구획) |
| 필터·하이라이트 | 카테고리별 필터, 하이라이트 선정 보조 |

> a-hub 문서 10의 `topic_id`(**의미 클러스터링**, 검색용)와 다르다. 여기 분류는 **표시용
> 고정 카테고리**이고 a-lens가 소유한다. 검색용 의미 클러스터가 필요해지면 그건 a-hub 몫.

## 4. ② 요약 · ③ 서사 — 대상 필드

[04-data-mapping.md](04-data-mapping.md)에서 **"서사 (서버 제공)"**으로 표시된 필드가
대상이다(그 문서 지침: *"결정이 바뀌면 서사 행만 재지정"* — 아래가 재지정 결과).

| 뷰모델 필드 | 현재(raw/규칙) | 바뀔 것 | 단계 | 화면 |
|---|---|---|---|---|
| `knowledge[].category` (신규) | 없음 | 카테고리 라벨 | ① | 배지·그룹핑 |
| `knowledge[].summary` | `body[:120]` (collector.py:258) | 본문 2~3문장 요약 | ② | 모달·신착 |
| `agents[].recent_activity` | 규칙 문장 (collector.py:128) | 최근 업무 사람 문투 | ③ | 말풍선 |
| `events[].summary` | f-string (collector.py:291) | 사건 한 줄 서사 | ③ | 하이라이트·피드 |
| `highlight` | 더미/없음 | 선정 사건 서사 | ③ | 게시판·방 카드 |

**번역하지 않는 것:** 수치·카운트·상태·타임라인 라벨은 **집계/공간 번역**이라 그대로 둔다.
LLM은 **문장화·분류까지만**, 수치·사실은 데이터에서만([README 번역 기준](README.md#정체성--뷰어가-아니라-번역기)).

## 5. 어디서·언제 — 문서당 1회, 한 번의 LLM 호출

[03 §핵심 기술 결정](03-architecture.md#핵심-기술-결정)의 원칙을 집행한다:
**"조회 시가 아니라 이벤트 발생 시 1회 생성해 캐시."**

- a-lens는 30초 폴링(`CACHE_TTL`)한다. **폴링마다 재분류·재요약하면 비용 폭발.**
- 요약 대상(page 본문)을 **콘텐츠 해시로 키잉**해 캐시한다. 본문 불변이면 히트 → LLM 0.
  신규·수정 문서만 처리한다. "이벤트 발생 시 1회"를 **콘텐츠 해시 변화 = 이벤트**로 근사
  (허브 이벤트 스트림 부재, [04 G4](04-data-mapping.md#c2에-없는-것-갭-목록)/#40 대기).
- **분류·요약·서사를 한 번의 LLM 호출로** 받는다 → 문서당 1콜(3콜 아님).

```
collector 스냅숏 (30s 폴링) — 각 page 본문 fetch
   ▼
[Translator]  key = (page_id, sha256(body))
   ├─ 캐시 히트 ─────────────▶ {category, summary, narrative} 재사용 (LLM 0)
   └─ 미스 ─▶ C3 LLM 1콜 ─▶ {category, summary, narrative} ─▶ 캐시 저장
                 │ 실패 시
                 └─▶ 폴백: 규칙 분류 + body[:120] — 화면은 절대 안 비운다
   ▼
pipeline 뷰모델 (category·summary·서사 주입)
```

LLM 반환 형식(초안):

```jsonc
{ "category": "troubleshoot",
  "summary":  "PMU ACE 인터페이스에서 발생한 타이밍 위반을 …로 해결했다. (2~3문장)",
  "narrative":"전하린이 PMU 타이밍 문제를 풀어 팀에 공유했어요." }
```

## 6. LLM 의존성 (C3) — a-lens의 첫 LLM 소비

a-hub와 **같은 공용 클러스터**([a-hub 03 §5](../a-hub/03-architecture.md#5-공용-인프라--rtx-5070-클러스터))를
OpenAI 호환 엔드포인트로 소비한다. a-lens는 소유하지 않고 **주소만 안다.**

| env (A_LENS_ 접두) | 용도 | 기본 |
|---|---|---|
| `A_LENS_LLM_URL` | OpenAI 호환 base URL(LiteLLM 게이트웨이) | 없음 → 번역 비활성(규칙 폴백만) |
| `A_LENS_LLM_MODEL` | 모델명 | `space-a-narrate`(신규 용도명) |
| `A_LENS_LLM_KEY` | 게이트웨이 키 | 없으면 생략 |

- **용도별 모델명 분리**([a-hub 03 §5.2](../a-hub/03-architecture.md#52-클러스터-구성--litellm--ollama)):
  `space-a-ingest`·`space-a-coach`와 겹치지 않게 `space-a-narrate` — Pillar 간 GPU 경쟁 통제.
- **env 미설정이면 번역은 꺼지고** 현행 규칙(`body[:120]`+규칙 분류)로 동작 — a-lens는
  설정 없이도 뜬다는 원칙([a-lens/CLAUDE.md](../../../../a-lens/CLAUDE.md)) 유지.
- 프롬프트 개요: *"다음 지식 문서를 (a) 카테고리 1개로 분류, (b) 팀 관전용 2~3문장 요약,
  (c) 한 줄 서사로. 수치·고유명사는 본문에 있는 것만. 없는 사실 지어내기 금지. JSON으로."*

## 7. 폴백·안전장치

| 리스크 | 대응 |
|---|---|
| LLM 실패/타임아웃 | **폴백 = 규칙 분류 + `body[:120]`.** 화면은 절대 안 비운다(`_DEGRADE` 철학) |
| 환각(없는 수치·사실) | "본문에 있는 것만" 강제. 수치·카운트는 애초에 번역 대상 아님(집계 담당) |
| 오분류 | 라벨 폐쇄 집합(§3.1) + 애매하면 `note`. 카테고리는 표시 보조라 오분류의 피해가 낮음 |
| 개인 감시로 읽힘 | 서사도 **팀 단위** 원칙 — 개인 랭킹·개인 토큰량 문장화 금지([README](README.md#북극성-지표)) |
| 지연(폴링 블로킹) | 캐시 미스에서만 LLM. 실패 시 즉시 폴백. 필요 시 비동기로 돌려 다음 폴링 반영 |
| 비용 | 콘텐츠 해시 캐시로 신규/변경분만. 로컬 클러스터라 과금 0 |

## 8. 권한·tier

번역은 **이미 tier 트리밍된 데이터 위에서** 돈다 — collector가 게스트 응답에서 이슈를
제거하고, 로비는 `visibility:'space'` 문서를 미노출한다([04 게스트 트리밍](04-data-mapping.md#게스트유리벽-트리밍--서버-몫)).

- 로비/게스트 노출 번역은 **org-safe 데이터에서만** 생성(추가 유출 경로 없음).
- 캐시 키에 tier를 섞지 않는다 — 번역은 콘텐츠 기반이고 **노출 여부는 상위(collector
  트리밍)가 거른다.** 트리밍은 번역 이후가 아니라 **원천 선별 단계**에서 유지(현행 동일).

---

## 9. 배치 — collector vs pipeline

- **collector**: 본문을 가져오는 지점이라 **번역 주입도 여기서**(summary/category를 채우는
  자리 — collector.py:258·291). Translator는 별도 모듈(`alens/translator.py` 신설 제안)로
  두어 원천 로직과 분리.
- **pipeline**: 결정론 번역(하이라이트 랭킹 등)만 유지 — category별 그룹핑·집계는 여기서
  결정론으로 처리(라벨은 이미 채워져 들어옴).
- **원천별**: 허브 실데이터는 번역, 더미는 파일 요약을 그대로 통과(재번역 불필요).

---

## 10. 비목표

- **의미 검색·벡터·임베딩·RAG 아님.** 표현 다른 유사 문서 찾기는 에이전트(C1)/a-hub 몫
  → [a-hub/10](../a-hub/10-ingestion-indexing-rag.md). a-lens는 **표시할 것을 분류·요약**할 뿐.
- **인덱스 구축 아님.** a-lens는 자체 지식 저장소를 안 만든다(정본은 a-hub). 캐시는 번역
  결과 캐시일 뿐 색인이 아니다.
- **프론트 변경 최소.** 프론트는 기존 필드에 `category` 소비만 추가 — 값 품질이 오른다.

## 11. 단계

| 단계 | 내용 | 결과 |
|---|---|---|
| **P0** | `translator.py` 스캐폴딩 + 콘텐츠 해시 캐시 + 규칙 분류/폴백. LLM 미연결 | 구조·규칙 분류 배지가 뜸, 요약은 현행 |
| **P1** | C3 연결(`A_LENS_LLM_*`), 1콜로 `category`+`summary`를 LLM 결과로 | **지식이 분류 배지 + 사람 요약으로 표시 — 요청의 직접 해결** |
| **P2** | `recent_activity`·`events[].summary`·`highlight`까지 서사 확장 + 카테고리 그룹핑/집계 화면 | 말풍선·피드·하이라이트·분류 대시보드 |

> **P1이 요청("raw를 분류·요약해 서사 있게")의 최소 해결선.**
