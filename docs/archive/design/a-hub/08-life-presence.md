# Space A Hub — 라이프 상주(Presence) 설계

> 담당: 허준녕
> 에이전트가 항상 어느 방에 "있는" 상태를 1급 개념으로 도입한다.

## 1. 컨셉

에이전트는 체크인한 방에 상주한다. 다른 방의 활동을 하려면 그 방에 입장해야 하고,
퇴장 전까지는 그 방에 있는 것으로 취급된다.

| 얻는 것 | 내용 |
|---|---|
| 시각화 | "지금 누가 이 방에 있나"가 상태 조회로 끝남 — 별도 체크 로직 불필요 |
| 기록 기본값 | 기록 대상 방을 호출자가 매번 지정하지 않아도 됨 (§4) |
| 검색 맥락 | 현재 방 지식을 우선 노출 (§3) |
| 재미 요소 | 방문·말풍선·강제소환 등 시각화 이벤트의 기반 |

## 2. Presence 상태

- **휘발성 상태다.** 지식 데이터와 분리 저장하고, 서버 재시작 시 날아가도 무방
- `check_in(space_id)` / `check_out()` 툴로 명시 전환
- **하트비트 TTL 병행** — 에이전트는 프로세스라 퇴장 없이 죽는다.
  마지막 활동 후 TTL 경과 시 자동 체크아웃 (TTL 값은 미결, §7)
- 체크인은 소속 여부와 무관하게 허용 — 비멤버는 **게스트**로 입장한다.
  게스트가 볼 수 있는 것은 기존 유리벽 규칙이 이미 깎아준다 (§5)

## 3. 핵심 원칙 — Presence는 세 가지만 만진다

> **권한 계산 함수 `f(토큰의 소속, 문서 visibility)`에 presence는 등장하지 않는다.**

| Presence가 만지는 것 | 만지지 않는 것 |
|---|---|
| 기본값 — 기록 대상 방 (§4) | 열람 가능 여부 (권한) |
| 랭킹 — 검색에서 현재 방 부스트 (§5) | 검색 후보 풀의 범위 |
| 렌더링 — 아바타 위치, 방문 이벤트 | 쓰기 자격 (소속이 결정) |

이 원칙이 막는 실패 모드 두 가지:

- **과잉 허용** — "방에 있으니 그 방 데이터를 준다"가 되면, 체크인 한 번으로
  유리벽을 우회한다. "MCP 검색 범위 = UI 열람 범위" 규칙([05 §2](05-contracts.md#2-권한-모델--하나의-모델-두-개의-경로)) 위반
- **과잉 차단** — "방에 들어가야만 그 방 데이터를 검색할 수 있다"가 되면,
  원래 볼 권리가 있는 전사(org) 지식을 찾으러 방을 순회해야 한다.
  답이 어느 방에 있는지는 검색 전엔 모른다 — 지식 순환이 죽는다

## 4. 쓰기 규칙

읽기와 쓰기는 비대칭이다: **읽기는 부스트만, 쓰기는 presence가 기본값이되 불일치는 거부.**

| 규칙 | 이유 |
|---|---|
| `open_issue`의 기록 대상 기본값 = **현재 방** | space_id 파라미터 실수 제거 |
| 쓰기는 **입장 + 소속** 둘 다 요구 — 게스트는 기록 불가 | 입장 ≠ 자격 |
| 명시 `space_id`가 현재 방과 다르면 **조용히 넘기지 않고 에러** | 에이전트가 "다른 방에 있음"을 인지하게 강제. 엉뚱한 방 기록 = 데이터 오염 + 정보 유출 |
| `resolve_issue`·`cite_knowledge`는 현재 방이 아니라 **이슈가 열린 방**을 따른다 | open과 resolve 사이에 방을 옮겨도 기록이 찢어지지 않음 |

## 5. 읽기(검색) 규칙

- 검색 후보 풀은 presence와 무관하게 **전사 공개(org) + 내 소속 방** — 항상 동일
- 현재 방의 문서는 **랭킹 부스트**로 우선 노출 (부스트돼도 권한 필터는 그대로)
- "이 방만 검색" 은 명시 옵션으로 별도 제공
- 검색 정렬 가중 상세: [07-search-design.md §3](07-search-design.md#3-질의-파이프라인)

## 6. 비밀 데이터 보호 — presence 밖의 문제

남의 방 `space` 문서는 후보 풀에 없으므로 presence로는 접근 불가.
다만 결과 목록에서 빼는 것으로는 부족하며, 아래는 검색·배치 구현이 지킬 경계다:

- **사전 필터** — visibility/space 필터를 BM25·벡터 **질의 시점**에 건다.
  후보를 뽑은 뒤 걸러내면 에이전틱 루프의 로컬 LLM이 판정 과정에서 이미 읽은 뒤다
- **파생물 경계** — 심야 압축은 visibility 경계 안에서만 병합한다
  (`space` 문서끼리는 `space` Best Practice로). 통계·활동 요약도 동일
- **루프 로그** — 다회 시도의 중간 컨텍스트는 문서 원문과 같은 민감도로 취급

## 7. 계약 영향과 미결

| 항목 | 내용 |
|---|---|
| C1 | `check_in` / `check_out` 툴 추가 — **추가만이라 기존 소비자 안 깨짐** |
| C2 | 방 상세에 presence 필드(또는 별도 조회) 추가 — 시각화 담당과 응답 형태 협의 |
| 미결 | 강제소환(주인 호출) 등 재미 요소의 이벤트 규격 |

## 8. 추신 — life 서버 쪽 프레즌스는 별도로 먼저 들어갔다 (2026-07-30)

이 문서는 **work 공간의 check_in/check_out**(MCP) 프레즌스 설계다. 그와 별개로 **life 서버**
(방 방문)에는 접속 신선도가 먼저 필요해져 구현됐다 — `agents.last_seen`. 규격은
[life-visit.md §4 프레즌스](specs/life-visit.md)에 있다.

계기: a-lens가 온라인/오프라인을 **"마지막 허브 write(page·issue)가 1시간 안인가"** 로 판정하고
있었다. a-mate의 write는 사람당 하루 1~3건이고 전부 자정 직후에 몰려서, 하루 23시간이 오프라인이고
정작 켜지는 1시간은 새벽이었다. 즉 신호가 반대로 켜졌다.

§2의 **"에이전트는 프로세스라 퇴장 없이 죽는다 → 하트비트 TTL 병행"** 이 정확한 진단이었고,
§7에서 미결로 남았던 **TTL 값**은 life 쪽에서 다음과 같이 결론이 났다 — 위 미결 목록에서 지웠다.

| 결정 | 내용 |
|---|---|
| 서버가 TTL로 자동 체크아웃하지 **않는다** | 적정 창 크기는 화면 성격에 달렸고 서버는 그걸 모른다. 서버는 `last_seen`(관측 사실)만 주고 판정은 소비자가 한다 |
| 창은 소비자 설정 | a-lens `A_LENS_PRESENCE_WINDOW`, 기본 3600초 |
| 전용 하트비트 엔드포인트 없음 | a-mate가 이미 스캔마다 인증 호출(방문·방명록 폴링)을 하므로, `_authed()`에서 시각만 남기면 된다. 클라이언트 변경 0 |

**work 쪽에 check_in/check_out을 넣을 때도 같은 규율을 쓰는 게 맞다** — 서버가 상태를 만료시키는
대신 마지막 활동 시각을 노출하고, 창은 소비자가 정한다. 그러면 "TTL이 짧아서 일하는 사람이
사라진다 / 길어서 퇴근한 사람이 남아 있다"를 서버 배포 없이 조정할 수 있다.

⚠️ 현재 life의 `last_seen`이 답하는 것은 **"a-mate 앱이 켜져 있나"** 까지다. a-mate는 실행 중이면
작업 여부와 무관하게 폴링하므로, "실제로 코딩 중"(`working` vs `idle`의 본래 의미)은 아직 신호가
없다. 그건 a-mate가 활동 여부를 페이로드에 실어야 하고 — 연속 활동 브로드캐스트라 별도 옵트인이
필요하다 — 미착수다.
