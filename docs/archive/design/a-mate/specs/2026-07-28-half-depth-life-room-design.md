# 싸이월드형 반깊이 Life 방 전환 설계

- 상태: 구현 완료
- 날짜: 2026-07-28
- 범위: `a-mate` Life 렌더러·인테리어 편집기, `a-hub/life` 좌표 검증·저장 데이터 정리

## 1. 목표

현재 방은 20×20 전체를 아이소메트릭으로 투영한 완전한 마름모다. 이를 옛 싸이월드 미니룸처럼 다음 구조로 바꾼다.

- 화면 위쪽은 좌·우 벽이 여백 없이 전부 채운다.
- 바닥은 뒤쪽 코너에서 시작해 화면 좌우로 넓어지며, 기존 마름모의 앞쪽 절반은 사용하지 않는다.
- 방 뷰 자체의 세로 높이를 크게 줄여 기본 창에서 가로로 넓은 미니룸처럼 보이게 한다.
- 좌표 번호와 20×20 계약은 유지한다.
- 새 바닥에서 사라지는 좌표의 가구는 제거해도 된다.
- 사라지는 좌표에 있던 봇은 서버가 유효한 빈 좌표로 옮긴다.

## 2. 핵심 결정

### 2.1 논리 격자는 20×20 유지

`grid.w=20`, `grid.h=20`은 바꾸지 않는다. 대신 바닥 셀의 유효 조건을 추가한다.

```text
0 <= x < 20
0 <= y < 20
x + y < 20
```

따라서 유효 바닥은 20×20 정사각형의 뒤쪽 절반인 삼각형이며 210셀이다.

```text
뒤 코너
                      (0,0)
                        ◆
                      ◆ ◆
                    ◆ ◆ ◆
                  · · · · ·
        (0,19) ◆ ◆ ◆ ◆ ◆ ◆ ◆ (19,0)
                ── 앞쪽 절단선 ──

        x+y >= 20인 기존 좌표는 비활성
```

20×10 직사각형으로 바꾸지 않는 이유:

- 기존 좌표의 의미와 벽 길이를 유지할 수 있다.
- north·west 벽을 각각 20셀 그대로 쓸 수 있어 기존 창문 데이터가 보존된다.
- 기존 아이소메트릭 식 `screenX=(x-y)×TW/2`, `screenY=(x+y)×TH/2`를 유지한다.
- 화면 결과가 첨부 예시의 뒤 코너에서 양옆으로 펼쳐지는 바닥과 일치한다.

### 2.2 화면 뷰포트

현재 투영 상수 `TW=28`, `TH=14`, `OX=450`, `OY=140`, `WALL=110`은 유지한다. 좌표와 에셋 배율을 흔들지 않기 위해서다.

권장 뷰포트:

```text
VIEW_X = 170
VIEW_Y = 30
VIEW_W = 560
VIEW_H = 257
scene aspect-ratio = 560 / 257
```

현재 `580/420`에서 약 `2.18:1`의 가로형 화면으로 바뀐다. 유효 셀의 마지막 타일이 화면 아래 경계에 닿아 별도 바닥 여백이 생기지 않는다.

### 2.3 벽은 화면 상단 전체를 채움

현재 벽은 바닥 변을 위로 평행 이동한 두 사각형이라 상단 좌우에 배경 여백이 남는다. 새 벽은 화면 상단 모서리까지 직접 연결한다.

```text
┌───────────────────┬───────────────────┐  VIEW_Y
│      west 벽      │      north 벽     │
│                   │                   │
│                  뒤 코너              │
│                ╱         ╲            │
│             ╱               ╲         │
└───────────╱────── 바닥 ───────╲───────┘
```

- west 벽: `[(VIEW_X,VIEW_Y), (OX,VIEW_Y), a, d]`
- north 벽: `[(OX,VIEW_Y), (VIEW_X+VIEW_W,VIEW_Y), b, a]`
- 두 벽의 경계는 `(OX,VIEW_Y) → a` 수직선이다.
- 창문은 기존 north·west 벽과 20셀 인덱스를 유지한다.
- 창문 클릭 영역은 각 벽 셀의 바닥 경계에서 화면 상단 방향으로 세운 사각형으로 바꾼다.

## 3. 화면 구성

```text
┌─────────────────────────────────────────────┐
│ ⚙                                           │
│                 벽 모서리                   │
│                   │                         │
│                  ╱╲                         │
│              창문  창문                     │
│                ╱    ╲                       │
│             가구   봇   가구                │
│──────────── 유효 바닥의 앞 경계 ────────────│
└─────────────────────────────────────────────┘
```

- 방 뷰는 컨테이너 좌우·상단·하단에 내부 캔버스 여백을 두지 않는다.
- 방 뷰 외곽은 둥글게 자르거나 별도 테두리를 두지 않는다.
- 벽 폴리곤에는 외곽선을 두르지 않고 중앙 모서리와 벽·바닥 경계만 화면 기준 1px 구조선으로 한 번씩 그린다.
- 설정 버튼은 현재처럼 방 뷰 좌측 상단에 오버레이한다.
- 바닥은 유효 셀과 절단선 바깥의 시각 보충 타일 한 줄을 함께 렌더한 뒤 뷰 경계에서 자른다.
- 시각 보충 타일은 잘린 경계와 양끝 모서리의 빈 삼각형을 채우기 위한 표현 전용이며 클릭·배치 대상으로 사용하지 않는다.
- 에이전트 스프라이트는 새 장면 높이에서 찌그러지지 않도록 퍼센트 높이를 재계산하거나 `aspect-ratio:1`로 고정한다.
- 가구의 가로 배율은 기존 월드 좌표 기준을 유지한다.

## 4. 서버 계약

### 4.1 프로토콜 4

단순 `grid:20×20`만으로는 삼각 바닥을 표현할 수 없으므로 capabilities를 명시적으로 확장한다.

```json
{
  "life_protocol": 4,
  "grid": { "w": 20, "h": 20 },
  "floor": {
    "shape": "half-depth",
    "max_xy_exclusive": 20
  },
  "footprint_mask": true,
  "wall_objects": true
}
```

클라이언트는 `life_protocol=4`와 `floor.max_xy_exclusive=20`을 확인한 뒤 편집 저장을 허용한다.

### 4.2 단일 유효성 함수

서버에 다음 함수를 두고 이동·입장·가구·스폰·마이그레이션이 모두 공유한다.

```python
def _is_floor_cell(cell):
    x, y = cell
    return 0 <= x < GRID_W and 0 <= y < GRID_H and x + y < FLOOR_DEPTH
```

- `move`: 목표 셀이 비활성이면 `invalid_request`
- `enter(cell 지정)`: 비활성 셀이면 `invalid_request`
- 자동 입장·등록: 유효 셀만 후보로 사용
- 가구: 점유 셀 전체가 유효해야 저장 허용
- 창문: floor mask와 무관하며 기존 벽 범위 검증 유지

## 5. 기존 데이터 마이그레이션

DB 스키마는 바꾸지 않는다. Life Server가 저장 데이터를 로드한 직후 전역 락 밖에서 서비스 시작 전 한 번 정리하고, 변경된 행만 다시 저장한다.

### 5.1 가구

- 창문은 유지한다.
- 바닥 가구는 `occupied_cells()` 중 하나라도 새 유효 바닥 밖이면 해당 객체 전체를 제거한다.
- 남은 가구의 좌표는 이동시키지 않는다.
- 방별로 제거 후 `save_design(life)`를 한 번만 호출한다.

부분만 남기는 대신 객체 전체를 제거하는 이유는 footprint와 스프라이트 기준점이 분리되면 화면·충돌이 어긋나기 때문이다.

### 5.2 봇

방별로 다음 순서로 처리한다.

1. 남은 가구 점유 셀을 계산한다.
2. 유효 좌표에 있고 가구와 겹치지 않는 봇은 유지한다.
3. 비활성 좌표·제거된 가구 좌표·중복 좌표의 봇을 `agent_id` 정렬 순서로 재배치한다.
4. 재배치 후보는 새 유효 바닥만 사용한다.
5. 각 이동을 `save_agent(agent)`로 영속화한다.

권장 스폰 앵커:

```text
SPAWN_X = 9
SPAWN_Y = 9
```

`x+y=18`이라 앞쪽 경계 근처 중앙에 보이며, 기존 거리 버퍼 3→2 폴백과 에이전트별 SHA-256 타이브레이크는 유지한다.

### 5.3 원자성과 재실행 안전성

- 서비스가 API 요청을 받기 전에 마이그레이션을 끝낸다.
- 마이그레이션은 유효 데이터에 다시 실행해도 변화가 없는 멱등 처리다.
- 볼륨과 토큰, 방 ID, 테마, 유효 영역의 가구는 유지한다.
- 별도 DB migration version 컬럼은 필요하지 않다. 유효성 검사 자체가 완료 여부다.

## 6. 클라이언트 기하 변경

`geometry.ts`에 서버와 같은 바닥 규칙을 둔다.

```ts
export const LIFE_FLOOR = { maxXYExclusive: 20 } as const;
export const isFloorCell = ([x,y]) =>
  x >= 0 && y >= 0 && x < 20 && y < 20 && x + y < 20;
```

다음 함수가 이 규칙을 사용해야 한다.

- `isInsideLife`: 객체 점유 셀 전체 검사
- `placementOrigin`: 앞 경계에서 큰 가구를 놓을 때 유효한 가장 가까운 원점으로 뒤쪽 보정
- `rotatedOrigin`: 회전 후 전체 footprint가 유효한 가장 가까운 원점 선택
- LifeView 타일 렌더·hover·click
- ghost와 placed-cell 표시

원점 보정은 축별 단순 clamp 대신 가능한 모든 원점 중 다음 정렬로 고른다.

```text
1. 목표 원점과의 Manhattan 거리
2. 목표 원점과의 Chebyshev 거리
3. y
4. x
```

20×20에서 최대 400후보라 hover 중에도 충분히 작고, 복잡한 footprint와 회전에 같은 규칙을 적용할 수 있다.

## 7. 렌더 순서

1. 화면 전체를 채우는 west·north 벽
2. 유효 바닥 삼각형 base
3. 유효 셀 타일
4. 편집 중 점유 셀·ghost
5. 창문
6. 일반 가구
7. 봇·말풍선·이름
8. 설정 버튼·가구 메뉴

기존 `z=20+round((groundX+groundY)×10)`은 유효 영역에서도 그대로 쓸 수 있다.

## 8. 구현 순서

1. 프로토콜 4와 공용 바닥 유효성 함수 추가
2. 서버 이동·입장·스폰·디자인 검증 전환
3. 서버 시작 시 가구 제거·봇 재배치 마이그레이션
4. 서버 단위 테스트와 SQLite 재시작 테스트
5. 클라이언트 geometry와 테스트 전환
6. LifeView 벽·바닥·뷰포트 렌더 전환
7. 인테리어 배치·회전·창문 수동 검증
8. 실제 로컬 SQLite 복사본으로 서버 재시작 후 데이터 정리 결과 검증

## 9. 필수 검증

### 서버

- `x+y=19` 이동 성공, `x+y=20` 이동 거절
- 자동 스폰된 모든 봇이 유효 셀
- 경계에 걸친 가구 저장 거절
- 기존 DB 로드 시 경계 밖 가구만 제거
- 기존 DB 로드 시 경계 밖 봇을 서로 겹치지 않게 이동
- 창문 데이터 보존
- 마이그레이션을 두 번 실행해 두 번째에는 변경 없음

### 클라이언트

- 방 뷰 네 변에 캔버스 여백 없음
- 상단 전체가 벽으로 채워짐
- 바닥 앞 절반이 보이지 않고 클릭되지 않음
- 앞 경계에서 큰 가구 ghost가 유효 영역 안으로 보정됨
- 4방향 회전 후 footprint가 유효 영역을 벗어나지 않음
- 봇·가구 스프라이트 종횡비 유지
- 기본 창과 확대 창에서 동일 좌표가 동일 위치에 표시됨

## 10. 제외

- 20×20 좌표 번호 재매핑
- 기존 가구를 자동으로 안쪽으로 옮기는 기능
- 창문 좌표 마이그레이션
- 서버 DB 스키마 변경
- 에셋 자체의 크기·방향 보정

## 11. 후속 결정

이 제안을 확정해 구현할 때 프로토콜 4, 삼각 바닥 mask, 파괴적 가구 정리 정책을 ADR로 채택한다. 채택 전에는 서버 데이터에 마이그레이션을 실행하지 않는다.
