## 2. 확정된 결정

### 2.1 세 분류

`CoachKind = 'coaching' | 'learning' | 'news'` — 항목에서 순수 함수로 유도한다.

| 분류 | 재료 | 카드 문법 | 좌측 라인 |
|------|------|-----------|-----------|
| **코칭** | 룰 finding(R6·R7·R8) + `personal` 태그 레슨 | A (로그 카드) | `--pastel-mint` |
| **학습** | 커리큘럼 팁(`dimension`) + Boris + 팀 지식 | B (카드뉴스) | `--pastel-lav` |
| **소식** | `changelog`·`kind='news'` + 로컬 공지(⑥) | B (카드뉴스) | `--accent` |

- **카드 문법은 PR②의 2종을 그대로 유지한다.** 코칭 카드는 근거·행동·처분 버튼이 필요하고 소식 카드는 전문 링크가 주 CTA라 담을 것이 근본적으로 다르다. 통합하면 「전문 보기」가 각주 링크와 같은 위계로 내려가 약해진다.
  - **⑥ 이후 문법 B의 슬롯이 셋 늘었다**(아카이브된 unification 스펙 §4.2 표에는 없다): ①**📊 근거 줄**(`personal` — 문법 A와 같은 슬롯) ②**기한 칩** `⏳ MM-DD까지` ③고정 슬롯의 **`[확인]` 버튼**. ①은 `coachTip`(🤖 맞춤 코칭 한 줄)을 폐지하면서 배움 카드에서 개인화가 통째로 사라지는 것을 막으려고 넣었다 — 두 문법이 "근거 → 내용"으로 수렴한다. ②③은 §6.4 고정 슬롯 전용이다. 단일 스트림에서 문법 B를 다시 정리할 때 이 셋을 슬롯 표에 반영할 것.
- **배지는 분류 이름 3종으로 고정하고, 세부 출처는 보조 칩으로 남긴다** (§4.1 확정). 현행 `toLearnCardView`의 배지 한 칸이 7종(공지/소식/Boris/팀/축 라벨 5종/배움)을 다 짊어지고 있어 3종으로 줄이면 축 라벨과 「공지」가 갈 곳을 잃는다. 슬롯을 둘로 가른다:

  | 재료 | 분류 배지 | 보조 칩 |
  |------|-----------|---------|
  | `notice` 태그 (긴급 안내) | 소식 | **공지** |
  | `changelog` · `kind='news'` | 소식 | — |
  | `boris` 태그 | 학습 | **Boris** |
  | `team` 태그 | 학습 | **팀** |
  | `dimension` 있음 | 학습 | **`DIM_LABEL[dimension]`** (「워크플로 자동화」 등) |
  | 그 밖의 콘텐츠 | 학습 | — |
  | 룰 finding · `personal` 레슨 | 코칭 | — |

  - 보조 칩은 **있을 때만** 렌더한다. 현행 폴백 `'배움'`은 분류 배지와 겹치므로 **버린다** — 칩이 없는 것이 곧 "특별한 출처가 없음"이다.
  - 칩은 톤다운(작은 글씨·`--ink-soft`)이라 분류 배지와 위계가 갈린다. **축 라벨을 살리는 것이 이 결정의 목적**이다 — Boris·팀은 본문 끝에 출처가 이미 있지만 축 라벨은 본문 어디에도 없어 버리면 역량 사다리 진행이 화면에서 완전히 사라진다.
- **라인 색이 분류를 뜻하므로 severity를 색으로 쓸 수 없다.** severity는 이미 아이콘(⚠/💡/ℹ)이 나타내므로 `LogCard`의 `.card.warn`(coral)을 제거한다.

### 2.2 정렬 — 전체 `first_seen` 내림차순, 상한도 같은 축으로

분류와 무관하게 한 줄로 깐다. 행동 가능한 코칭 카드가 소식 아래로 밀릴 수 있음을 **의도적으로 수용한다**(요청 사항).

> **⚠ 후속 (2026-08-03): 상한 자체를 폐지했다.** 아래 결정은 구현 뒤 실환경 스모크에서 뒤집혔다 — 근거는 §4.2의 후속 각주. 지금 코드에는 카드 상한이 없다.

**카드 상한은 6을 유지하되 자르는 축을 score에서 `first_seen`으로 바꾼다** (§4.2 확정). 현행 `partitionCoachItems`는 score 내림차순 배열을 그대로 받아 `slice(0, 6)` 하는데, 정렬이 시간순이 되면 **자르는 축과 보여주는 축이 어긋난다** — "스트림 맨 위가 1시간 전인데 30분 전 항목은 어디에도 없다"가 실제로 가능해진다. 백엔드가 `score >= 0`으로 이미 걸러 보내므로(§3.7) 시간 기준으로 잘라도 쓸모없는 항목이 올라오지 않는다.

파이프라인 순서 — **이 순서를 지켜야 한다**:

```
tips = listContent(false)              // 백엔드가 준 score 내림차순
  ↓
pinned = pinnedNewsItem(tips, …)       // ⚠ score 순 배열을 그대로 넘긴다 (아래 주의)
  ↓
tips 에서 pinned 제외
  ↓
first_seen 내림차순 정렬 → slice(0, CONTENT_CARD_LIMIT)   // ← 상한은 여기 한 곳
  ↓
룰 finding(상한 없음)과 합쳐 다시 first_seen 내림차순 → 스트림
```

- **⚠ `pinnedNewsItem`은 score 순 배열을 전제한다** — 주석이 "`items`는 점수 내림차순이므로 첫 후보가 곧 우선순위 1위"라고 못박고 있다. 시간순으로 재정렬한 배열을 넘기면 고정 슬롯이 `priority` 대신 최신순으로 뽑혀 ⑥ §6.4의 우선순위 규칙이 조용히 깨진다. **정렬은 고정 항목을 빼낸 뒤에 한다.**
- 상한은 **콘텐츠에만** 걸린다. 룰 finding은 지금도 대상이 아니고 그대로 둔다(보통 R6·R7·R8 몇 건).
- *수용하는 대가*: 고득점 커리큘럼 팁이라도 오래되면 상한 밖으로 밀린다. `first_seen`이 오래됐다는 것은 이미 여러 번 노출됐다는 뜻이라 받아들인다.

### 2.3 탭 배지 = 안 본 개수 — **시각이 아니라 활성 키 집합으로 센다**

```
unseen = activeKeys.filter(k => !seenActiveKeys.has(k)).length
```

**`first_seen > lastCoachSeenAt` 방식은 채택하지 않는다** (§4.5 확정). `first_seen`은 삽입 시각이지 활성화 시각이 아니라 `pending`→`new`와 재발 복귀(`resolved`→`new`)를 둘 다 놓치기 때문이다(§3.1). 그 두 전이야말로 "카드가 새로 보이기 시작하는" 순간이다.

- `seenActiveKeys` = **마지막으로 코칭 탭을 봤을 때 활성이던 카드 키 집합**. localStorage 영속.
- 키는 처분 줄과 같은 네임스페이스 규약을 쓴다 — `finding:<dedup_key>` / `content:<id>`. `dedup_key`와 콘텐츠 `id`는 다른 이름공간이라 접두사 없이 합치면 충돌할 수 있다.
- **두 전이가 공짜로 잡힌다**: `pending`·`rejected` 카드는 화면에 없고(fail-safe 침묵) `resolved`·`dismissed` 카드는 처분 줄에 있을 뿐 활성이 아니다 → 둘 다 저장 시점의 집합에 **없다** → `new`로 올라오는 순간 `unseen`에 잡힌다. **Rust 변경이 필요 없다.**
- **`first_seen`은 정렬·상한 전용이 된다.** A(#161)가 한 일은 §2.2에서 그대로 값을 한다.
- 저장은 **현재 활성 키 전부로 덮어쓴다**(누적이 아니다). 처분·프룬으로 사라진 키는 자연히 빠지므로 집합이 무한히 자라지 않는다 — 별도 상한이 필요 없다.
- 갱신 시점은 **코칭 탭이 보이는 동안 목록이 바뀔 때마다**. 탭을 연 채로 새 카드가 도착하면 사용자가 이미 보고 있으므로 즉시 본 것으로 친다.
- **수명이 끝난 공지는 활성 집합에서 뺀다**(§2.6) — 화면에 영영 안 보이는 카드를 세면 탭을 열어도 배지가 사라지지 않는다. 상한과 달리 수명은 "나중에 올라올" 여지가 없다.
- 그 밖에는 **상한(§2.2)을 적용하기 전의 활성 항목 전부**다. 고정 슬롯 항목도 자연히 들어간다(그것도 `status='new'`이므로). 상한 밖으로 밀린 항목까지 "봤다"고 치는 셈인데, 화면에 보이는 것만 세려면 고정 슬롯 판정(`pinAcks`·`today`)을 배지 계산부로 끌어와야 해서 배보다 배꼽이 커진다. 잃는 것도 작다 — 나중에 상한 안으로 올라와도 배지에 한 번 안 잡힐 뿐이다.
- 처분 줄은 정의상 활성이 아니라 `unseen`에 섞이지 않는다 — ③이 지키라고 한 성질(§4.3)이 구조로 보장된다.
- 첫 실행이면 집합이 비어 있어 모든 활성 카드가 `unseen`이다. 처음 보는 것이 맞다.

처분하지 않아도 배지가 사라진다는 성질은 그대로다(현행 「미처리 개수」와 의미가 바뀐다). 다이어리·방명록 배지가 이미 "본 것은 안 센다"를 쓰고 있다.

### 2.4 홈 「지금 볼 코칭」 위젯 — 세 분류 모두

뷰모델에 `kind`와 `oneLine`을 더한다.

| 분류 | `oneLine` |
|------|-----------|
| 코칭 (finding) | `suggested_action` |
| 코칭 (레슨) | `splitLessonBody().action`, 없으면 `title` |
| 학습 · 소식 | `title` |

위젯 행에도 분류 배지·라인 색을 넣어 탭과 같은 시각 언어를 쓴다.

### 2.5 스트림 밖의 두 칸 — 위에 고정 슬롯, 아래에 처분 줄

"한 줄 스트림"은 **활성 카드에 대한 규칙**이다. 그 위아래로 성격이 다른 칸이 하나씩 붙는다.

```
┌─────────────────────────────────────┐
│ ⏳ 8/5까지  [점검] 로그인 지연  [확인]│ ← 고정 슬롯 (최대 1건, §4.4)
├─────────────────────────────────────┤
│ ┃코칭  같은 지시를 3개 세션에서…  2분 전│
│ ┃소식  Claude Code 새 릴리스…   1시간 전│ ← 스트림 (first_seen 내림차순)
│ ┃학습 [워크플로 자동화] hooks로…    어제│
├─────────────────────────────────────┤
│ ✔ 해결함  큰 MCP 결과가…      실행취소│ ← 처분 줄 (§4.3)
│ ◷ 무시    이 프로젝트, 가벼운… 실행취소│
└─────────────────────────────────────┘
```

**고정 슬롯은 스트림 위 별도 칸으로 유지한다** (§4.4 확정). 정렬에 편입하지 않는다 — 편입하면 편입된 카드에게 「강등」이란 곧 제자리이고 그 자리는 `first_seen`이 정하므로, **기한 경과 자동 강등이 LLM 오추출의 안전망**이라는 성질(⑥ §6.4)이 대체물 없이 사라진다. 별도 칸이면 그 안전망이 그대로 살고 ⑥의 `pinnedNewsItem`·`loadPinAcks`·`savePinAcks`·`LearnCard pinned` 를 손대지 않는다. *대가*: 화면이 순수한 한 줄은 아니다. 최대 1건이고 `[확인]` 한 번이면 스트림으로 내려온다.

**처분 줄은 스트림 아래 따로 둔다** (§4.3 확정). 섞지 않는 이유는 **시간축이 다르기 때문**이다 — 처분 줄의 시각은 *처분한* 때(`status_ts`)이고 카드의 시각은 *처음 본* 때(`first_seen`)라, 한 줄에 섞으면 두 축이 겹쳐 순서가 무엇을 뜻하는지 말할 수 없게 된다. 아래에 모아 두면 §2.3의 "배지는 활성만 센다"도 구조로 강제된다. ③의 `toDisposedRows`·`isDisposedVisible`·`disposedLabel`을 위치만 옮겨 그대로 쓴다.

### 2.6 공지 수명 — 기한이 있으면 그때까지, 없으면 며칠

공지는 **시한부**인데 **데이터에 발행 시각이 없다.** `tengu_startup_announcements`(GrowthBook 피처 플래그 캐시)에도 `lastShownEmergencyTip`에도 날짜 필드가 없어, 우리가 가진 유일한 시각은 `first_seen`("우리가 처음 본 때")이다.

**실측 (2026-08-03, 개발 PC의 실제 DB)** — 세 공지 모두 번역은 끝났고 `deadline`은 정상적으로 `null`이다(본문에 기간이 없다):

| id | score | `first_seen` | `deadline` |
|----|-------|--------------|------------|
| `cc-announce-emergency-…` (「공지」) | **325** | 2026-08-03 06:45 | null |
| `cc-announce-fable-5-promo-2-4-team` | 321 | 2026-08-03 06:45 | null |
| `cc-announce-opus-5-launch` | 320 | 2026-08-03 06:45 | null |

`announcementImpressions`에는 5건이 기록돼 있는데 플래그에 남은 건 2건뿐이다 — **지나간 공지는 이미 소스에서 내려가 수집할 수 없다.** 우리가 다룰 수 있는 것은 "남아 있는 것을 언제까지 보여줄까"뿐이다.

**규칙:**

| 조건 | 수명 |
|------|------|
| `deadline`이 유효하고 미경과 | **그 날짜까지** |
| 기한 없음 · 일반 공지 | `first_seen` + **7일** |
| 기한 없음 · 장애 공지(`notice` 태그) | `first_seen` + **2일** |

수명이 끝나면 **활성 목록에서 뺀다** — 스트림·고정 슬롯·탭 배지 셋 다에서 사라진다. DB 행은 남으므로 나중에 아카이브 화면을 만들 여지는 남는다.

**왜 장애 공지만 짧은가**: `lastShownEmergencyTip`은 「마지막으로 표시한」 스냅샷이지 「지금 유효한」 값이 아니다. Claude Code가 이 키를 지우지 않아 **해소된 장애가 영원히 남는데**, 그 상태에서 `priority: 5` → 325점으로 공지 중 최고점과 「공지」 배지를 받는다. 만료를 알 신호가 데이터에 없으므로 "장애는 길어야 하루이틀"이라는 성질로 대신한다.

*수용하는 한계*: `first_seen`은 발행 시각이 아니다. 앱을 새로 깔거나 이번처럼 파이프라인이 막 생기면 **두 달 된 공지도 「오늘 처음 본」 공지**가 되어 수명이 그때부터 시작한다. 데이터에 발행 시각이 없어 고칠 방법이 없다 — 즉시 치우려면 사용자가 `✕`로 닫는다(영구 제외).

## 3. 착수 전 알아야 할 코드베이스 사실

**모두 2026-08-02 `dd4a5bc`(#152 머지) 기준 실측이다.** 줄 번호는 밀릴 수 있으니 심볼로 찾을 것.

### 3.1 `first_seen`은 신뢰할 수 있다 — `last_seen`·`occurrences`와 다르다

스펙 §1.2 D5가 `occurrences`·`last_seen`을 「스캔 지표」라 못 쓴다고 못 박았는데, **`first_seen`은 예외다.** 두 테이블의 `ON CONFLICT`가 `first_seen`을 갱신하지 않기 때문이다.

| 위치 | `ON CONFLICT DO UPDATE SET` | `first_seen` |
|------|------------------------------|--------------|
| `store.rs` `upsert_finding` | `last_seen`, `occurrences+1`, `evidence_json`, `severity`, `prescription_json`, `est_tokens_saved` | **미갱신 → 보존** |
| `store.rs` `replace_content_items` | `score`, `title`, `body`, `source_url`, `trigger_tags`, `last_seen` | **미갱신 → 보존** |

두 테이블 스키마에 `first_seen TEXT`가 이미 있다(`findings`, `content_items`).

**⚠ A(#161)에서 드러난 한계 — `first_seen`은 「삽입 시각」이지 「활성화 시각」이 아니다.** 위 표는 여전히 맞지만, 값이 *처음 노출된* 시각이라는 보장은 없다. 카드가 **새로 보이기 시작하는** 두 전이가 이 값을 갱신하지 않는다:

| 전이 | 왜 노출이 늦는가 |
|------|------------------|
| `pending` → `new` | R6·R7 세션 후보는 `upsert_finding`의 `init_status`가 `pending`으로 넣고 **판정을 통과할 때** 비로소 노출된다. 판정 실패는 `attempts < 3`까지 재시도되므로 그 창이 며칠일 수 있다 |
| `resolved` → `new` | 「해결함」 뒤 재발 복귀(§5.1 `status_evidence_n` 초과) — 키도 severity도 그대로다 |

둘 다 `first_seen`은 과거에 머물러 **시각 비교 배지(`first_seen > lastCoachSeenAt`)가 그 카드를 놓친다.** ③이 같은 전이를 알림 경로(`diff_findings`→`coach:finding`)에서 살려낸 것과 **같은 실패 모드**다 — 상태 전이는 저장이 아니라 알림 경로에서 샌다.

→ **§4.5에서 해결했다**: 배지가 시각 비교를 버리고 **활성 키 집합 diff**로 간다(§2.3). 두 전이 모두 "저장 시점에 활성이 아니었다"는 사실로 잡히므로 활성화 시각 컬럼이 필요 없다. **`first_seen`은 정렬 전용으로 남는다** — 이 한계는 정렬에서는 문제가 아니다(오래 전에 삽입된 카드가 하단에 있는 것은 옳다).

콘텐츠 쪽의 같은 문제(노출된 적 없는 항목이 시각을 선점)는 **A에서 고쳤다** — §3.2 참조.

### 3.2 ~~콘텐츠 프룬이 `first_seen`을 리셋한다~~ → **A(#161)에서 완료**

`store.rs` `replace_content_items` 끝. **③·⑤로 조건이 바뀌었다** — SQL 한 방이 아니라 Rust에서 걸러 개별 DELETE 한다:

```
SELECT id, trigger_tags FROM content_items WHERE status IN ('new','resolved')
  → 이번 랭킹에 있으면 보존
  → TTL로 스킵한 소스의 태그를 가지면 보존 (⑤)
  → 나머지는 DELETE            ('resolved'는 ③이 추가 — 미방출 레슨 정리)
```

랭킹에서 빠진 행은 **삭제된다.** 다시 랭킹에 들면 `INSERT`가 새 `first_seen`을 찍는다 → 어제 본 카드가 오늘 신규처럼 맨 위로 튄다. 순수 최신순 정렬이 이 흔들림을 **카드 순서가 제멋대로 튀는 현상**으로 증폭시킨다. ③이 `resolved`를 대상에 더해 **삭제 범위는 오히려 넓어졌다.**

**⑥에서 같은 함정을 한 번 밟았다** — `content_items`의 파생 캐시(`summary_ko`·`title_ko`·`deadline`)를 `id`만 보고 보존했더니, `cc-changelog-latest`처럼 **id가 고정이고 내용만 갱신되는 소스**에서 화면이 영영 낡은 채로 굳었다(Codex P1). `content_first_seen`도 `id` 기준 보존 테이블이므로 **"이 id의 항목이 그때 그 항목이 맞는가"를 따져볼 것.** `first_seen`은 "처음 본 시각"이라 내용이 바뀌어도 유지가 맞다고 보이지만, 판단을 명시적으로 남길 것.

**A(#161)가 구현한 것 — 권장안 그대로 별도 테이블:**

```sql
CREATE TABLE IF NOT EXISTS content_first_seen (id TEXT PRIMARY KEY, ts TEXT NOT NULL);
```

- 큐레이션 때 `INSERT OR IGNORE`(`replace_content_items`의 **기존 트랜잭션 안** — 락 3단을 깨지 않고 `pipeline.rs` 호출부도 안 건드렸다), 조회 때 `LEFT JOIN` + `COALESCE(fs.ts, c.first_seen)`.
- **`CONTENT_COLS`의 모든 컬럼과 `ORDER BY`에 `c.` 접두사가 붙었다** — `id`가 양쪽 테이블에 있어 빠뜨리면 `ambiguous column name`으로 **런타임에** 깨진다(컴파일로는 안 잡힌다). 이 상수를 쓰는 쿼리는 셋(`list_content` ×2, `content_needing_translation`)이다.
- 마이그레이션은 **백필뿐**이다. 테이블 자체는 `SCHEMA`의 `CREATE TABLE IF NOT EXISTS`가 만든다(`open`이 매번 `execute_batch(SCHEMA)` → `migrate` 순서). 백필을 빼면 기존 사용자는 **마이그레이션 후 첫 프룬에서** 값을 잃는다 — 그때 `INSERT OR IGNORE`가 찍는 건 원래 시각이 아니라 그 큐레이션의 `now_ts`다.
- `status`에 `'stale'`을 더하는 대안은 예정대로 **피했다**(③이 같은 어휘에 `resolved`를 넣었다).

**id 고정·내용 갱신 소스에 대한 판단(위 ⑥ 경고에 대한 답):** **유지가 맞다.** 번역은 "그 원문의" 번역이라 원문이 바뀌면 버려야 하지만 `first_seen`은 "처음 본 시각"이어서 내용 갱신과 무관하다. **대가: 내용이 새로워진 `cc-changelog-latest`가 최신순 스트림 하단에 남는다** — §4 질문 4(고정 슬롯)와 정면으로 맞물리는 지점이다.

**⚠ A의 Codex 리뷰가 잡은 것 — 노출된 적 없는 항목이 시각을 선점하면 안 된다.** `content.rs`의 `rank()`는 점수로 걸러내지 않아서 `replace_content_items`에는 `list_content`가 `score >= 0`에서 숨기는 항목이 섞여 들어온다(통달 축 `SCORE_SUPPRESS=-1000`, 태그 미스 `SCORE_TAG_MISS=-600`, 프론티어보다 2단 이상 먼 축 `100 - dist*60`). 그런데 **프론티어가 이동하면 같은 팁의 점수가 음수→양수로 바뀐다** — 즉 "한 번도 안 보인 항목이 나중에 자격을 얻는" 경로가 실재한다. 그것까지 시딩하면 자격을 얻는 순간 이미 과거 시각을 들고 있어 하단에 묻히고 배지에도 안 잡힌다.

→ **`score >= 0`인 랭킹 항목만 시딩한다.** *남은 한계*: 축 쿨다운(같은 dimension의 `dismissed` 형제가 14일 이내)으로 숨는 항목은 **다른 행의 status·시각**에 달려 있어 쓰기 시점에 판단할 수 없다. 근본 해결은 조회 시점 시딩인데 그건 읽기 경로에 쓰기를 넣어야 해서 락 규율과 충돌한다.

*수용하는 트레이드오프*: 오래 사라졌다 돌아온 항목도 옛 `first_seen`을 유지해 하단에 묻힌다. 갭 길이로 예외를 두는 건 넣지 않는다(YAGNI).

### 3.3 ~~`first_seen`이 프론트에 노출되지 않는다~~ → **A(#161)에서 Rust 쪽 완료**

`FindingRow`·`ContentRow`에 serde 필드가 들어갔다. `CoachFinding`이 `FindingRow`를 `#[serde(flatten)]`하므로 커맨드 변경 없이 payload에 실린다.

### 3.7 콘텐츠 카드 상한은 프론트에만 있다 (⑥에서 4 → **6**)

`store.list_content`에는 **LIMIT이 없다**(`status='new' AND score >= 0`인 행 전부). 상한은 `coach-helpers.ts`의 `CONTENT_CARD_LIMIT`가 `partitionCoachItems`에서 가르기 전에 적용한다 — 원래 삭제된 `TipCard`의 `items[0] + items.slice(1, 4)`를 이어받은 4였는데, ⑥이 소스(로컬 공지)를 하나 더하면서 **6으로 올렸다**. 4를 두면 공지 2건이 배움 카드를 전부 밀어낸다.

**고정 슬롯(최대 1건)은 이 상한 밖의 별도 칸**이다 — `CoachTab`이 고정된 항목을 빼고 `partitionCoachItems`에 넘긴다. 자르는 지점은 여전히 한 곳뿐이다.

**⑥ 실측(2026-08-03, 실제 `claude.json`)**: 로컬 공지 3건은 `SCORE_ANNOUNCEMENT + priority`로 320·321·325를 받았고, 프론티어 축 팁이 **한꺼번에 500점**이라 상한 6 안에 공지는 1장만 들어왔다. **문제가 아니라고 판단했다** — 처분이 큐를 비운다. 공지를 `✕`로 닫으면 영구히 빠지고(프룬은 `new`·`resolved`만 지운다), 팁을 하나 닫으면 **축 쿨다운 14일**이 걸려 그 축 4~5장이 한꺼번에 사라진다. 단일 스트림에서 상한을 재검토할 때 이 동역학을 전제로 삼을 것.

→ **§4.2에서 확정**: 이 동역학 때문에 폐지·증액은 필요 없다고 보고 **6을 유지**하되, 자르는 축만 score → `first_seen`으로 바꾼다(§2.2).

### 3.8 `enrich_personal`은 태그로 붙어 레슨 본문과 어긋날 수 있다

`store.rs` `tip_personal_evidence`는 `trigger_tags`로 분기하고, `has("subagent")` 분기는 **카운트가 0이어도 항상 값을 반환**한다. `lesson-cache`의 태그가 `["context", "subagent", "personal"]`이라 캐시 재읽기 레슨에 서브에이전트 수치가 달린다.

→ PR②는 `personal`로 본문 근거를 **대체하지 않고 둘 다 싣는** 쪽으로 갔다(`toLessonCardView`). 근거 슬롯을 손댈 때 이 결정을 되돌리지 말 것.

### 4.1 축 라벨과 「공지」 — 버리지 않고 보조 칩으로

*질문이 왜 생겼나*: 배지를 분류 이름으로 고정하면 축 라벨이 갈 곳이 없다. Boris·팀은 본문 끝에 출처가 이미 있어 괜찮지만 축 라벨은 본문 어디에도 없어 완전히 사라진다. **⑥이 배지를 하나 더 늘려** 긴급 팁(`lastShownEmergencyTip`, `notice` 태그)은 「공지」, 나머지 로컬 공지는 「소식」이 되었고, 3분류로 고정하면 「공지」도 갈 곳이 없었다.

*확정*: 배지 슬롯을 **분류 배지 + 보조 칩** 둘로 가른다. 매핑 표는 §2.1. 「공지」와 축 라벨이 둘 다 칩으로 살아남고, 폴백 `'배움'`만 분류 배지와 겹쳐 버려진다. 카드 헤더에 텍스트가 하나 늘어나는 것을 대가로 받아들인다 — 축 라벨은 역량 사다리 진행을 알리는 **유일한** 화면 표시다.

### 4.2 카드 상한 — 6은 유지하고 자르는 축만 바꾼다

*질문이 왜 생겼나*: ⑥이 4 → 6으로 올렸고 고정 슬롯 1건은 상한 밖이다. §3.7의 실측 동역학(처분이 큐를 비운다 — 공지 `✕`는 영구, 팁 `✕`는 축 쿨다운 14일로 그 축 4~5장이 한꺼번에 빠진다)을 전제로 삼아야 했다.

*확정*: 상한 6은 그대로 두고 **자르는 축을 score → `first_seen`으로** 바꾼다(§2.2). 상한 자체가 문제가 아니라 **자르는 축과 보여주는 축이 어긋나는 것**이 단일 스트림에서 새로 생기는 문제였다. 폐지·증액은 §3.7의 동역학상 필요하지 않다 — 처분이 큐를 비우고 백엔드가 `score >= 0`으로 이미 거른다.

**⚠ 후속 (2026-08-03) — 이 판단은 뒤집혔다. 상한을 폐지했다.**

구현 후 실환경 스모크가 근거를 무너뜨렸다. 실측 DB에서 `score >= 0`인 활성 콘텐츠 중 **오늘 들어온 6건이 동률로 상한을 정확히 채웠고**, `cc-changelog-latest`·`lesson-frontier`가 상한 밖으로 밀려 화면에서 사라졌다.

> **⚠ 정정 (같은 날, 실물 확인 후).** 처음에는 `T-L3-1~4`(커리큘럼 팁)·`boris-b83412`도 상한에 밀린 것으로 판단했으나 **틀렸다.** 그 5건은 상한이 아니라 **축 쿨다운으로 백엔드에서 이미 걸러지고 있었다** — 오래 전에 닫힌 `boris-d7c2ea`(같은 `automation` 축)가 쿨다운을 영구히 재무장시키고 있었다(원인·수정은 `store.rs` `list_content` 주석). 상한을 없애도 그 카드는 돌아오지 않았고, 쿨다운을 함께 고쳐야 §4.1의 축 라벨 칩이 비로소 화면에 나온다. **상한 폐지의 순효과는 2건**이고, 아래 세 근거는 그와 무관하게 유효하다.

폐지 근거 셋:
1. **배지와 화면이 일치한다.** §2.3이 활성 키를 "상한 적용 전 전부"로 세는 탓에 배지 14 / 화면 7행이었다. 그 불일치를 "수용하는 대가"로 적었는데, 상한이 없으면 대가 자체가 사라진다.
2. **시간순에서 꼬리의 뜻이 다르다.** 상한을 둔 원래 이유(②의 사고)는 *score 순* 목록의 꼬리가 잡동사니라서였다. 시간순에서 꼬리는 "이미 본 오래된 것"이라 아래 있는 게 자연스럽다.
3. **처분이 정리 수단으로 실제 작동한다.** 스모크에서 공지 2건을 `✕`로 닫자 `plugin-reco` 2건이 곧바로 올라왔다(§3.7 동역학 실증).

*최대치 실측*: 프론티어 축은 한 번에 하나라 축 팁은 최대 7건(`orchestration`)이고 나머지 4축 21건은 `score < 0`으로 숨는다. 축 무관(소식·레슨·팀·공지)이 8건이라 **20장 내외**가 현실적 상한이다. *남은 리스크*: 팀 지식(`hub-page_229`)이 누적되면 그 그룹이 커진다 — 프론트 상한이 아니라 **백엔드 랭킹·프룬**에서 다룰 문제다(`list_content`에 LIMIT이 없는 것이 원래 설계 공백).

### 4.3 처분 줄 — 스트림 아래 따로 (③의 판정을 그대로 이어받는다)

*확정*: **스트림 아래 별도 구역.** 근거는 §2.5 — 처분 줄의 시간축(`status_ts`)과 카드의 시간축(`first_seen`)이 달라 한 줄에 섞으면 순서의 뜻이 무너진다.

③은 **위치를 정하지 않고 판정만** 순수 함수로 확정했다. 섹션이 사라지면 「섹션 하단」 좌표가 무의미해지므로 의도적으로 남긴 몫이다.

**그대로 재사용할 것** (`coach-helpers.ts`, 전부 테스트 있음):

| 심볼 | 하는 일 |
|------|---------|
| `RESOLVED_WINDOW_DAYS = 7` | 「해결함」 복구 창 |
| `disposedLabel(status)` | `✔ 해결함` / `◷ 무시` / 처분이 아니면 `null` |
| `isDisposedVisible(status, statusTs, nowMs)` | 무시=영구, 해결함=7일. **처분 시각을 모르면 보이는 쪽**(실행취소를 뺏지 않는다) |
| `toDisposedRows(findings, content, nowMs)` | 룰 카드+개인 레슨을 `DisposedRow[]`로 병합. 문법 B와 판정 내부 상태(pending·rejected)는 제외 |
| `partitionCoachItems` | 처분 항목을 **카드 상한(§3.7, 현재 6) 적용 전에** 걷어낸다 |

**배치**: ③이 이미 「숨긴 항목 N개 보기」 토글을 없애고 탭 맨 아래에 톤다운 한 줄씩 바로 노출해 뒀다 — **그 자리가 그대로 확정이다.** 스트림 아래라는 좌표가 섹션 소멸 뒤에도 그대로 성립하므로 옮길 것이 없다. `DisposedRow.source`(`finding`|`lesson`)가 실행취소를 어느 커맨드로 보낼지 이미 담고 있다.

**B가 밟기 쉬운 함정 둘**
- 처분 줄의 재료는 `listContent(**true**)`다. `listContent(false)`는 백엔드가 `status='new'`+점수+축 쿨다운으로 걸러 처분 행이 아예 오지 않는다. ③은 두 호출을 `Promise.all`로 병렬로 쓴다(`tips` / `allTips`).
- 7일 컷오프는 **시계가 흘러야** 닫힌다. `$derived` 안의 `Date.now()`는 반응성 의존이 아니고 파이프라인엔 주기 tick이 없어(`debounce_loop`는 로그 감시 트리거), ③은 1시간 눈금 `$state` 시계를 둔다. 옮길 때 이 시계를 빠뜨리면 만료가 멈춘다.

### 4.4 고정 슬롯 — 스트림 위 별도 칸으로 유지

*질문이 왜 생겼나*: 「전체 `first_seen` 내림차순 한 줄」(§2.2)과 「최상단 고정 1건」이 정면으로 부딪혔다. 편입하면 **기한 경과 자동 강등이 LLM 오추출의 안전망**이라는 성질(⑥ §6.4)을 무엇이 대신할지도 함께 정해야 했다.

*확정*: **편입하지 않는다.** 대신할 것이 없기 때문이다 — 정렬에 편입된 카드에게 「강등」이란 곧 제자리이고 그 자리는 `first_seen`이 정하므로, 잘못 뽑힌 날짜가 스스로 내려오는 경로가 사라진다. 기한 칩만 남기는 절충안(시간순에 깔되 `⏳ MM-DD까지` 유지)도 같은 이유로 탈락했다 — 칩은 시선을 끌 뿐 안전망이 아니다.

*따라오는 이득*: ⑥의 `pinnedNewsItem`·`loadPinAcks`·`savePinAcks`·`LearnCard pinned`·날짜 `$state` 시계를 손대지 않는다.

*⚠ 연쇄 주의*: 고정 슬롯이 살아남으므로 **`pinnedNewsItem`에는 score 순 배열을 넘겨야 한다.** 시간순 재정렬은 고정 항목을 빼낸 뒤에 한다(§2.2 파이프라인).

### 4.5 배지 기준 — 활성 키 집합 diff (Rust 변경 없음)

*질문이 왜 생겼나*: A(#161) Codex 리뷰에서 신설됐다. `first_seen`은 삽입 시각이지 활성화 시각이 아니라(§3.1) `first_seen > lastCoachSeenAt` 배지가 `pending`→`new`와 재발 복귀를 놓친다. 세지 않기로 하면 **③이 알림 경로에서 고친 재발 감지가 배지에서 다시 새는 것을 받아들이는 것**이었다.

*조사로 좁혀진 것*: 프론트가 활성화 시각을 **복원할 수 없다**. 재발 복귀는 `status_ts`를 지운다 — `store.rs`가 `UPDATE findings SET status='new', status_evidence_n=NULL, status_ts=NULL`을 쓰고 실행취소(`set_content_status(…, 'new', …)`)도 같다. 즉 활성 상태에서 `status_ts`는 언제나 NULL이라 그 컬럼으로는 "언제 활성이 됐나"를 알 수 없다.

*세 안*:

| 안 | 두 전이를 잡나 | 비용 |
|----|----------------|------|
| `first_seen` 시각 비교 (§2.3 원안) | ✗ 둘 다 놓침 | 0 |
| **활성 키 집합 diff** | **✓ 둘 다** | **프론트만 — 0** |
| Rust에 `activated_at` 신설 | ✓ 둘 다 | B가 프론트 전용이라는 범위가 깨지고 마이그레이션이 하나 는다 |

*확정*: **활성 키 집합 diff**(§2.3). `pending`·`resolved` 카드는 저장 시점의 활성 집합에 없으므로 `new`로 올라오는 순간 자동으로 잡힌다. Rust를 건드리지 않고 정확도를 얻는다.

*③이 지키라고 한 성질(#155)*: `partitionCoachItems`가 처분 항목을 걸러 카드 목록엔 활성만 남는다. 탭 배지(`App.svelte`)와 알림 로그는 지금 `listFindings(false)`(백엔드 `status='new'`)를 쓴다 — 바꿀 때 **처분 줄이 `unseen`에 섞이지 않도록** 활성만 세는 성질을 유지할 것. 활성 키 집합 방식은 정의상 이 성질을 만족한다.

### 4.6 §3.5에 더할 것 — 재발은 `coach:finding`에 실린다 (#155)

스캔의 before/after 스냅숏이 `store.finding_severities()`(전체)에서 `store.active_finding_severities()`(`status='new'`만)로 바뀌었다. `diff_findings`는 **새 키 또는 severity 상승**만 fresh로 보는데 재발 복귀(`resolved→new`)는 키도 severity도 그대로라 전체 스냅숏에선 보이지 않았고, 그래서 알림·말풍선이 뜨지 않았다.

**부수 제약**: `pipeline.rs`의 before/`run_rules`/after는 이제 **한 락 블록에 있어야 한다**. 쪼개면 사이에 낀 `set_finding_status`(사용자의 처분·실행취소)가 diff에 섞여 "새로 떴다"고 알린다. 예전 주석은 "쪼개도 안전하다"였는데 그 전제가 깨졌다.

`content:ready`도 **빈 목록일 때까지 무조건 emit**으로 바뀌었다 — 큐레이션은 노출 목록을 바꾸기만 하는 게 아니라 행을 지우기도 한다(미방출 `resolved` 레슨 프룬). 리스너를 늘릴 때 빈 payload를 전제할 것.

## 6. ③·⑥ 계획에 생기는 여파

- **③ — 완료(#155).** 「처분 카드를 섹션 하단 톤다운 줄로 이동」이 계획이었으나 섹션이 사라지므로, ③은 처분·수명 **모델**(재발 감지·`status_evidence_n`·마이그레이션)에 집중하고 표시 위치를 남겨뒀다. 그 결과와 B가 이어받을 심볼·함정은 **§4.3**에 정리돼 있다.
- **⑥ — 완료(#156).** 로컬 공지가 「소식」 분류로 그대로 들어간다. B가 흡수해야 할 것은 넷이고 전부 확정됐다: 배지 「공지」 → 보조 칩(§4.1), 고정 슬롯 → 별도 칸 유지(§4.4), 문법 B의 늘어난 슬롯 3종(§2.1), 상한 6 → 유지하되 축 변경(§4.2).
  - `content_items`에 `summary_ko`·`title_ko`·`deadline`이 생겼고 `ContentItem`으로 노출된다. 카드는 `title_ko ?? title`, `summary_ko ?? body`로 폴백한다 — **엔진 미설정 사용자에게는 영어 원문이 그대로 보인다**(소식은 코칭이 아니라 정보 전달이라 값이 남는다).
  - `coachTip`(🤖 맞춤 코칭 한 줄)·`coach_tip` 커맨드·`coach_prompt`가 **제거**됐다. §6.3 표가 한국어 소스를 「그대로」로 못박아 LLM을 아예 부르지 않는 쪽으로 갔고, 그 자리는 §2.1 ①의 결정론 📊 근거 줄이 대신한다.
