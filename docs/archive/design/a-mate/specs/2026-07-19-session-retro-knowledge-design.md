# 세션 회고 지식 — a-mate가 a-hub에 "언제·어떻게" 글을 쓰나 (검토 + 설계)

> **질문**: 허브 글쓰기를 a-mate 단일 창구로 할 때, 세션에서 **어려웠던 일·참고할 만한 일**을
> 언제·어떻게 올리는 게 a-hub 취지에 맞나?
> 관련: [지식 공유 스펙](2026-07-18-hub-knowledge-sharing-design.md) · [텔레메트리 스펙](2026-07-18-hub-telemetry-design.md) · [작성 지침](../../../../architecture/a-hub/writing-guide.md)

## 0. 30초 요약

- **결정**: 허브 글쓰기 단일 창구 = **a-mate** (세션 속 에이전트가 아니라). 세션이 **끝난 뒤**, **"고생 끝 해결" 신호가 있는 세션만** 골라, **로컬 생성 요약**(Engine)으로 issue→resolve 발행.
- 트리거는 결정론(오류→회복 패턴), 서사는 LLM, 수치는 브리프만(정밀도의 선). 세션당 평생 1회 (하루 상한은 2026-07-30 폐지 — §2 참고).

## 1. 왜 a-mate 단일 창구인가 (검토)

a-hub 취지는 "**재사용 가치 있는 것** — 남도 겪을 문제 + 통한 해결책 + 실패한 시도"(작성 지침)이고,
❌ 목록이 "일회성·자명한 것"이다. 세션 속 에이전트(Claude Code)가 직접 쓰게 하면:

1. **세션 안에서는 재사용 가치를 모른다.** "고생"인지는 해결이 끝나야 알고, 자명한 이슈인지는 다른 세션들과 비교해야 안다. a-mate만 전 세션·전 호스트를 사후 조망할 수 있다.
2. **품질 편차와 스팸.** 세션마다 판단 기준이 달라 허브가 일회성 글로 흐려진다 — 코칭 v2에서 배운 "세션 단위 카드는 스팸" 교훈의 허브 버전.
3. **세션 토큰 낭비.** 작업 중 허브 왕복은 주 작업 컨텍스트를 소모한다. a-mate는 스캔에 편승해 0 추가 세션 비용.

→ Claude Code용 MCP/skill 쓰기 경로는 남겨두되(수동·의도적 기록용), **자동 기록은 a-mate가 게이트키퍼**.

## 2. 언제 쓰나 (트리거 — 결정론)

**"어려웠던 일"의 신호는 이미 수집돼 있다**: `tool_result`의 `error/denied` 상태(v2.1 수집).

| 조건 | 값 (env 조정 가능) | 근거 |
|---|---|---|
| 세션 종료 | `last_ts` 30분 이상 조용 | 해결 여부는 끝나야 안다. 세션 중 발행 금지 |
| 고생 신호 | error+denied **≥ 3** | 1~2회 오류는 자명한 일상 — 취지의 ❌ |
| 회복 신호 | 마지막 tool_result가 **ok** | "실패로 끝난 세션"은 해결책이 없다 → 백로그감이지 지식이 아님 |
| 유의미 규모 | 이벤트 ≥ 20 | 초단기 세션의 오류는 노이즈 |
| 나깅 방지 | 세션당 평생 1회(`retro\|{session_id}`) | 허브도 나깅 방지 대상 |

> **2026-07-30 개정 — 하루 상한 폐지.** 원안의 "하루 최대 2건"은 제거했다(사용자 지시).
> 이유: `select_retros`가 `last_ts DESC`로 최신부터 집어가므로, 후보가 하루 2건씩만 빠지는 동안
> 오래된 세션은 **영구 미발행**이 됐다(2026-07-30 확인 시 미발행 후보 20건, 최고령 7/21).
> 나깅 방지의 실질은 세션당 평생 1회 dedup이 담당하므로 그건 유지한다. 다시 조이려면
> `SPACE_A_RETRO_DAILY_CAP`(env)으로 건다 — 기본값 없음 = 무제한.

"참고할 만한 일"(성공 패턴 발굴)은 신호가 모호해 **v2 유예** — R6(Skill화 후보)과 합쳐질 예정.

## 3. 어떻게 쓰나 (형식)

- **issue→resolve** (작성 지침의 "문제 해결 기록" 표준 — 해결책이 Page로 발행돼 검색·cite 대상이 됨).
- **본문 = 로컬 생성 요약.** 결정론 브리프(작업 한 줄 요약 대상, 오류 도구·횟수, 소요, 규모)를 Engine에 주고
  2~3문장 요약 + 제목을 받는다. #46의 "서버로 나가는 것은 … **로컬 생성 요약**뿐" 원칙 그대로.
  - 정밀도의 선: LLM은 브리프의 사실·수치만 인용. 프롬프트에 명시.
  - Engine 미설정이면 **발행 보류**(다음 스캔 재시도) — 품질 > 정시성 (diary 철학). 결정론 폴백 발행은 하지 않는다: 원문 요약 없는 회고는 재사용 가치가 낮다.
- **프라이버시**: 세션 원문(첫 요청 미리보기)은 사용자가 고른 **Engine까지만** 간다(egress 동의 경계). 허브에는 요약 텍스트만. cwd·경로·세션 id는 허브 본문에 싣지 않는다.

steps 구성(재현→시도→해결, 지침 형식): ① 작업 맥락(요약) ② 시행착오(오류 도구·횟수 — 결정론) ③ 해결 상태(회복) ④ 규모(~N 이벤트, ~M분).

## 4. 세 계층 정리 (a-mate → a-hub 전체 그림)

| 계층 | 트리거 | 내용 | 소비자 |
|---|---|---|---|
| 텔레메트리 | 매일 1회(전날) | 집계 JSON | a-lens 대시보드 |
| 코칭 지식 | 규칙 finding 문턱 | 결정론 처방(R1 등) | 팀원(검색·cite) |
| **세션 회고 (이 스펙)** | 고생 끝 해결 세션 | LLM 요약 경험담 | 팀원(같은 삽질 방지) |

## 5. 코드 배치·검증

- `store.rs`: `struggle_sessions(min_errors, min_events, settled_before)` — error/denied 집계 + call↔result 조인으로 오류 도구 식별 + 마지막 결과 ok 판정
- `hub.rs`: `build_retro_brief`(결정론) · `retro_prompt`(정밀도의 선 명시) · `run_retro_push(store, cfg, engine)` — issue→resolve, `retro|{session_id}` dedup, 하루 2건 상한
- `pipeline.rs`: `maybe_post_retros` — 스캔 편승, 락 규율(Engine·네트워크는 락 밖)
- CLI: `agent-mentor retro` (E2E/수동)
- 검증: 단위(선별 조건·상한·브리프 스크럽) + 실서버 E2E(실제 고생 세션 → 발행 → 재실행 dedup)
