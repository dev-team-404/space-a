# Agent Mentor — 프로젝트 브레인스토밍 & 킥오프

> **이 문서의 목적**
> Claude Code에서 이 프로젝트를 브레인스토밍하기 위한 출발점(seed) 문서입니다.
> 사전 논의에서 이미 확정된 결정과 아직 열려 있는 질문을 구분해 정리했습니다.
> Claude Code는 이 문서를 읽고, 열린 질문들을 함께 탐색하면서 설계를 구체화하는 방식으로 진행합니다.
> **아직 코드를 짜지 마세요.** 먼저 브레인스토밍 → 설계 합의 → 그 다음 구현입니다.

---

## 0. 한 줄 요약

**Agent Mentor** — WSL과 Windows 양쪽의 Claude Code 사용 기록(JSONL 등)을 로컬에서 분석해,
사용자가 AI 코딩 에이전트를 **토큰 낭비 없이 효율적으로** 쓰도록 코칭하는
**Windows 상주형 데스크톱 앱**. 조용한 트레이 유틸리티로도, 대화하는 데스크톱 캐릭터로도 동작한다.

### 제품명: Agent Mentor
- **의미**: "mentor"는 오디세이아에서 텔레마코스를 가르친 인물의 이름이 그대로 보통명사가 된 것 — Claude 모델의 서사/신화 명명(Mythos, Fable)과 결이 통한다. 한국인에게도 외래어("멘토")로 이미 직관적이다.
- **"agent" 접두어의 이유**: `claude-` 접두어(Anthropic 상표) 대신 사용. Claude Code에 국한하지 않고 **OpenCode·Codex 등 다른 에이전트로의 확장**을 이름에서부터 열어둔다. 실제로 기존 도구(ccusage)도 14+ 에이전트를 지원하는 방향으로 갔다.
- **패키지/식별자**: `agent-mentor` (예비 확인 결과 동명의 저명 패키지 없음. 단, 배포 직전 `npm view` / `cargo search` / GitHub org / 도메인 직접 조회로 최종 확정할 것.)
- **태그라인 제안**: "Your mentor for Claude Code — use AI agents efficiently, without token bloat."
- **네임스페이스 주의**: 최근 "agent" + "skills" 계열 패키지가 폭증(`skills.sh`, `npm-agentskills`, Vercel `skills` 등). 목적(사용 코칭 vs 스킬 배포)이 다르므로 혼동 위험은 낮지만, README·태그라인에서 "usage coaching / efficiency" 정체성을 분명히 할 것.

## 1. 핵심 컨셉

사용자의 Claude 사용 패턴을 관찰해서:

- 어떤 skill / MCP / plugin을 어떤 용도로 얼마나 쓰는지 **통계**를 보여준다
- **잘못 쓰고 있는 경우** 개선점을 제시한다 (예: 단순 작업에 과한 모델, 반복 파일 읽기, 안 쓰는 MCP가 매 세션 토큰 소모)
- 반복 작업을 감지해 **스킬(SKILL.md) 초안 작성**을 제안한다
- 더 나은 **유명 스킬 사용을 권고**한다
- 전체적으로 **토큰 맥싱(불필요한 토큰 소모) 없이** 에이전트를 쓰도록 돕는다

핵심 가치는 **"집계"가 아니라 "코칭"**이다. (아래 4번 경쟁 분석 참고)

## 2. 확정된 결정 (Fixed)

사전 논의를 통해 이미 정해진 사항. 브레인스토밍에서 뒤집을 필요는 없지만, 근거가 약하면 재검토 가능.

### 2.1 기술 스택: **Tauri v2** (Rust 백엔드 + Webview2 프론트)

선택 이유:
- **상주 비용**: 종일 트레이에 떠서 파일을 감시하는 앱. OS webview를 써서 Electron(Chromium 상주, 수백 MB) 대비 메모리가 가볍다.
- **상주 + 자동 업데이트가 프레임워크 내장**: system tray 플러그인, autostart 플러그인, 서명 기반 updater 플러그인 모두 공식 제공.
- **무거운 로컬 처리를 Rust로**: JSONL 대량 파싱·집계·파일 감시(`notify` crate)·SQLite 캐싱(`rusqlite`)이 자연스럽다.
- **모델 지식**: Tauri v2는 2024년 10월 정식 릴리스. 최신 Claude 모델(Sonnet 5 / Opus 4.7·4.8, 컷오프 2026년 1월)에 충분히 학습되어 있다.

> **주의 (Electron 관련 정정)**: 이전에 겪은 CA 인증서 이슈는 *Claude Code*(Bun 컴파일 바이너리가 BoringSSL을 써서 `NODE_EXTRA_CA_CERTS`를 무시한 것)의 문제였고, 일반 Electron 앱과는 무관하다. Electron은 CA 관점에선 오히려 정상적이다. 즉 스택 선택의 근거는 CA가 아니라 **상주 비용**이다.

### 2.2 플랫폼: **Windows 전용**

- WSL + Windows 양쪽 `.claude`를 모두 모니터링하되, 앱 자체는 Windows 네이티브.
- 크로스플랫폼 포기 덕분에 데스크톱 캐릭터의 클릭-스루 문제(아래 3.3)와 macOS 투명 창 버그를 피할 수 있다.

### 2.3 UX 형태: **3-윈도우 하이브리드**

| 윈도우 | 성격 | 역할 |
|---|---|---|
| `tray` | 아이콘, 상시 | 코어 감시 + 메뉴. 기본 상태 |
| `mascot` | 투명·alwaysOnTop·작게, 옵션 | 데스크톱 캐릭터. 켜면 말풍선으로 조언 |
| `chat` | 일반 창, on-demand | 마스코트/트레이 클릭 시 생성. 심층 질문 |

세 윈도우가 **하나의 Rust 백엔드**(파서 + SQLite + 규칙 엔진 + 조언 생성)를 공유하고,
조언 텍스트는 백엔드가 이벤트로 mascot·chat 양쪽에 밀어준다.

> 마스코트 캐릭터는 제품명 "Mentor"의 의인화로 디자인할 수 있다 — 곁에서 조언하는 스승/동반자.

### 2.4 집계는 직접 만들지 않는다

토큰 집계는 이미 레드오션(`ccusage` 등). 집계는 `ccusage --json` 같은 기존 도구를 **파서로 감싸서** 위임하고, 우리는 그 위의 **코칭 레이어**에만 집중한다. 이렇게 하면 JSONL 스키마 변경(릴리스마다 바뀜)의 유지보수 부담도 그들에게 넘길 수 있다.

## 3. 열린 질문 (Open — 여기가 브레인스토밍의 핵심)

### 3.1 데이터 소스 — 실제 스키마 검증 필요

가정하고 있는 소스들 (Claude Code 기준):
- `~/.claude/projects/**/*.jsonl` — 세션 트랜스크립트 (메시지, tool_use/result, 토큰, 모델명)
- `~/.claude/settings.json`, 프로젝트 `.claude/settings.json`, `~/.claude.json` — 설정, MCP 서버, 권한
- `~/.claude/skills/`, 프로젝트 `.claude/skills/` — 설치된 스킬
- `~/.claude/plugins/`, `~/.claude/history.jsonl` — 플러그인, 명령 히스토리

WSL vs Windows 경로:
- Windows: `C:\Users\<user>\.claude\`
- WSL: `\\wsl$\<distro>\home\<user>\.claude\` (Windows에서 UNC 경로로 직접 접근)

**브레인스토밍 과제:**
- [ ] 실제 내 `.claude` 디렉터리를 열어 JSONL 한 줄의 진짜 스키마를 확인한다 (가정 검증)
- [ ] 여러 WSL distro가 있을 때 어떻게 열거·통합할지
- [ ] 스키마가 버전마다 변하는 문제를 어떤 추상화로 방어할지 (파서 인터페이스 설계)
- [ ] 향후 OpenCode/Codex 등 타 에이전트 로그 경로·포맷을 파서 인터페이스에 어떻게 일반화할지 (제품명 "agent"의 약속을 지키는 설계)

### 3.2 코칭 로직 — 무엇을, 어떻게 탐지할까

두 갈래로 나뉜다:

**A. 규칙 기반 (신뢰도 높음, 먼저 구현)**
- 캐시 히트율 낮음 → 대화 구조 개선 제안
- 매 턴 같은 파일 재읽기 → 컨텍스트 관리 문제
- 단순 반복 작업에 Opus 사용 → Haiku/Sonnet 권장
- 동일 워크플로 N회 반복 → 스킬/슬래시 커맨드 추출 제안
- MCP 도구 결과가 매번 폐기됨 → 불필요한 연결
- **컨텍스트 예산 분석**: 안 쓰는데 매 세션 always-on 토큰을 태우는 MCP/plugin 탐지 (가장 큰 차별점 중 하나 — 대부분의 사용자가 모름)

**B. LLM 기반 (강력하나 주의)**
- "이 세션 어떻게 더 잘 쓸까?"를 Claude에게 물어보는 메타 분석
- 코칭 앱이 스스로 토큰을 태우면 자기모순 → 규칙으로 후보를 좁힌 뒤에만 호출, 결과 캐싱, **명시적 옵트인**

**브레인스토밍 과제:**
- [ ] 초기 규칙 셋을 구체적 임계값과 함께 정의 (예: "캐시 히트율 < X%면 경고")
- [ ] 조언의 톤/전달 방식 (마스코트 말풍선은 짧게, 채팅창은 상세히)
- [ ] LLM 분석을 언제/어떻게 트리거할지, 프라이버시 경계

### 3.3 데스크톱 캐릭터 — 클릭-스루 전략

**확인된 함정**: Tauri v2는 per-region hit-testing(영역별 클릭 판정)을 노출하지 않는다. 화면을 덮는 큰 투명 창을 쓰면 투명 영역 클릭도 창이 먹어서 바탕화면을 못 만진다.

두 가지 해법:
1. **폴링**: Rust 루프가 커서 위치를 ~60fps로 보고 `setIgnoreCursorEvents`를 토글. 컴파일된 타이트 루프라 생각보다 가벼움.
2. **작은 창 (추천)**: 화면을 덮지 말고 캐릭터 크기에 딱 맞는 작은 투명 창을 옮겨 다니게 함. Windows 전용이면 이쪽이 훨씬 간단. 말풍선 뜰 때만 창을 잠깐 키움.

**브레인스토밍 과제:**
- [ ] 두 방식 중 선택 (또는 하이브리드)
- [ ] 캐릭터 애셋/애니메이션 방식 (Live2D? 스프라이트? 간단한 SVG?)
- [ ] `contentProtected: true`로 스크린샷 방지를 걸지 (사내 코드 노출 대비)

### 3.4 유명 스킬 추천 — 기존 레지스트리 위임 (업데이트됨)

**상황이 유리하게 바뀌었다.** 처음엔 성숙한 레지스트리가 없어 수동 큐레이션해야 한다고 봤으나, 2026년 들어 agent skill 패키지 매니저·레지스트리가 빠르게 자리잡았다:

- **skills.sh** — `npx skills find "<작업>"`으로 작업에 맞는 스킬 검색, `npx skills add`로 설치하는 커뮤니티 레지스트리
- **SkillsMP** — GitHub의 SKILL.md를 크롤링해 AI 시맨틱 검색으로 색인. 35만+ 스킬 보유(최대 카탈로그)
- **Vercel `skills`** — 표준 지원 에이전트면 어디서든 동작하는 크로스플랫폼 배포 CLI

→ 따라서 추천 카탈로그를 **직접 유지할 필요 없이**, 이들 레지스트리의 검색을 백엔드로 호출해 "이 반복 작업엔 이런 스킬이 있다"를 매칭할 수 있다.

**브레인스토밍 과제:**
- [ ] 어떤 레지스트리를 1차 소스로 쓸지 (skills.sh 검색 API vs SkillsMP 시맨틱 검색)
- [ ] 품질 필터: SkillsMP는 GitHub 스타 외 품질 게이트가 없음 → 신뢰도 임계값(스타 수, 유지보수 활성도) 설계 필요
- [ ] 우리 앱이 감지한 "반복 작업 패턴"을 레지스트리 검색어로 어떻게 변환할지

### 3.5 스킬 배포 생태계와의 관계 (신규 고려)

Agent skill 배포가 "npm처럼" 표준화되는 흐름(Vercel/Prisma/Supabase 등이 공식 스킬 출시). Agent Mentor가 생성한 SKILL.md 초안을 이 생태계에 어떻게 태울지 여지를 남겨둔다.

**브레인스토밍 과제:**
- [ ] 생성한 SKILL.md를 로컬 `.claude/skills/`에 바로 설치할지, 아니면 공유 가능한 형태로 export할지
- [ ] (장기) 우리 앱 자체가 스킬 배포 표준(agentskills 오픈 포맷)을 따를지

## 4. 경쟁 지형 (왜 코칭에 집중해야 하는가)

리서치 결과 요약:

**집계·모니터링 = 완전 포화. 뛰어들지 말 것.**
- `ccusage` — 사실상 표준. 로컬 JSONL 파싱, 일/주/월/세션 리포트, JSON export, MCP 서버 내장, 14+ 에이전트 지원
- `Claude-Code-Usage-Monitor` — 실시간 번레이트/한도 예측 대시보드

**코칭·낭비 탐지 = 이미 진입했지만 아직 미성숙 = 우리의 전장.**
- JSONL을 읽어 토큰 낭비 / CLAUDE.md 준수 실패를 짚고 diff 형식 개선안을 내는 도구
- 반복 읽기·헤매기·비용 이상치 탐지하는 로컬 대시보드
- tool/agent/MCP/skill별 토큰 실시간 귀속 도구
- /coaching /insights 스킬을 포함한 "Mission Control" 플러그인

→ 전부 **CLI/터미널 기반**이고 개별 낭비 패턴에 국한. "스킬화 제안 + 유명 스킬 추천 + WSL/Win 통합 + 데스크톱 코치 UX"를 통합한 건 아직 없다.

**Agent Mentor의 3대 차별점:**
1. WSL + Windows 통합 모니터링을 **GUI**로 (경쟁 도구는 전부 단일 환경 CLI)
2. 스킬화의 완성 — **탐지에서 SKILL.md 생성·설치까지**
3. **컨텍스트 비용 정적 분석** — 대화 시작 전에 새는 always-on 토큰 (MCP 5개 세팅이 대화 전 55,000 토큰 소모하는 문제)

## 5. 리스크

- **비공식 JSONL 스키마 의존** — 가장 큰 리스크. Claude Code 업데이트마다 깨질 수 있음. → `ccusage`를 파서로 감싸 완화.
- **프라이버시 (Samsung 사내)** — 트랜스크립트에 사내 코드·비밀정보 포함. → 100% 로컬 처리 기본값, LLM 전송은 명시적 옵트인. 사내 반출 정책 확인 필수.
- **Tauri v1/v2 혼동** — 웹에 v1 예제가 많아 모델이 오래된 API(`SystemTray`, `tauri::updater`, `WindowBuilder`)를 섞을 수 있음. → 최신 모델 사용 + Context7 MCP로 실시간 문서 참조 + CLAUDE.md에 "v2만, v1 금지" 명시.
- **코드 서명** — updater는 서명 검증 필수. 사내 배포 시 인증서 정책 확인.
- **이름 충돌** — "agent-mentor"는 예비 확인상 비어 있으나 미확정. 배포 전 npm/crates/GitHub/도메인 실조회 필수.

## 6. MVP 스코프 (우선순위)

| 우선순위 | 기능 | 난이도 | 차별성 |

## 7. Claude Code에서 활용할 스킬 / MCP

이 프로젝트는 여러 스킬의 도움을 받으면 훨씬 수월하다.

- **`skill-creator`** — 이 앱의 핵심 기능("반복 작업 → SKILL.md 초안 생성")을 만들 때 참조. 스킬 구조·description 작성법·평가 방식을 여기서 배운다. 앱 자체의 개발용 커스텀 스킬을 만들 때도 사용.
- **`mcp-builder`** — 만약 이 앱을 MCP 서버 형태로도 노출하거나(예: Claude Code가 Agent Mentor의 분석 결과를 도구로 호출), Context7 유형의 참조 MCP를 붙일 때 참조.
- **`frontend-design`** — 마스코트/채팅창/대시보드 UI를 만들 때. Webview 프론트의 디자인 토큰·스타일 가이드.
- **Context7 MCP** (외부) — Tauri v2 최신 문서를 실시간 참조해 v1/v2 혼동 방지. **설치 권장.**

**CLAUDE.md에 넣을 프로젝트 제약 (초안):**
```

  에이전트별 로직은 하드코딩하지 말고 파서/어댑터 인터페이스 뒤로 추상화할 것.
- 스택: Tauri v2 + Rust 백엔드. v1 API 사용 금지 (SystemTray, tauri::updater, WindowBuilder 등 구버전 심볼 금지).

```
