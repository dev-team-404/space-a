# 0002. 사람 뷰(space-view) 프론트엔드 스택 — Svelte 5

- 상태: 제안(Proposed) — 팀 리뷰 후 확정
- 날짜: 2026-07-15
- 관련: [space-view 설계](../design/space-view/README.md) 열린 질문 Q2

## 배경

space-view는 read-only 관전 서비스다. mock 프로토타입([`prototype/frontend-viz/`](../../prototype/frontend-viz/))은
프레임워크 없이 검증을 마쳤고, 라이브 API 연동(P1)부터는 프레임워크가 필요하다.
후보는 Svelte 5와 React로 좁혀져 있었다 (README Q2).

스택 선택에 영향을 주는 이 서비스의 성격:

| 성격 | 의미 |
|---|---|
| 표면이 적다 | 로비·씬·모달·대시보드 — 라우트 4개 수준, 폼·복잡한 상태 없음 |
| 씬 = 좌표 스프라이트 + 폴링 | 절대 좌표 오브젝트 수십 개가 짧은 주기 폴링(프레즌스·상태)으로 갱신 — 바뀐 필드만 최소 패치되는 게 중요 |
| 어댑터 계층이 자산 | C2 wire → 뷰모델 번역(c2-adapter)은 프레임워크 무관 모듈로 이미 검증됨 |
| 사내 관전 툴 | SEO·SSR 불필요, 번들·의존성은 가벼울수록 좋다 |

## 선택지 비교

| | **Svelte 5 (runes)** | React |
|---|---|---|
| 씬 갱신 모델 | 시그널 기반 세밀한 반응성 — 폴링으로 바뀐 스프라이트만 DOM 패치 | vdom 재렌더 — 좌표 오브젝트 다수에서 memo 튜닝 필요 |
| 프로토타입 이식 | 상태 → HTML 문자열 구조가 컴포넌트로 거의 1:1 이식 | JSX·훅 구조로 재작성 폭이 더 큼 |
| 번들/의존성 | 런타임 소형, 컴파일 타임 최적화 | 런타임 + 상태관리·memo 관례 추가 |
| 생태계·인력 풀 | 작음 — 단, 이 서비스의 외부 라이브러리 수요는 차트 정도 | 큼 (최대 강점) |
| Q3(캔버스 전환) 시 | 씬이 PixiJS로 가면 프레임워크는 패널·피드만 담당 — 양쪽 영향 동일 | 동일 |

## 결정 (제안)

**Svelte 5 + Vite SPA**를 제안한다. 데이터 계층은 프레임워크 밖에 유지한다 —
`fetch → c2-adapter(뷰모델 번역) → 스토어` 구조로, 어댑터는 프로토타입 코드를 승계.

React의 강점(생태계·인력 풀)은 인정하되, 이 서비스는 표면이 적고 외부 라이브러리
수요가 낮아 그 강점이 발휘될 면적이 좁다. 반면 "폴링으로 수십 개 오브젝트를 최소
패치"라는 씬의 핵심 부하에는 세밀한 반응성 모델이 구조적으로 맞는다.

## 결과

- (+) 씬 갱신이 기본 동작만으로 효율적 — memo/최적화 계층 불필요
- (+) 프로토타입 → 실서비스 이식 비용 최소, 어댑터·CSS 승계
- (+) 번들 소형, 의존성 최소 — 사내 툴 유지보수 부담 낮음
- (−) 팀·조직의 Svelte 경험이 React보다 얕을 수 있음 — 온보딩 비용
- (−) 채용·외부 예제 풀이 작음

## 확정 조건 (리뷰에서 확인)

   (기술 격차보다 팀 속도가 우선)
2. 대시보드 차트 라이브러리 요구 수준 (복잡해지면 생태계 가중치 상향)
