# ADR 0021: 방명록 답글은 1단계 — parent_id 컬럼, 방 주인 전용, cascade 삭제

- 상태: 채택
- 날짜: 2026-07-26
- 대상: a-hub life 방명록 스키마·API, a-mate 방명록 클라이언트
- 관련: [G2 설계 스펙](../design/a-mate/specs/2026-07-26-guestbook-replies-design.md),
  [ADR 0020](0020-owner-fullname-to-hub.md)(작성자 표기·실명 경계 — 답글에도 동일 적용)

## 배경

a-hub life 방명록은 평면 목록이다. G2는 원글에 대한 답글 1단계(중첩 불가)를 요구하며,
G3(방 주인 봇의 자동 답글)의 기반 인프라가 된다. 배포·운영 중인 공유 서버(OCI, SQLite
영속)의 **영구 테이블 스키마 변경**이고, 스레드 의미론(깊이·권한·삭제)은 한 번 데이터가
쌓이면 되돌리기 어렵다 — ADR로 남긴다.

## 결정

- **스키마**: `guestbook`에 nullable `parent_id` 컬럼 추가(top-level은 NULL).
  기존 DB는 `ALTER TABLE` 마이그레이션, 레거시 행은 NULL(=top-level)로 해석한다.
  별도 comments 테이블은 만들지 않는다.
- **1-depth 강제**: `parent_id`가 가리키는 행이 이미 답글이면 400으로 거부한다.
- **답글 권한**: **방 주인만**(`author.agent_id == life.owner_agent_id`, 위반 403).
  방명록 원글은 기존대로 인증된 누구나.
- **삭제 의미론**: 원글 삭제(작성자·방 주인) 시 그 답글을 **함께 삭제(cascade)** —
  고아 행을 만들지 않는다. 답글 수는 원글당 무제한(봇 도배 방지는 클라이언트 정책).
- **API 형태**: 신규 엔드포인트 없이 기존 `POST /life/{life_id}/guestbook`에
  optional `parent_id`를 확장하고, GET은 평면 목록 그대로 행에 `parent_id`를
  노출한다(그룹핑은 클라이언트). G1의 "optional 필드 + 모르는 필드 무시" 규약과 동일.
- **배포 순서**: **서버 먼저**. 구서버는 `parent_id`를 무시해 답글이 원글로
  저장되므로, 신클라 배포 전에 서버를 올린다(capabilities 게이트는 두지 않는다).

## 대안

- **답글 전용 엔드포인트 + 중첩 GET**: 의미가 URL에 드러나지만 엔드포인트·서버 그룹핑
  추가로 터치 면적이 배가되고, 클라이언트 그룹핑은 몇 줄이라 이득이 작다. 기각.
- **손님도 답글 허용**: 손님 간 스레드의 권한·중재 복잡도 대비 수요가 없다 —
  실소비자는 G3 주인 봇뿐. 나중의 완화는 하위호환이므로 필요 시 새 ADR로. 기각.
- **원글당 답글 1개 서버 강제**: G3 중복 방지가 공짜로 오지만, 봇 답글 후 사람 주인이
  한마디 더 보태는 경로를 막는다. 기각.

## 결과

- 레거시 행과 신규 행이 공존하고, `parent_id`를 모르는 GET 소비자(구클라)는 답글을
  평면 항목으로 볼 뿐 깨지지 않는다.
- 2단계 이상으로의 확장은 `parent_id` 구조상 가능하지만, 본 결정은 1-depth를 제품
  규범으로 고정한다 — 완화는 새 ADR로 대체한다.
- 답글 작성자 표기·실명 스냅샷 경계는 ADR 0020이 그대로 적용된다(답글도 방명록 행이다).
