# 0002. 레포 구성 — 계약 중심 하이브리드

- 상태: 제안(Proposed) — 팀 승인 대기
- 날짜: 2026-07-12
- 제안자: msalt

## 배경

[ADR 0001](0001-record-architecture-decisions.md)이 "레포 구성: 모노레포 vs 멀티레포"를
다음에 기록할 결정으로 예고했다. 이제 정할 시점이다.

다만 **교과서적인 양자택일 상황이 아니다.** 이미 벌어진 사실이 있다.

| Pillar | 담당 | 현재 위치 |
|---|---|---|
| 1. AI 사용 코칭 (Agent Mentor) | — | **이 저장소 밖.** Rust/Tauri 워크스페이스로 별도 개발 중 ([설계 문서](../design/overview-mentor/)만 이 저장소에 있음) |
| 2. 에이전트 자율 협업 공간 (Space A Hub) | msalt | 이 저장소 (아직 코드 없음) |
| 3. 커뮤니티 시각화 | 김주영 | 이 저장소 (`prototype/frontend-viz/`) |

즉 **"하나로 모을 것이냐"가 아니라, "이미 흩어진 것을 어떻게 정리할 것이냐"**가 실제 질문이다.

### 세 컴포넌트의 성격이 다르다

| | Pillar 1 | Pillar 2 | Pillar 3 |
|---|---|---|---|
| 스택 | Rust + Tauri (Windows 데스크톱 앱) | Python/Node (서버) | 웹 |
| 배포 | 각 임직원 PC에 **설치** | 사내 서버 **1대** | 사내 웹 **1대** |
| 릴리즈 주기 | 앱 버전 (느림) | 서버 배포 (빠름) | 서버 배포 (빠름) |
| 빌드 도구 | cargo | pip/npm | npm |

**공유 빌드 파이프라인을 만들 여지가 거의 없다.** 하나의 툴체인으로 묶으려는 시도가
오히려 셋 다 불편하게 만든다.

## 결정

**계약 중심 하이브리드**를 채택한다. 저장소를 억지로 합치지 않고, **계약만 한 곳에서 관리**한다.

### 1. 이 저장소는 "허브 + 계약 + Pillar 2/3 구현"

```
space-a/
├── contracts/          ★ 세 컴포넌트를 잇는 유일한 결합점 (single source of truth)
│   ├── c1-mcp-tools.json      Pillar 2 → 임직원 에이전트 / Pillar 1
│   ├── c2-rest-api.json       Pillar 2 → Pillar 3
│   └── fixtures/              서버 없이 먼저 개발하라고 주는 응답 예시
│
├── docs/               설계 문서 (세 Pillar 전부) + ADR
│   ├── adr/
│   └── design/{collab-space, frontend-viz, overview-mentor}/
│
├── hub/                Pillar 2 구현 (예정)
├── web/                Pillar 3 구현 (현재 prototype/frontend-viz/)
└── prototype/          실험용. 정식 구현으로 승격되면 위로 이동
```

### 2. Pillar 1은 별도 저장소로 유지한다

되돌리지 않는다. 이유:

- **이미 상당히 진행됐다.** 되돌리는 비용이 얻는 것보다 크다.
- **스택·배포 주기가 완전히 다르다.** 데스크톱 앱을 서버 코드와 같은 CI에 묶을 이유가 없다.
- **결합점은 C1 하나뿐이다.** Pillar 1은 Space A의 MCP Tool을 호출할 뿐, 코드를 공유하지 않는다.
  계약만 맞으면 **어디에 있든 상관없다.**

대신 **설계 문서(`docs/design/overview-mentor/`)는 이 저장소에 유지**한다.
세 축의 설계를 한자리에서 볼 수 있어야 한다.

### 3. `contracts/`가 유일한 결합점이다

이 결정의 핵심이다. **레포가 몇 개인지는 중요하지 않다. 계약이 한 곳에 있느냐가 중요하다.**

- 세 컴포넌트는 **코드를 공유하지 않는다.** 오직 `contracts/`의 스키마를 참조한다.
- 계약이 바뀌면 **여기서 바뀌고**, PR로 리뷰된다.
- 소비자(Pillar 1/3)는 이 파일을 **복사해 가거나 URL로 참조**한다.

### 4. 멀티레포로 완전히 쪼개지 않는 이유

Pillar 2와 3을 각자 저장소로 떼는 것도 가능하지만 **하지 않는다.**

- 3인 규모에 CI·버전 동기화 비용이 이득보다 크다.
- **계약과 소비자(Pillar 3)가 같은 저장소에 있으면**, 계약을 바꾸는 PR에서 프론트가 깨지는지
  바로 보인다. 이게 실질적인 안전망이다.
- Pillar 1이 밖에 있는 것만으로 "서로 다른 릴리즈 주기" 문제는 이미 해결됐다.

## 결과

### 좋아지는 것

- **계약이 한 곳에 있다.** 세 컴포넌트가 흩어져 있어도 결합점은 하나다.
- 각 컴포넌트가 **자기 스택에 맞는 툴체인**을 쓴다. 억지 통합이 없다.
- Pillar 2·3이 같은 저장소에 있어 **계약 변경의 영향이 PR에서 바로 보인다.**
- Pillar 1을 되돌리는 비용이 0이다.

### 감수하는 것

- **Pillar 1은 계약 변경을 자동으로 못 잡는다.** 저장소가 달라 CI가 안 걸린다.
  → 완화: `contracts/`의 **변경 정책(추가만 허용)**이 1차 방어선.
    C1을 깨는 변경은 버전을 올리고 별도 고지한다.
- 저장소가 2개라 **전체 상태를 보려면 두 곳을 봐야 한다.**
  → 완화: 설계 문서는 전부 이 저장소에 모은다.

### 나중에 바꿀 수 있는가

- **Pillar 1을 이 저장소로 흡수**하는 것: 가능하다. 계약이 유지되므로 위치만 옮기면 된다.
- **Pillar 2/3을 각자 저장소로 분리**하는 것: 가능하다. 이미 코드를 공유하지 않는다.
- 즉 **이 결정은 되돌릴 수 있다.** 되돌리기 어려운 건 `contracts/`를 없애는 것뿐이다.
