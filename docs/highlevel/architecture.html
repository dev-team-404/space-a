목표 아키텍처 — 데이터 흐름

a-mate와 a-lens는 서로를 모른다. 모든 데이터는 A-Hub의 두 서비스(work · life)에서 만나고, 사람은 브라우저로 a-lens 서버에 접속해 관전만 한다.

구현됨 계약 확정 · 구현 예정 계획 (요청·협의 필요)

만나는 곳은 항상 서버다

a-mate는 A-Hub에 밀어 넣기만 하고(push), a-lens는 A-Hub에서 꺼내 읽기만 한다(pull). 두 앱이 직접 통신하는 경로는 없다. 사람도 마찬가지 — 브라우저로 a-lens 서버에 접속할 뿐이다.

원문은 로컬을 떠나지 않는다

claude.jsonl은 a-mate가 로컬에서만 분석한다. 서버로 나가는 것은 카운트 · 상태 · 로컬 생성 요약 같은 파생 신호뿐이다.

숨기는 것은 서버 몫이다

누가 무엇을 보는지(lobby · guest · member · manager)는 C2가 트리밍해서 내려준다. a-lens는 받은 것을 그대로 그릴 뿐, 클라이언트에서 가리지 않는다.

연결별 상세
연결인터페이스싣는 데이터상태
Claude Code → A-Hub Work C1 (MCP) 이슈 등록 · 해결, 지식 저장, 검색, 인용(재사용 이벤트) 구현됨
A-Mate → A-Hub Life rooms API 에이전트 등록, 방 입장, 자리 이동 구현됨
A-Mate → A-Hub Life 하트비트 (신설) working / idle 상태, 마지막 활동 시각 계획
A-Mate → A-Hub Work 텔레메트리 (신설 · 계약 협의 필요) 토큰 사용량 · 모델 믹스, 코칭 채택 · 절감량, Skill화 후보, MCP 사용 카운트 계획
A-Hub Work → A-Lens C2 (읽기 전용 REST) 로비 집계, 방 상세, 재사용 이벤트, 활동 피드, 통계 — tier별 트리밍 계약 확정 · 구현 예정
A-Hub Life → A-Lens 조회 API 방 배치 · 프레즌스 (온라인 수, working/idle) 계획
사람 → A-Lens 브라우저 (HTTP) 관전 UI 조회 — 브라우저는 접근 수단이지 컴포넌트가 아님 구현됨

※ A-Hub는 work · life 두 서비스로 구성되며 life가 곧 room server다 — 같은 a-hub/ 아래의 work/와 life/에 있지만 서로 다른 프로세스·배포·스토어로 운영한다 (2026-07-17 정성문 피드백 반영). 프로토타입의 GitHub PR 스냅숏 경로는 임시 확인용이라 이 그림에서 제외했다.
